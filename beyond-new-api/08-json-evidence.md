# 08 完整JSON响应的证据合并候选

2026-11-17。状态：第一片已实施，定向验证与60RPS连续两轮通过，完整故障矩阵及最终验收未完成。目标仍是完整链路稳定严格超过3000RPS、CPU≤2ms及强资金保证；本片不代替资金cells、批量SQL或生产HA验收。

## 1. 实际热点与范围

S3c40次轮2529个含预热请求生成5058个receipt：4690 ACCEPTED、368 STALE。CANONICAL头均FINAL，2529个revision2及2161个revision4；没有证据支持把该短JSON容量的主要成本归给ESTIMATED。

当前observeAttempt在response hook返回FINAL usage时先单独publish；Gateway随后的control.end又以相同usage发布带终态的FINAL。两次各等待耐久接纳，worker通常在两组不同事务分别处理。已有PG group协议支持同attempt多事件，并在整组事实判定后只做一次供应结算及客户结算。

因此暂缓不作用于该热点的ESTIMATED跳资金锁候选。它的保守安全条件及terminal未收费反例另有只读审计，不能直接按finality删除资金锁。

## 2. 第一片目标行为

仅同步chat、manifest.stream=false且facts.background=false的完整JSON响应可选择终态组模式；其他操作、背景资源、poller、SSE及第三方的流式过程继续及时接受证据。平台Worker与第三方Wasm沿相同证据规则，不因执行器类型改变收费。

保持原两份事实及其event_id、source_revision、usage、finality和终态字段，不删除已生成事实或更改历史schema。响应hook产生的第一份FINAL暂存于该attempt唯一所有者；finish把它与原终态事件按同一durable group提交。成功响应任何字节发给客户端前必须完成该组WAITAOF和副本确认。worker仍在PG提交后ACK，任何组ERROR均不ACK。

只暂存至多一份FINAL，容量固定。若finish前发生另一次观察、partial/unknown更新或其他需及时记录的变化，先把原待提交事实耐久接纳再继续原规则，不允许无界积累或覆盖事实。attempt关闭/取消须释放引用；dispose不偷偷发布或宣称已经接受。

## 3. 有意改变的边界

内部response hook返回不再表示那份暂存FINAL已经单独durable；该保证转移到finish整组成功。必须显式迁移所有依赖此时序的调用方与测试，不能伪称内部契约完全不变。组内事件仍分别由Gateway签名，当前PG独立验证其owner、revision及事实。

若Gateway在生成用量后、终态组耐久之前崩溃，内存事实可能未被接受，原PG客户/供应预扣与permit继续承担UNKNOWN责任，不按超时释放或假造NOT_EXECUTED。相较原实现，已知用量到耐久的窗口延伸到finish；不能宣称恢复事实及时性毫无变化。已成功返回的请求必须拥有相同或更强的完整证据保证，故障时责任仍有资金覆盖；若无法证明这两项，本片不切换。

JSON解析失败、插件失败、客户端取消和请求截止即使发生在FINAL生成后，也必须把原用量与原规则选定的实际终态记录，不因合并少收供应成本、误判客户成功或重发上游。若整组接纳回执不明，继续UNKNOWN而非假回滚。此前发出的partial不被移入终态缓冲。

本片不引入“FINAL后客户取消必为CANCELLED”的新收费规则。沿现完整JSON路径，合法完整terminal/body且资源声明检查通过后，调用方只选择一次SUCCEEDED并进入独立证据封存；取得合法完整结果前的中断沿原失败/UNKNOWN路径，终态选择之后的断连或截止不反写相反终态。需用真实门控区分最后观察返回、终态seal及WAITAOF等待三处竞争，不能仅凭observer缓冲声称已覆盖这些时序；若发现原实现与该已完成请求语义有缺口，先单独记录证据，不借合组暗改金额判定。

seal固定签名身份，不固定PG授权。PG仍在处理时持锁核security_revoked_at；seal后到flush前吊销可使整组两事实均QUARANTINED，而旧拆组可能已有第一份ACCEPTED。此派生差异必须保留UNKNOWN预扣责任且禁止越权结算，不声称所有竞争情形最终金额/可结算性都完全相同。

最小片不允许缓冲跨越retry/deferred：relayJSON在terminal缺失、非法resource等情况下可进入retryLater，原previous.conclude可能推迟到下一次BEGIN之后，且旧deferred会吞接纳失败。进入任何重试、健康上报或下一准入边界前，先显式flush已seal FINAL并恢复原单事实接受路径；不能把本片窗口悄悄延伸到下一attempt。若flush接纳失败，不得继续下一上游发送。成功或已知最终失败紧邻finish时才合组。

## 4. 接口与迁移

拟把observeAttempt的record从单事件改为有界事件数组，另用显式seal回调在事实生成时立即签名，缓冲只保存该已封装事实，避免把签名身份选择推迟到flush。seal与record采用泛型所有权，plugin-host不引入Core客户端或保存其私钥。所有直接调用方和单测同步迁移，不保留旧record别名。两种delivery模式都显式声明；progressive每次提交单元素组，只有明确的同步chat JSON调用方启用terminal-group。复用现有CoreEvidenceGroupV1及UsageProducer，不新增持久wire版本、数据库字段或兼容分支。

observer须提供有界flush供上述边界使用；成功后释放唯一待提交引用，失败仍保留原已seal身份及原接纳未知语义，不重新生成event_id冒充新事实。dispose只释放，不隐式写入。

仅response hook的FINAL可暂存，stream_feed/end/drain即使报告FINAL也仍立即提交，避免上游意外返回SSE时被请求参数误导。所有观察、flush和finish沿现Gateway顺序await；同attempt并发操作明确拒绝，不引入隐藏无界任务队列。dispose阻止迟到插件结果产生新事实，已经开始的耐久I/O由原调用方等待收敛，不能宣称撤销了已接纳事实。

原client在Gateway启动时注册一次，signEvidence使用该receipt及私钥；reconnect本身不换receipt。仍须验证有意再次startup或close时不会替换已封装事实，不能从缓冲重新读取当前身份重签。跨session终态不获原permit授权，沿原拒绝和UNKNOWN边界；本片不增加继承旧permit的能力。

PG原group按全部事件先判冲突，再统一处理资金。两份正常同用量FINAL在组内依次ACCEPTED，latest canonical为revision4，仅做一次supplier settle。旧拆组逆序可能得到STALE，canonical及cost版本条数也可能不同；目标等价是保留原签名事实、最终金额与责任，不承诺逐条receipt outcome或内部版本历史相同。此差异须在新性能报告列出。需要实测核对两份RAW及receipt、客户收费、供应expense与reserve，并确认同组两份FINAL不误判争议。历史拆分组保留读取、重投与结算能力。

## 5. 验收

- 单独观察尚无外部成功；finish前后耐久边界明确，event_id及revision不变，最多一份暂存。
- JSON成功、带usage的失败、取消、截止、第二次观察与组接纳未知均有独立期望；partial和SSE仍及时接受。
- 真实Gateway/Redis/PG证明成功前整组已确认；暂停或杀Gateway在组前/组后、worker在提交前/后、ACK丢失均保留资金责任和幂等。
- 真实同组对照核两份RAW/receipt、客户与供应journal、费用与hold，含同revision冲突、旧拆组重放、组内失败隔离；不调弱旧资金断言。
- 审查内部生命周期与消费方、跑全部仓库检查和耐久/备份，再以同构建连续两轮严格容量及同并发对照量化收益。没有数据前不承诺倍增或最终达标。

## 6. 第一片实测

定向17例80断言通过，类型检查339文件及lint/build退出0；资金独立只读审查无阻断问题。这些结果没有覆盖§5全部故障竞争，完整门禁也未为每个小改动重复执行，不能称本节全量验收完成。

同构建、1000钱包、单供应账户、256并发、16预热并发、worker并发8、证据AOF always及副本确认，60目标/61到达连续两轮通过：窗口交集均3646，HTTP P99为358.88/374.77ms，服务CPU24.948/25.155ms每请求，PG顶层调用56.831/57.382、执行23.644/24.012ms、WAL60686/60780字节每请求。每请求两份RAW/receipt均保留，客户收费100且双方reserve为0。次轮结束后工具句柄已被回收，退出码未取得，归档明确为null；原始audit、HTTP和cleanup均保留。

100目标/101到达一轮失败：正式6060请求最终全部成功，但窗口完整交集4902，且PG统计发生驱逐使审计无效；不把该轮PG数字用于有效比较、不重复压测掩盖失败。下一片见09，仍未达到3000RPS或CPU≤2ms。
