# 11 短 JSON 主链的容量差距与重构

## 1. 目前卡在哪里

在同一台 12 核机器上，v2 的 S5 稳定档为 60 RPS，两轮加权服务 CPU 为 25.051 ms/请求，其中 PG 为 16.617 ms。new-api 的真实正额预扣对照在 3000 RPS 两轮通过，服务 CPU 为 2.100 ms/请求，其中 PG 为 0.828 ms。v2 的总 CPU 成本约为参考的 12 倍，PG 约为 20 倍。参考的 Redis 缓存、上游传输和处理完成条件与 v2 有差异，数字用于定位数量级，无法直接分摊每项契约的边际成本。[参考基线](../docs/performance/p0-2026-11-17.md#3-最高已确认稳定档) [S5 实测](10-funding-engine.md#1-实测依据与范围)

按 S5 的全成功成本线性估算，3000 RPS 需要约 75 个 CPU 核，其中 PG 约 50 个核。即使把 PG 成本降到零，其余 8.434 ms/请求仍需要约 25 个核。12 核全部用于产品也只有 4 ms/请求，2 ms 的目标给上游、负载器、外部消费者和操作系统留下约 6 核。现有成本结构需要同时改 PG 和联网进程的热路径，单独扩连接池、增加 Worker 或修改批大小无法达到预算。

CPU 差距之外还有事务和排队放大。1811 的相同 300/301 档下，跨任务合并把 PG CPU 从 35.908 降到 23.968 ms/已准入，但结算与 ACK 的窗口交集由 115.40 降到 86.73 RPS。约第 59 秒，队列等待任务由 1101 增到 1687，排空从 15.7 秒增到 41.2 秒。合并轮在 60 秒内约有 14760 个有效 HTTP 完成，其中约 5200 个在窗口内取得结算 ACK。失败轮 CPU 包括拒绝工作，分母仅为已准入，需与 S5 的全成功成本分开解读。[同档证据](../docs/performance/implementation-2026-11-17.md#21-worker跨任务合并的反例)

PG 语句累计执行时间包含等待，嵌套项与入口重叠。暂时无法把 42% 的冲突输出归因给某一种锁，也不能从频次反推其独立 CPU 成本。最新诊断库增长后的总大小约 618 MB，除以 15039 个已准入约 41 KB/请求，含样本固定开销。按当前大小粗推 3000 RPS 为每小时约 444 GB 关系存储、约 698 GB WAL 写入量。WAL 写入量不等于留存空间。以既有装置的默认 5 KB/请求做长测空间估计可能偏低，长测前要从候选构建重测字节增长。

## 2. 结构方向

选择压缩本机每请求实际工作量。Gateway 保持无 PG，Core 保留发送前的权威授权和预扣，Worker 保留证据、账单、流水同一 PG 提交及提交后 ACK。Gateway 成功返回前，完整证据组仍交给现行 Redis WAITAOF 耐久路径。扩大机器可以增加容量，但保留每请求成本、供应单账户竞争及锁重试，无法满足本机预算。用更少证据或放松持久性获取的吞吐无法验证现行契约。

1. **结算批从输入键查找。** 先让组依赖检查从本批 UUID 逐项按主键取 attempt、hold、wallet，限定读取规模。真实回归确认两处全扫消失后，连接级查询计划在 `settle_requests` 读取账单快照的争议判断中仍捕获到全表扫描。为 `metering_conflict` 增加部分索引，集合查询只需要访问争议记录。保留跨组共用 attempt、事件或钱包、可到期授信、争议和重放的现有顺序。通过真实签名组结算，在无关历史增长后观察表行读取，核对独立归组、回执和扣账。
2. **缩小批事务的锁与计算范围。** 用工作量受限的并行分组验证独立调用。按正式持锁生命周期度量钱包、request 和 cell 冲突。若组间锁重叠经证实占主因，使用现有权威关系解析依赖后组批，同组原子性由存储负责。对普通成功组探索 typed、逐 attempt 暂存和批尾集合写，先计量批内 JSON 重建和重复扫描，再替换确实占预算的部分。例外走同一权威状态和账本。
3. **收缩发送前控制面交互。** 将可推导的 context 改为带修订版、身份、候选和明确有效期的投影。优先验证 ADMIT 用现有 verifier 在 PG 独立定位客户、从权威事实复核的路线，避免 Core API 数据库角色自行声明客户主体。verifier 由受签名保护的客户凭证派生，原 token 不入库。BEGIN 保留当前配额证明和提交不确定时的单次发送语义。先验证吊销、候选更新、待确认提交、重放和执行恢复，再比较 RPC 次数、WAL 与 CPU。[权威校验边界](05-implementation.md#无状态context的sql权限缺口)
4. **压测预算闭合。** 完整短 JSON 路径进入 300 RPS 诊断时比较同配置的 CPU、排队时间和逐 ID 交集。随后逐档升压，直至两个完整 60 秒轮次、60 分钟长测与同并发对照均满足原容量契约。只有故障注入和相关全量门禁通过，才可交付最终候选。[容量契约](../docs/performance/capacity-contract.md)

## 3. Worker 调度的单独对照

将批内完整原任务上限和存储并行度一起作为调度候选，与同 schema 的原调度做相同 300/301 档对照。候选最多合并 4 个任务，最多 4 路存储调用并行，仍受 128 个完整组的总权重上限约束。每个任务至少占用 32 组权重，待处理总权重仍不超过 4096。大任务保持完整，忙时 1 ms 收集、结果归属、组级重试和提交后 ACK 保持原有顺序。此次比较回答整体调度是否减少积压。它无法分辨两项参数的独立贡献，记录每批实际任务和组数、冲突密度及窗口吞吐判断是否保留。

1812 的四路候选在同 schema 的失败 300 档中，把窗口吞吐由 86.18 提到 122.20 RPS，排空由 39.48 降到 18.84 秒，同时提高了服务 CPU、503 和冲突输出比例。候选在全链路耐久配置下取得连续两轮 100 RPS，服务 CPU 仍需 23.270 ms/请求，其中 PG 17.560 ms。即使消除全部 PG CPU，其余服务按 3000 RPS 仍需要约 17 个核。下一片同时验证结算事务和发送前控制面能削减的实际工作量。[验收记录](../docs/performance/implementation-2026-11-17.md#100-rps-连续验收)

## 4. 按阶段核算下一片收益

两次 100 RPS 通过轮的加权成本为 PG 17.560、Gateway 含内置适配器 2.260、Core API 2.018、Core worker 0.483、三类 Redis 合计 0.950 ms/请求。以真实正额预扣的参考数据比较，总成本差约 11 倍，PG 约 21 倍。WAL 约 60 KB/请求，即同吞吐下约为参考的 23 倍。量级说明索引命中和 Worker 并行是改善当前容量的措施，下一阶段要同时降低单位请求工作量和写放大。[参考基线](../docs/performance/p0-2026-11-17.md#3-最高已确认稳定档) [连续通过记录](../docs/performance/implementation-2026-11-17.md#100-rps-连续验收)

合并两轮的 PG 顶层统计，执行批和证据持久化入口累计 333 秒，占顶层执行时间约 81%，两者合计产生 564 MB WAL，占约 76%。context 入口自身约产生 3.17 KB WAL/请求。去除 context 写入还要配合减少准入重读、阶段间序列化和结算事实的写放大。顶层累计执行时间是跨会话的数据库执行时间，包含等待。[原始审计 A](../docs/performance/evidence-implementation-2026-11-17/s7-worker-four-way-100-a/audit.json.raw) [原始审计 B](../docs/performance/evidence-implementation-2026-11-17/s7-worker-four-way-100-b/audit.json.raw)

- **发送前持久化。** Gateway 必须先取候选才能执行适配器准备，ADMIT 必须拿到准备产物和请求摘要才能预扣。将这两个动作拆成只读取路由与首次持久化授权。路由阶段按当前目录和客户权威构造短期投影。准入阶段用证书会话、客户 verifier、目录版本、请求体摘要及当前资源归属重核，事务内同时落请求、预扣、命令和许可。将 BEGIN 需要的客户主体和具体候选绑定保存在已有权威记录。测量由此节约的查询、网络字节及 WAL，并逐项核对重放、租约、吊销和最晚发送边界。
- **结算事务。** 先在测试库为同一签名样本对照互斥的单组调用与多个独立组的集合调用，记录每组的进程 CPU、访问行和缓冲、SQL 执行、WAL、回落与锁键类别。生产候选以批内有效 attempt 和事件键为输入，逐个计算精确金额和快照，再一次写入各事实、余额差额和流水。持锁后仍由 PG 复核可用额和共享钱包依赖。对重复、争议、退款、过期授信和部分失败验证与现有资金结果等价，独立观察较短锁持有时间是否降低 Core 准入重试。
- **整链对照。** 以当前 100 RPS 的 23.270 ms 为成功路径基线。先在相同环境对候选测同档 CPU，再提高负荷观察结算积压和准入 503。隔离微测用于选择结构，最终用真实资金、WAITAOF、逐 ID 交集和两个稳定窗口共同验收。长期空间预算按候选数据库增长率与可用磁盘重新计算。[容量契约](../docs/performance/capacity-contract.md)

## 5. 1813 准入读取与结算事务首片

准入批从输入提取真实 context 和 attempt UUID，再去重读取客户权威。共享锁仍按组织、主体、项目、Key 的原顺序获取，取锁后仍比较读取前后的归属。ADMIT 与 NEXT 合在一次数据库往返中先查已有命令，未命中才读取上下文。BEGIN 与配额同步只接收许可状态、epoch、关闭状态和租约，PG 在原来需要重核的命令上仍从 context 取权威字段并授权。首次路由处的完整 context 写入及其历史依赖继续由后续迁移处理。

证据事务在现有生产者、钱包、request、permit 和 hold 锁保护下，按本批实际会话和 attempt 读一次对应权威行，再按每个事件核对来源、epoch、代理资源及撤销状态。按实际投递、事件和修订键读取已有回执，并在本次分类中复用结果。有既存回执、修订或隔离状态的批次直接走原组。首轮提前锁资金 cell 的候选在 300 档回退，修订后等分类和依赖复核完成，再按原顺序以 `SKIP LOCKED` 获取本批实际需要的 cell。如果某原组需要的任一 cell 忙碌，整组返回 `55P03`，其余独立原组继续同事务集合落账，按原顺序拆回结果。资金、冲突、估算和特殊慢路继续复用原实现。

成功短 JSON 的收尾仍在证据耐久确认之后等待 `OBSERVE`。Core 用该调用释放渠道探测占位，更新结果和延迟统计。实测窗口交集仍要求有效 HTTP、精确 PG 提交和外部 ACK。[1813 的诊断与连续验收](../docs/performance/implementation-2026-11-17.md#23-1813-准入读取和结算组隔离)

## 6. 结算批的有类型暂存

200 档归因中 14229 次组级锁冲突有 14208 次来自供应资金单元，含重投。停止准入后，串行排空无锁冲突仍只有约 147 笔/秒。对照据此从持锁期间普通结算组每次重建整批 JSONB 的工作入手。证据权威读取和锁边界保持原顺序。阶段内按 attempt 和 request 保存有类型的状态，按事件追加证据及回执记录，再集合写入。存量证据摘要、事件与快照顺序、精确计价、原子组、锁冲突回退、特殊路径、提交后 ACK 继续执行现有契约。

200 和 300 档是同口径比较点，用于定位失败段和选下一次到达率。容量目标仍是 3000 RPS 完整链路，按连续轮、长测及故障恢复契约验收。新批次实现根据逐笔金额、证据与回执一致性以及同档窗口完整吞吐决定是否保留。[锁归因](../docs/performance/implementation-2026-11-17.md#24-结算资金锁归因) [容量契约](../docs/performance/capacity-contract.md)

## 7. 持续 3000 RPS 重构

本轮只按同机完整短 JSON 的 3000 RPS 验收。结算先复用同事务内已验证的预扣、规范用量及精确计价。普通首次完整且无风险的组按笔生成成本与流水，余额继续由现有资金单元事务提交。发生重放、历史修订、部分或越界用量时执行已有资金规则。上线顺序先追加数据库迁移，再切换应用。历史账单、证据和待确认命令继续按原身份恢复。

无资源的短 Chat 准备阶段只需路由投影，准入阶段由 PG 依据 verifier 复核客户与实际候选，保留 BEGIN 的一次发送权和配额证明。Gateway 只有在完整结果和签名原子组有独立所有者时才能归还插件槽，成功响应仍等待队列的 AOF 副本确认。已发送且结果未知的请求保留资金责任。验收按每个 request ID 核对 HTTP、精确 PG 提交、外部 ACK，连续两轮 60 秒后再验 60 分钟。

部署时先运行迁移，再升级全部 Core API 并摘除旧实例，最后升级 Gateway。旧 Gateway 可以继续使用持久 context。回滚时先回退 Gateway，等正在使用路由票据的请求排空，再回退 Core API，并保留数据库中的上下文与命令供恢复使用。

在无资源的短 Chat 路径上，Gateway 在向 Core 查询路由之前预留插件槽，绑定插件时接管同一槽位。目录候选的私有投影指纹由同一个 PG 实例对 JSONB 文本计算，外部账单、签名和回执摘要仍由原算法生成。结算普通成功组在同一次请求行更新中写入终态与首次关闭时间，只有本次首次关闭的请求才推进配额释放。

## 8. 1817 准入与结算的写入边界

首次完整正额结算从每笔已锁定的供应预扣计算成本，逐笔保存成本头、平衡分录和流水。按实际账户、币种、资金单元汇总余额增量，一次检查每个单元的可用资金、支出上限和修订余量，再统一写回。短 Chat 的同钱包组只有在每笔均由单一预付批次足额覆盖、无到期资金、授信、债务或历史修订时才能集合落账。客户和供应成本分别按原规则逐笔取整。超出 64 条证据时，以完整签名组为单位拆窗，在同一事务内结算，保留原有组序和回执身份。任何组不符合条件时仍按原组执行。

准入分配器在插入请求、attempt 时写入执行预算和绑定关系。历史分配器所有者只有列级插入权限时，执行入口在同一事务补齐字段。BEGIN 的幂等查询和租约读取共享一次数据库往返，首次激活三个范围的租约时统一检查身份、版本及剩余有效时间并集合写入。READ COMMITTED 下，BEGIN 用事务共享锁保护钱包发送资格，冻结与解冻取得同一标识的排他锁。普通余额变动继续使用原资金行锁。历史及新增的未决证据争议都会冻结钱包。

外部签名及证据摘要继续按 UTF-16 键序计算。仅有 ASCII 字段名的对象可以直接按同序的 C 排序规则编码，混合 Unicode 的对象仍逐个计算 UTF-16 键序。

结算的一个批次只涉及一个钱包且遇到行锁时，仅在该 SQL 语句开始后的 12 ms 内按原取锁顺序等待，拆窗和原组回退共享这个截止时间，并继承调用方更短的锁超时。超时继续返回可重试结果；多钱包事务仍按钱包标识排序并立即退让。在同一个尝试内等正在提交的事务完成，可以避免反复重验同一批签名证据。配额激活从本次提供的租约 ID 逐一取主键行锁，再按同一批已锁 ID 写回，避免激活成本随租约历史增长。
