# ADR 0012 渠道插件定义、修订发布与验证

- 状态：已实施
- 基线：`5b63227`
- 前置：[ADR 0009](0009-enterprise-gateway-worker-architecture.md)、[ADR 0010](0010-provider-plugin-architecture.md)、[ADR 0011](0011-production-operations.md)

## 目标

每个内置厂商独立维护声明式定义，继续共享执行器与通用协议实现。已有仓库内的 Provider 和 Content 插件使用统一定义、启用前预检、不可变修订及显式绑定。对现有部署保留实际生效的配置和历史账务。以官方协议文档独立构建本地上游假体，并用真实网关、账本和多节点拓扑验证功能、性能及故障恢复。

## 目标架构

- `plugin-engine` 维护四类插件的定义校验、请求适配、内容处理、精确计量边界和 WASM 运行约束。`ledger` 持有目录、不可变修订、绑定和发布审计。Gateway 编排请求并构建按配置纪元隔离的执行计划。凭证、出站网络和结算由宿主持有。
- 以 `capability` 和 `kind` 区分 `PROVIDER/DECLARATIVE`、`PROVIDER/WASM`、`CONTENT/WASM`、`CONTENT/WEBHOOK`。冻结修订前验证配置格式、声明的操作和 hook、目标宿主 ABI、签名与资源预算。插件编辑、预检、启用是独立动作。定义与 OpenAPI 使用同一校验来源。
- 渠道绑定一个 Provider 修订，路由绑定渠道、上游模型和有序的 Content 修订。配置优先级为 Provider、渠道、路由；映射按键覆盖，转换按顺序执行。请求选择一个快照，备用路由重新适配原始输入。预览和实发共享处理计划。出站凭证在适配后注入。回程分别校验计量与协议终态，账务提交后发成功终态。
- 发布提交时核对预检摘要和目标绑定版本，并在同一事务写入前后绑定、操作者、幂等结果和 `config_epoch`。Redis 通知加速，PG 轮询补偿。以实际已应用的快照和修订报告收敛。回滚为一次带并发检查的反向切换。普通切换允许在途使用原修订，紧急撤销通过纪元传播中止相关调用，已发出且结果不明的尝试保留 `UNKNOWN`。
- WASM 宿主按修订摘要校验执行身份与缓存结果。队列、并发和缓存按资源预算收敛，失败后回收或替换执行槽。声明式渠道保持本地计划执行。

## 验证口径

- 用 `bun run bench:single` 与 `bun run bench:prod` 对相同机器、并发、请求组合、Mock、数据库耐久条件做改造前后对照。记录实际成功结算吞吐、P99、错误分类、尾部排空和账务守恒，标准短 JSON 沿用 ADR 0010 的 12,000 RPS 门槛。多节点伸缩与极限期间的拒绝请求分别计量。
- 多渠道验证必须从 Gateway 正常入口发起，Mock 依据官方文档独立验证线协议。按预设记录 JSON、SSE 或二进制流覆盖点，测试地址使用环回和合成凭证。性能使用相同固定工作负载，渠道正确性矩阵单独计量。
- 复用 `bun run verify` 和 `bun run test:production`。通过实际故障注入核对丢通知、进程重启、配置收敛、坏修订、并行发布和回滚、PostgreSQL 与 Redis 主备恢复、资金守恒。插件重负载建议做 30 分钟稳态，健康节点正常发布传播目标 P99 不超过 3 秒，按环境单独报告结果。

## 已交付的管理操作

1. `PUT /internal/v1/plugins` 创建修订，默认停用。同名同版本原样重复提交复用已存在的修订，改变其规范返回 `409 plugin_revision_conflict`。数据库也禁止原地替换修订。内置安装也只创建草稿，两个入口均拒绝 `enabled` 字段。
2. 渠道初始化时允许按名称选择预设，写入时固化为 UUID。已有渠道的 Provider 和已有路由的 Content 链仅通过发布操作切换。发布前验证各项绑定。
3. `POST /internal/v1/plugin-releases/validate` 按当前 `expected_epoch` 验证目标绑定。目标以 `channel_id` 与 `provider_plugin_id` 表示渠道变更，或以 `route_id` 与 `plugin_pipeline` 表示内容链变更。首次启用可用 `{ "plugin_id": "<修订 UUID>" }`。WASM Provider 预检提交 `samples`，以修订 UUID 为键，提供 `request`、需要的 `response` 和终态 `event`。执行预检使用独立的有限执行池。
4. `POST /internal/v1/plugin-releases` 接收同一结构，重新验证后原子切换绑定。`id` 是调用方生成的幂等 UUID，响应包含数据库提交纪元、当前节点应用纪元、提交时固定的 `expected_nodes` 和节点确认清单 `nodes`。`GET /internal/v1/plugin-releases/:releaseId` 查询记录。
5. `POST /internal/v1/plugin-releases/:releaseId/rollback` 接收新的幂等 `id`、当前 `expected_epoch` 及必要样例。回滚校验旧绑定与当前路由，目标被后续发布改动时返回冲突。

6. `POST /internal/v1/plugins/:pluginId/revoke` 接收 `reason`。撤销事务记录操作者和纪元，并永久停用该修订。已撤销的路由退出新请求的选路，其他健康路由仍可承接该模型。值班人员发布并绑定新修订恢复受影响的路由。

## 发布确认和紧急撤销实施

- 上传和内置安装只创建草稿。首发可用修订编号作为发布目标，通过同一预检和纪元事务完成激活。渠道和路由可在修订激活后首次绑定。
- Gateway 以独立进程编号登记，使用独立快照连接池（`SNAPSHOT_DB_MAX_CONNECTIONS`）持久化最近应用纪元与心跳，避免数据面连接池打满影响配置刷新与撤销收敛。发布事务固定当时有新鲜心跳的节点。只有持久化了该纪元的应用确认才报告 `APPLIED`。无应用确认且节点已越过纪元时为 `SUPERSEDED`。尚未追上且超过 6 秒未见心跳或正常停机时为 `OFFLINE`，其余为 `PENDING`。Worker 主节点按小时清理超过 24 小时且无发布引用/确认记录的离线历史节点。
- 快照重载支持按插件 `(id, digest)` 增量复用 `wasm_bytes`（仅拉取新增或修订变更的 WASM 二进制），并在运行时严格按渠道固定 `provider_plugin_id` 解析（`resolvePinnedProviderPlugin`）。`config_epoch` 维护随版本号自动轮换的 `lineage_token`，配合撤销集合单调性校验拦截 PITR 回退分叉。
- 撤销是持久化的单向变更。节点安装包含撤销的新快照时停止与对应修订关联的在途工作。已确认未发出的尝试释放，有上游执行可能的尝试保留 UNKNOWN。被撤销修订不能重新发布或作为回滚目标。数据库或网络故障期间，在线节点依靠 Redis 与 PG 两条传播路径，节点安装包含撤销的快照后才能作出确认。已进入提交的账务事务仍按实际数据库结果核对，观察到撤销的请求停止发送客户端成功响应和终态。原生 WASM Worker 的请求会立即解除等待，已进入原生运行的调用最多运行至燃料预算耗尽。
- 吞吐定位使用独立进程采样和对照试验，保留原负载、耐久和账务口径。逐档提高并发，记录吞吐平台、错误、尾延迟和最高稳定档。

预扣通过有序的 `FOR KEY SHARE` 检查钱包和供应商租约。关闭租约在枚举未决预扣前取得 `FOR UPDATE`，等待先前取得共享锁的预扣提交，后来的预扣则在锁定后重新检查 ACTIVE。结算仍以 `FOR NO KEY UPDATE` 串行扣减同一租约的余额，与预扣的锁兼容。租约续期和结算只延长到期时间，分摊只能消耗已有批次。WAL、记账事务、Outbox 顺序和终结帧的提交约束沿用现行协议。 [PostgreSQL 17 行锁兼容性](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)
