## 2. 最小权威持久化（拟新增，不分配迁移版本）

在 b.1 独占的 `2026111204` 接纳后由唯一 schema owner 串行追加；本文不改它或 baseline，也不复用它的管理员身份。以下四表属于内部工作负载身份，不构建通用 IAM。

1. `internal_service_instances`：PK `(service,instance_id)`；service 枚举 gateway/core-api/core-worker；instance_id 限 ASCII `[A-Za-z0-9_-]{1,100}`；`enabled boolean`、`authorization_revision numeric(38,0)>0`、`security_revoked_at timestamptz NULL`、`security_reason` 固定枚举或 NULL、created_at。仅部署 provision/revoke 窄动作可写；服务对应操作 allowlist 放代码且逐端点检查，不允许客户端注册 service 或选择权限。enabled=false 是停止新操作，security_revoked_at 是来源可信性事故，不能混用。
2. `internal_service_certificates`：PK `certificate_sha256`（对实际叶证书 DER 取小写 SHA-256，不用显示字符串）；FK `(service,instance_id)`；`uri_san`及`subject_altname_exact` 精确预配置值、`not_before/not_after`、`retired_at NULL`、`security_revoked_at NULL`、`authorization_revision>0`。一张叶证书只能映射一个 service/instance；允许同 instance 多张轮换证书。索引 `(service,instance_id,certificate_sha256)`。证书先由受信部署目录 provision，challenge 端点绝不自助登记身份；首版直接复用已证实的`getPeerCertificate().subjectaltname`入口，与可信provision记录的完整`subject_altname_exact`字符串逐字相等；不是contains/前缀匹配，也不自行编写ASN.1解析器。provision对实际证书原件校验预期URI SAN与DNS名称并捕获完整字符串，客户端不能提供它；允许Core server DNS SAN与service URI SAN共存时必须预登记完整匹配值。CA信任、完整SAN匹配与精确pin/身份映射同时校验，未登记的额外SAN拒绝。
3. `internal_startup_registrations`：PK `challenge_id uuid`，UNIQUE `(service,instance_id,registration_id uuid)`；FK certificate_sha256；`audience`、`public_key_spki bytea`、`public_key_sha256`、`boot_nonce bytea(32约束)`、`server_nonce bytea(32约束)`、`registration_digest`、`challenge_expires_at`、`created_at`；state=PENDING/REGISTERED/EXPIRED；`session_id NULL UNIQUE`（到 sessions 的 FK）、`receipt NULL`（严格安全 JSON，仅公开 IDs/key digest/期限）；REGISTERED 要求 session_id/receipt 同时非空。索引 `(state,challenge_expires_at,challenge_id)` 清理待注册数据。无私钥或 bearer session token。失败密码证明不写成功 receipt，也不消费 challenge。
4. `internal_startup_sessions`：PK `session_id uuid`；UNIQUE `incarnation_id uuid`；UNIQUE `public_key_sha256`（全局永久已使用 startup key 身份）；UNIQUE `(service,instance_id,boot_nonce)`；FK `(service,instance_id)`、certificate_sha256；canonical Ed25519 `public_key_spki`、`registered_at/expires_at`、`disabled_at NULL`、`security_revoked_at NULL`、`authorization_revision>0`。对 immutable 身份列禁止 UPDATE；只有停用/安全撤销/revision 可受控更新。索引 `(service,instance_id,expires_at,session_id)`；不加“一 instance 仅一个 active”约束。普通过期是时钟谓词，不靠 worker 把 state 改 EXPIRED 才生效。

registration 的 session FK 可后加，sessions 不回引 registrations，以避免循环插入；挑战行和新 session 在一个事务共同提交。public key digest 由解析后重新导出的 DER SPKI 生成，数据库的 length/hash 一致性也校验。生产 wire 只收 canonical unpadded base64url DER，不接受 PEM；输入限 128 decoded bytes、实际 Ed25519 canonical SPKI 为 44 bytes，算法必须 Ed25519，重新导出字节必须完全等于输入。即使未来接收 PEM，也只能先解析成同 DER 身份，不能产生第二个 key。

会话和已消费 registration 的公开回执／key 摘要保留为不可复用 tombstone；有 permit、command 或 evidence 引用的公钥/证书公开材料不得删除。过期 PENDING 可清 nonce/数据后保留有限 tombstone/idempotency digest，保留期不能早于部署定义的注册恢复窗口；REGISTERED key/boot 唯一记录不因清理失效。初版可不清已消费公开行，先交付正确性，T14 测量增长并设置运维清理策略。

除显式标记NULL外上述字段均NOT NULL；`security_revoked_at`一经设置不清除，恢复用新证书/session，instance级安全撤销需重新provision新instance，历史事故不因重新enabled消失。

现有表的必要引用增量：commands 增 nullable `owner_session_id` FK，并按下段命令分支强制；permits 增 `owner_session_id` FK、捕获 `owner_key_sha256`、service/instance/incarnation 与 certificate_sha256。捕获 canonical SPKI 可通过不可变 session FK 长期保留，不重复明文私钥。已接纳 evidence receipt/RAW 行引用 producer_session_id、key digest、signature、签名版本、payload digest 和验证处置，不另建一套费用或 usage 表。历史无 Core permit 的 LEGACY 行不猜填可信启动身份。

命令 owner 分支合同（接点 A）：保持唯一键 `(kind,caller_identity,command_id)`、既有 caller_incarnation 与 safe receipt 语义不变，不给 owner_session_id 全局 NOT NULL。服务端维护互斥命令类别：新 workload 执行集合 E 必须有 owner_session_id FK，且同事务核对 session.service/instance/incarnation、已验证 caller 与 permit owner；catalog 集合 C 的 actor 来自 b.1 已验证 bootstrap/operator/platform 身份，owner_session_id 允许 NULL，request/attempt FK 按该 catalog 合同为 NULL，不要求或伪造 Gateway session。C 的实际 kind/actor 字段以 b.1 接纳实物逐项固定，本轮不猜值、不修改其平台身份；无法匹配已接纳类别即拒绝。历史 LEGACY 命令可保持 NULL，只读恢复原 receipt，不补造 startup owner、不升级成 E；新执行路径不能以 LEGACY 绕过 E 的 FK。迁移 owner 在 b.1 接纳后以实际 kind 列表形成等价 CHECK/受控入口验证，禁止 NULL 自动判定为 catalog。permit 的新 workload owner_session_id 非空，历史无 Core permit 不补写虚假 FK。

权限：Gateway/guest 没有 PG 角色。Core API 只 EXECUTE 身份 challenge/register/current-session 与资金入口窄函数；Core worker 只读历史公开身份/执行证据入口，不得 provision、换 key 或 mint session；受限内部 verifier 可读必要公开目录，不能读 channels.secret。部署 provision/revoke 单独受限管理动作，不接项目 Key/ADMIN_KEY；使用既有技术管理授权入口时仅共享其 actor 验证，不修改 b.1 的管理员语义。所有新表先 REVOKE FROM PUBLIC/旧 gateway_runtime/gateway_worker；核心函数 owner 用 NOLOGIN 权限所有者、固定 search_path、schema qualified 引用，禁止任意 SQL 或通用注册 service 接口。

## 3. challenge、注册与并发恢复

拟新增 mTLS-only 端点：`POST /_internal/core/v1/identity/challenges` 输入 `{registration_id,public_key_spki,boot_nonce,contract_version:1}`；service/instance/cert 来自真实 stream peer。返回 challenge_id、audience、可信身份、cert SHA256、key SHA256、两个 nonce、expires_at。`POST /_internal/core/v1/identity/registrations` 输入 `{challenge_id,registration_id,signature,contract_version:1}`；从 PG 取完整 challenge 重新构造签名输入。成功 201（首次）或 200（同回执恢复），返回 session/incarnation/service/instance/key digest/expires_at，均不是 bearer token。未知字段拒绝。

挑战创建：先非锁定预读身份，再按顺序取下面的锁，重读当前 enabled/cert validity/非安全撤销；同 registration_id 同 digest 返回原 pending challenge，固定 nonce 和到期时间，不刷新 TTL；同 id 不同 key/nonce/cert 返回409 `registration_conflict`。挑战 TTL 建议30s、startup session TTL建议24h，均为新可配置有限默认而非已测 SLA；session 不滚动延长，长期服务到期 drain 后生成新 key/session，旧已grant链仍可收证。新 session 到期不能长于所绑证书 not_after。

统一新增身份锁放在金融设计第0级 advisory 后、第1级 organizations 前：`internal_service_instances → internal_service_certificates → internal_startup_sessions`，每类复合键排序。准入/next/begin对三者FOR SHARE NOWAIT，在同一资金事务用PG clock_timestamp重核当前有效性/revision；第8节历史收证按同序同锁，仅重核历史绑定与安全撤销，不套新admission的有效性谓词。两者均不用缓存结论。注册只需 instance/cert SHARE，再对 registration 行 FOR UPDATE；最后 INSERT 新 session 和 UPDATE challenge=REGISTERED/receipt。锁顺序没有 session→registration 的反向 writer。advisory namespace 同时包括 reg ID、规范key digest、instance+boot nonce，键先排序 try-lock，争用返回503 `identity_busy`、不造业务拒绝；唯一约束最终兜底，禁止无界 ON CONFLICT 等待。资金第0级需要的 command/intent 及所有身份 advisory 应先统一排序取得，不能进入身份锁后再回拿第0级。

并发/丢包逐步结果（设计推演，未跑 PG）：

- 两 Core 收同注册：A获 advisory，B得 BUSY；A验证当前mTLS指纹与challenge相等、challenge未消费且未过期、签名正确，INSERT session+回执+消费 challenge 同提交；B重试读已成功行，验证原签名和绑定，返回同 session。只创建一个 incarnation。
- 成功响应丢失：客户端保持原 key/boot/registration/challenge，换 Core 重发原注册证明。REGISTERED exact-match 分支不重新要求 challenge“尚未消费/尚未过期”，只返回原安全 receipt 和当前状态；否则正常丢包会无法恢复。同一次 consumed challenge 不可能再 INSERT session。session 已过期/停用时仍可返回原公开 receipt 标明不可新执行；不重签续期。当前 mTLS 无效时不能走恢复，走轮换/新启动，不冒用旧 owner。
- 未提交前崩溃：challenge仍PENDING，重试可消费；commit未知先查同注册 ID，不生成另一个 key/id 来碰运气。旧 key已丢失的重启只能新注册，旧 attempt 不移交。
- 同 key 不同 PEM/DER文本：规范DER产生同全局key唯一值；同注册返回原回执，不同注册409 `startup_key_reused`；旧session已过期/安全撤销也不允许复用该key。
- 同 instance+boot nonce 不同key：其中一个可提交，另一409 `startup_boot_conflict`，绝不更新赢家。不同instance偷用公开材料但没有原私钥不能完成证明；即便自己有新key，实际mTLS只会映射到自己instance。
- 不同 registration_id 同key同时：advisory/UNIQUE只许一 session；失败者不消费为REGISTERED，返回冲突。待注册challenge以后过期，不做隐式owner复用。
- challenge错audience/错cert/改nonce/过期/签名错：401/403或409有界失败，无session、permit、资金或消费副作用。客户端提交可公开获得的证书文本不构成 mTLS 持有证明；先有真实 TLS CertificateVerify/Finished，再证明 startup 私钥，两步不能互相替代。
- provision disable/revoke 与注册/begin：管理员只按 instance→cert→session 顺序 UPDATE 与审计，commit后答复；不持身份锁扫描钱包/permit。先获 SHARE 的注册/begin在线性化点先提交，管理员等待；管理员先提交则后续在锁内读新值拒绝。RESERVED清理由独立全序事务完成；已grant按UNKNOWN规则保留。

## 4. 编码、两种 digest 与 HTTP 合同

签名统一 `node:crypto.sign(null, utf8(JSON.stringify(stringArray)), startupPrivateKey)` / `verify(null,...)`，Ed25519原始64-byte签名用canonical unpadded base64url（86字符）传递。所有数组元素都是已验证字符串，不做 Unicode normalize、不隐式 trim；service/instance/枚举为ASCII，UUID小写规范形式，hash小写64 hex；时间严格 `YYYY-MM-DDTHH:mm:ss.sssZ`、毫秒整数可表示且无闰秒。version数组项为字符串 `"1"`；body contract_version仍现有数字1，adapter负责唯一转换。引用 [Node crypto 导入/签名接口](https://nodejs.org/api/crypto.html#cryptosignalgorithm-data-key-callback) 与 [RFC4648 base64url](https://www.rfc-editor.org/rfc/rfc4648.html#section-5)；Bun兼容性由本次小探针核实，不从Node版本推断全API兼容。

注册数组精确定义为：`["stg.internal.startup-registration","1",audience,service,instance_id,certificate_sha256,registration_id,challenge_id,public_key_sha256,boot_nonce_base64url,server_nonce_base64url,challenge_expires_at]`。其registration_digest是这个数组除server生成challenge_id/server_nonce/expires_at外的版本化申请语义摘要；不要把随机challenge重生成视作同申请。

每命令证明数组：`["stg.internal.command","1",audience,service,instance_id,session_id,incarnation_id,command_type,command_id,method,normalized_path,raw_body_sha256,deadline_at,trace_id]`。audience为部署固定cluster标识+目标服务（如cluster/core-api或cluster/gateway），不接受请求自选；跨Core副本同audience，Gateway目标也必须在业务permit指定实例中。原可信 service/instance 来自会话且和实际peer相等，不采纳header字段。

POST wire body建议统一 `{envelope:CommandEnvelope,data:EndpointDTO}`。证明放唯一 `x-stg-proof` header，其内容是有界base64url strict JSON，只有 session_id、incarnation_id、command_type、command_id、deadline_at、trace_id、contract_version、raw_body_sha256、signature；其余值由handler派生，不让header覆盖path/peer/audience。拒绝重复header/数组值/非法UTF8/超预算。证明自身不放body，避免digest自引用。解析body后要求重复字段逐项相同。

- `raw_body_sha256` 是实际接收全部DATA字节的SHA256，计算完成前不JSON解析、不mint信任上下文。Content-Encoding仅identity、Content-Type仅application/json（可约定UTF8参数唯一形式），请求声明content-length时必须精确匹配；禁止自动解压造成另一份摘要。
- 现有 `envelope.body_digest` 保持金融设计的semantic digest：strict schema通过后构造版本化对象 `{kind,contract_version,owner:{service,instance_id,session_id,incarnation_id},deadline_at,data:normalizedBusinessDTO}`，用既有canonical后SHA256。金额/数量字符串、币种、集合去重排序、所有影响执行的版本/IDs/digest/manifest都由端点schema规定；不含trace、signature或网络信息。raw字节换空白可改变raw digest但不改变语义回执；owner/期限或任一业务字段变化则同命令冲突。禁止用客户端body_digest替代重算。
- 上游 `dispatched_digest` 是第三个业务摘要，独立于前两者：它对第7节 strict `DispatchProjectionV1` 的外层技术投影求摘要，只覆盖 host 计算的实际 request-target/header/body 摘要、Core 已知且核对的可信 origin、有限 method/operation、不可变版本引用、完整 SDK auth 描述及凭证密文版本摘要等精确字段。实际 serialized path/query、非认证 header 名值与最终 body 字节只在 Gateway 私有内存，绝不随该投影传 Core。Core 只能从收到的严格投影重算外层 dispatch 摘要；原始网络材料的三个摘要由可信 host 计算与最终消费前复核，Core 不声称能从摘要反算或独立核验原文。

内部path采用拒绝歧义：只接受路由表生成的固定ASCII段和小写UUID/hash；禁 `%`、`//`、`.`/`..`段、反斜线、尾斜杠、fragment、absolute-form和不匹配`:authority`。method精确uppercase路由值；POST路径不带query。现有 `GET commands/{uuid}?kind=<allowlisted-kind>` 只收这一固定顺序唯一query，不收重复/额外字段，normalized_path包括整个该query；其他GET路由另有明确模板，不对任意URL“规范化后放行”。GET空bodyhash是SHA256空字节，proof command_id为本次查询关联UUID，目标ID在path；不把查询写入业务command表。内部规则不改变SDK上游相对path合同。

响应通过已验证Core mTLS连接、对应h2 stream和strict响应schema验证；核对command_id/kind、原owner、request/attempt、digest/deadline。安全receipt与瞬态grant是两个不同schema，未知字段失败；transport结束无HTTP status、截断JSON、GOAWAY/RST或超预算均为结果未知，不推断未提交、不自动重发物理发送。客户端显式同command恢复安全receipt，begin任何重试都不能得到第二份grant。

## 5. 可信上下文与有界执行

### 5.1 完整可调用信任路径与依赖（ID-R1）

WeakMap防误接线，不防同进程恶意代码；Core role/应用代码是明确受信边界，storage不是对任意调用者的h2认证oracle。测试替身只在公共 tests/support，经测试装配使用，不进入生产exports；不能通过导出生产 authenticate/mint 加 resolver 来方便测试。身份检查不替代业务schema/project/key授权，也不替代同事务撤销屏障。后续架构验收静态扫描所有新增模块和依赖循环，并以真实listener验证伪造context拒绝；本轮只有静态图与有限模型，不宣称已运行该产品验收。

建议首版有限默认（新增配置对象，由服务装配校验，名称不是现有env；容量由T14/T17验证）：identity request/response各8KiB；普通数字命令及receipt各256KiB；context含短期token最多32KiB；队列单签名事实64KiB、组最多128项/1MiB。插件包分发走既有包独立上限/独立pool，不套256KiB JSON。header解码后最多16KiB/32项；每session最多32并行stream、peer最多4连接、全进程最多128连接/256在途JSON命令且预留总16MiB接收缓冲，剩余请求立即429，不建无限队列。identity并发16、结算/租约独立限额及PG池，避免刷新挤占资金。

TLS连接/握手3s，首个HEADERS等待1s，body读取2s、连续无进展1s，普通RPC单次处理≤10s、identity≤5s、服务端idle连接30s、单连接最大生存5min后GOAWAY排空。`deadline_at`保持已接纳命令/执行的原始期限，不把单次RPC的10s处理预算误作整个推理执行期限；当前`apps/gateway/src/config.ts:71`的TOTAL_TIMEOUT_MS默认180000、合法上限3600000，Core部署使用同一受控总期限上限，接受时须`now<deadline`且不超过其上限。有效期内重放由权威命令仲裁拦截；业务原始deadline不得更改，命令过期只允许另签短期只读status请求，不延长旧命令。接收时和事务发grant前再检查PG当前时间；锁用try/NOWAIT，PG statement budget不长于剩余deadline（现有8s默认上界），事务取消后仍查询原命令处理commit未知。不得用客户端时间决定过期，不把时钟容差延长发送期限；T14测时钟漂移告警/拒绝。deadline后begin即使数据库已有成功也仅返回安全状态，不重发grant。

HTTP2 `requestCert/rejectUnauthorized/allowHTTP1:false/ALPN h2`；客户端CA+hostname校验，拒绝h2c、HTTP1、TLS early data新命令，不启用TLS session复用绕开peer身份（首版禁ticket复用或证明每次可取真实证书再开启）。已有socket每stream重查目录状态。取消只关闭该stream并清timer/buffer/listener；GOAWAY后不在旧session开新stream，关闭时drain有限时、destroy/reap自有资源；不会把单stream失败毁掉别人的有界正常stream。透明HTTP库重试必须关闭，只有显式同command恢复。

实现预算校准（2026-11-12）：Bun 1.4.4 的公开 node:http2 stream 事件在完整 HEADERS 解码后才交给应用，不承诺同一连接后续每个未完成 HEADERS/CONTINUATION 有独立1s起点。首个 HEADERS watchdog 单独限时；后续未结束块由连接 idle30s、最大存活5min及有限drain清理共同收口，并保留 decoded header16KiB/32项、peer/global连接/stream和应用全局接收预算。native maxSessionMemory=4 的单位是 MiB admission credit：内存占用超阈值时拒绝新流，不是已有流或整个进程RSS硬上限，不能代替应用生产response/body上限。精确默认关闭组合以产品配置和有限raw TLS/h2测试记录为准，不用类型声明声称能力。作者实测首header300ms配置约306.9ms关闭；合法首流后未结束新HEADERS的静默/25ms CONTINUATION在idle400ms/life1200ms配置约802/804ms关闭；8MiB声明HPACK值未END_HEADERS即native GOAWAY code9/2拒绝；5MiB排队输出后4MiB credit拒绝第二流，分别证明各自行为，不相互替代。T14/T17仍测整体RSS/压力和默认部署配置，不把局部证据当HA/容量结论。此校准只修工程预算边界，R1/R2/R3、私有上下文/撤销/正文投影/资金合同不变。

新错误合同：401 `internal_proof_invalid`/`internal_session_invalid`；403 `internal_peer_forbidden`/`internal_owner_mismatch`/`internal_identity_revoked`；400 `internal_request_invalid`；409 `registration_conflict`/`startup_key_reused`/`startup_boot_conflict`/既有拟定`command_conflict`；408 `internal_deadline`；413 `internal_body_too_large`；429 `internal_capacity`；503 `identity_busy`/`identity_store_unavailable`。形状沿规格`{code,category,retryability,command_state,request_id?,attempt_id?,message}`，认证/解析失败command_state=NOT_ATTEMPTED；BUSY/断连=UNKNOWN，稳定业务REJECTED仅在已有command仲裁后使用。retryability枚举NONE/SAME_COMMAND/STATUS_ONLY；服务端dependency错误最多SAME_COMMAND，begin传输未知固定STATUS_ONLY。认证错不写命令表，不回显证书、签名、token、SQLSTATE或解析正文；HTTP status在TLS未握手成功时不存在，客户端仍处理transport failure。

## 6. Core→Gateway 反向身份，不给Gateway数据库

所有三种service使用相同startup注册（不是只有Gateway）。Core API先启动仅提供identity端点的内部listener，以自己实际client证书通过loopback h2握手注册；Core worker同样向Core注册，然后业务ready。不能用“加载一份可公开证书”直接自mint session。部署证书EKU须支持其实际client/server角色，server hostname与URI service身份分别校验。

Gateway已有自己的mTLS和startup session后，反向收到Core API/worker请求，先验证真实peer和Ed25519proof。由于Gateway无PG，新增 `POST /_internal/core/v1/identity/authorize-reverse-command`：Gateway以自己的正常命令proof转交原caller session/instance/certSHA/签名数组/签名及raw body摘要和最小task/permit IDs（不转正文）。Core在共享PG按身份全序复核原caller当前状态、签名、service-operation allowlist及原资源action/task/目标Gateway owner/期限，返回此精确proof digest的有界授权判断。Gateway核对在线判断及原实际peer相同再进入本地registry。Core响应丢失只重试该只读授权判断，不能重派resource action。它是窄反向验证端口，不是任意证书验签oracle/任意role授予。

该授权判断的PG事务是撤销竞争的线性化点：revoke先提交则拒绝；授权判断先提交则动作已在撤销前受理，只能消费其已有permit且受原deadline约束，与begin语义一致。不能承诺revoke返回后抹掉此前已经授权/已发送动作。Gateway不缓存“session有效”用于新命令，不离线接受Core自签任意session。reverse authorize必须用服务端task/action状态，不据body把只读变成变更；当前first-chain未用的resource action只定义接点，T11按同合同实现，不在identity unit预建资源框架。

允许操作表：gateway→Core仅context/admission/next/begin/abort/lease/status/resource commit及包读取等已授权能力；core-worker→Gateway仅已有task/resource permit指定的内部资源执行；core-api→Gateway仅明确运维drain或已有permit对应动作，没定义的端点一律拒绝。角色不同不能用相同证书字符串假冒。gateway→Gateway、worker→Core admission均拒绝。

## 7. 受permit约束的host-only执行凭证

采用规格已有“句柄”分支，不引入HPKE/RSA或额外加密key；Ed25519只签名。TLS的认证加密保护RPC，公开key只用于身份/历史证据；[RFC8446](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3)说明CertificateVerify证明对应私钥持有，本身不让公开证书成为认证token。若未来要使中间存储可保存sealed capsule，再单独采用经过审核成熟HPKE实现及独立加密key并把key绑定注册签名；本次没有这一存储需求，也没有实施该协议。

1. 接点 C 选定 **Core context 提前给非秘密版本摘要**。context候选在一次权威目录读取中捕获channel/binding/config/package/cost IDs/revisions及 `credential_ciphertext_sha256=SHA256(UTF8(channels.secret))`，只将该64hex摘要与候选版本返回Gateway，不传ciphertext、secret、Core主密钥/pepper/DB URL。它是完整现有AES-GCM密文（含随机IV/tag）的版本指纹，不是裸secret hash或授权。当前 `channels.secret` 可变且无credential revision列，此合同不假定已有字段、不建新凭证库。Gateway在prepare前即拿到摘要；context候选不是资金许可。Core admission在持channel SHARE锁后重算摘要/版本与候选全等才可RESERVED；begin同锁再比permit snapshot。轮换/重加密导致旧摘要失配：admission不创建资金/permit，重取context再prepare；已RESERVED则原abort-before-send收敛后再走新attempt/命令，不能先fund再reprepare原许可。已grant责任/历史证据不因此失效。
2. 接点 B/C 与 ID-R3 使用两阶段 `HostAuthorizationPlan`，明确分开两份数据。prepare 前 host 已生成 proposed_request_id/proposed_attempt_id 及私有 registry；guest prepare 后先 materialize 最终 body、校验目标 origin/path/method/header/manifest，再完成一次最终 transport 序列化。`HostPrivateDispatchMaterialV1` 只存在 Gateway host 的有界私有内存，包含实际 serialized request-target（完整 path/query）、全部非认证网络 header 名值字节、最终 body 字节，以及核验所需 origin/method/auth 与原 prep 绑定。guest 只能给计划，不能读取 registry 或认证材料；该私有材料不导出给 core-client、Core、PG、Redis、日志或 safe receipt。合法 header/query 可能包含正文，不能因叫“技术字段”而出界。

   拟新增 Core wire `DispatchProjectionV1` 的字段集合精确如下；`CandidateRefV1` 逐字段沿已接纳金融设计 §3.2，不是任意 metadata：

   ```ts
     final_body_sha256: string;
     candidate_ref: CandidateRefV1;
     auth:
       { type: "none" } | { type: "bearer" } | { type: "api-key"; header: "api-key" | "x-api-key" };
     credential_ciphertext_sha256: string;
     billable_manifest_sha256: string;
     deadline_at: string;
   };
   ```

   UUID/deadline 沿第4节规范；所有 sha256/digest 字段仅接受小写64hex。origin 只能等于 Core 从当前可信候选取得并重新核对的唯一规范 origin（scheme/host/显式非默认端口，无 userinfo/path/query/fragment），不是 guest 提供的 raw URL；operation 为 kernel 公共有限枚举且与已授权请求/数字 manifest 一致。candidate_ref 只含 `route_id,channel_id,binding_id,plugin_version_id,package_digest,config_revision,config_digest,cost_version_id,customer_price_id,candidate_digest`，其 ID/revision/digest 必须逐项等于 Core 已知候选并由 admission 持锁重核；不接受新自由文本。auth 必须是 SDK 的完整 strict 联合，api-key.header 不能丢。数字 manifest 使用金融设计的 strict BillableManifestV1，Core 从 admission 的同一份 normalized manifest 重算 billable_manifest_sha256，不能由 guest 指定未核对的摘要。

   wire/admission、permit snapshot、返回的安全授权 snapshot 均只接受上述 strict 投影及本节明确的绑定字段。每层（含 candidate_ref/auth）未知键一律拒绝，不是静默 strip：`headers`、header 名值列表、`path`、`query`、request-target 原文、raw/full URL、body 字节、任意 metadata/扩展对象均无字段。origin 是上述受信相等值的唯一例外，不是任意 URL 容器；api-key.header 是有限认证输出名的唯一 header 文本。safe receipt/日志只由已验证投影与安全绑定构造，不能保存原 admission/prepare 对象或将解析失败内容放进错误。合法 guest prepare 经过可信 host 后，Core 的实际请求体就只有投影；strict 拒绝非法额外字段不被描述成“原文从未到达 Core”的证明。

5. 6. 认证注入发生在guest之外的最终transport；插件只给none/bearer/api-key描述，不能选择任意header读secret。禁止跨originredirect携带认证，网络重试及自动redirect必须受既有transport规则控制；签名/token不作为response计划输入。try/finally在成功、拒绝、超时、取消、trap、断连、drain中删除registry、释放buffer/timer/listener；可变Buffer.fill(0)，及时丢字符串引用，但不虚称JS GC能保证物理内存零残留。日志不序列化错误request/response对象，崩溃dump按部署禁敏感dump处理。

此方案约束可信host的使用，无法使上游原生bearer/API key在被攻陷host中成为上游服务器原生单次凭证；这是当前宿主信任边界，不承诺不存在的密码学隔离。guest隔离、宿主没有Core主密钥、原许可绑定和一次消费为本任务验收。

### 8.1 历史producer安全撤销屏障（ID-R2）

1. 可在事务外做strict schema、canonical/signature纯计算和不可变permit/task绑定预读；这不授予VERIFIED。同一group所有事实共同核验；producer key/session/cert必须由原permit或其独立resource/task授权派生并与wire核对，不以wire任意ID决定可信来源。
2. 进入已有evidence microbatch外层PG事务/每group子事务。第0级先取得全部command/intent/event及必要身份advisory try-lock，不能后补低级锁。整group均为精确已提交receipt时，必须逐条匹配原event/claim、完整semantic/signature payload digest、producer绑定及原disposition，才能只读返回原安全receipt；不同digest走既有冲突，不因event同名绕过验签/绑定。安全重放不生成新canonical/费用/释放，也不升级QUARANTINED。commit未知查询不成为prior anchor。
3. group含任一未锚事实时，对该group**全部producer**汇总去重instance、certificate、startup session（包含安全状态依赖的父instance及所绑cert；多个owner共同取全集）。按全局身份序先全部 `internal_service_instances(service,instance_id)`，再全部 `internal_service_certificates(certificate_sha256)`，最后全部 `internal_startup_sessions(session_id)`；每类按ASCII/规范UUID字节序排序。对每行执行 `FOR SHARE NOWAIT` 并在取得锁的权威行上重读immutable绑定及三层security_revoked_at；此身份级位于金融第0级后、第1级及任何wallet/account/request资金锁之前。出现任一NOWAIT冲突/绑定变化/缺行则整group回滚为BUSY/有类型故障，不按旧值VERIFIED、不拆组先扣一部分、不先锁钱后回锁身份。当前delivery worker自己的新操作授权检查与历史producer安全谓词分开；若其身份同属集合先去重统一取锁。
4. 有任一producer的instance/cert/session SECURITY_REVOKED，该事实即使验签正确且自报旧时间，未锚时仍为QUARANTINED/SECURITY_REVOKED。该group原子写相应RAW与安全receipt；隔离事实不得入canonical、费用、成功终态或释放UNKNOWN敞口。group若含混合处置须在任何费用前共同判决并按已接纳原子组规则写入，不能把被隔离数量合并进已验证事实；有效事实的既有仲裁不借隔离事实释放责任。自然expires_at、正常disabled/drain、证书自然expiry/retired_at不属于历史安全否决谓词，不套admission“当前有效”检查；不可变permit的曾grant/owner/key/epoch/dispatch仍必须全符。
5. 全部身份SHARE锁持至**外层commit或rollback**，包括group成功后的外层batch提交，不在验签后释放；receipt/RAW/canonical/cost head/两侧journal/审计随该外层事务原子提交。撤销动作按同一多对象身份全序 UPDATE对应security_revoked_at/revision并审计、commit后才答复；instance/cert/session任一层的普通非键UPDATE都必须与该SHARE竞争，不用KEY SHARE，不用事务尾普通SELECT冒充屏障。revoker不持身份锁去扫描钱包/permit；后续资金清理由独立全序事务做。

线性化两顺序：revoker先commit → ingester获SHARE重读见撤销 → 未锚事实仅QUARANTINED，无canonical/扣款/释放；ingester先获SHARE → revoker UPDATE等待 → ingester VERIFIED可信锚与钱先commit → revoker之后commit，同精确receipt可安全幂等。若revoker已持写锁未commit，ingester NOWAIT回BUSY回滚，重试后仍按权威状态处置。签名预验开始时间和网络应答到达次序不决定这条边界。

LEGACY无session：历史无Core permit/无startup身份的既存行只读保留原legacy来源/receipt；不补造producer session、不标新的VERIFIED、不继承任何workload grant。精确legacy既有receipt可按原合同只读返回；新签名入口要求Core permit/session却缺失时拒绝且不抢占event/claim，需既有legacy过渡writer的历史处理仍受已接纳金融迁移边界约束，不因此新增自动信任入口。单独安全事件/人工对账沿原resolution流程，不由NULL推断“未撤销”。

拟在已有计划的`core_evidence_receipts`追加`authentication_disposition`（VERIFIED/QUARANTINED，新Core记录NOT NULL、LEGACY可NULL）、`authentication_reason`（NORMAL/SECURITY_REVOKED/UNGRANTED）、producer_session_id FK、producer_key_sha256、signature_version=1、signature bytea长度64、signature_payload_digest；所有字段immutable。RAW和receipt保留重建签名字节所需的白名单字段，其他绑定从不可变permit派生。QUARANTINED记录不得指accepted canonical/cost head，重复返回原隔离receipt，后续人工裁决以已有resolution机制追加，不能UPDATE成已验事实。签名无效/subject不符不创建会计RAW/receipt或认领event/revision（避免攻击者抢占合法事件），只记有界技术安全审计。安全撤销不销毁历史公钥或数字事实。安全事件若影响已有canonical事实，交现有冻结/争议流程单独审计处置，不由identity silently重写账。只读补证普通停用/余额0仍可按原绑定做；security quarantine按安全隔离拒绝新网络执行，不能借“补证”获得新的任意send。异步外部事实来源若由新resource只读task得到，需其自己的有效task/permit签名与原resource绑定，不能把旧attempt grant转给新owner。

必须的独立验收向量：

- 合成可信CA下A/B实例，真实持有A证书者不能header伪装B；只提交公开证书无私钥无法握手；错CA/hostname/SAN/pin/过期/revoked拒绝。拿自己mTLS+别人的session无startup key不能签；签名可用但mTLS实例不符仍拒绝。
- 两Core同时同registration、相同key不同PEM、同boot不同key、commit前kill/commit后丢响应，各只得到0或1个session且无回执换owner；新session注册不撤销合法旧session、不更新旧attempt。
- 每个签名字段单独改动都拒绝；相同semantic JSON换空白需新raw签名但回执同一；deadline或owner变化同命令冲突。路径百分号/重复query/headers/Unicode异常/oversized/慢body/GOAWAY无status全部失败且无泄漏任务。
- 原session自然到期→证书轮换→Core重启→旧Gateway死亡后，队列原签名事实仍只入账一次；新owner只能转交，不能begin/NOT_EXECUTED旧链。安全撤销后未锚事实仅隔离，原UNKNOWN和资金责任保留；签名自报旧时间不能解冻。
- 注入bearer金丝雀只在Core解密与Gateway transport内存可见；guest inspect/config/state/IPC、command安全查询、PG新增表、Redis队列/WAITAOF payload、日志、错误、response plan及用户输出均不可见。改目标/method/query/body/header/config/deadline或重复consume无物理send；外层PGcommit未知时无material返回。finally的registry/buffer/timer/listener/awaited task全部归零。
- R3 正文金丝雀分别经合法 x-* header 值、合法相对 path/query（例如 `/v1/chat/completions?x=...`）由 guest prepare 输出。identity 前置 unit 以 strict DTO 拒绝 headers/path/query/raw URL/metadata 等未知字段并确认安全错误不回显，b.2 核 permit/安全 receipt 只从 strict 投影持久化；c 用真实 Gateway→Core request、PG snapshot/receipt/日志证明两种原文均不可见，并分别独立改变本地实际 target/header/body 验证绑定失配与 0 send。纯序列化模型不能代替这些产品验收，不扩远端 ID 或其他隐蔽通道。
- 反向worker错角色/错session/错Gateway owner/过期task/改action/重放变更许可拒绝；Core A注册、Core B在线判断在撤销后拒绝已有TLS连接上的新动作。判断先提交与撤销先提交均断言各自线性化结果，不能用网络到达顺序凑结论。
