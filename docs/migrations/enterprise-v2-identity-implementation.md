# T04.b.identity implementation record

Accepted design: enterprise-v2-internal-identity.md §§2–7/9. The accepted migration versions through 2026111204 remain immutable. This unit appends 2026111205, implements registration and signed current-session status, and rejects every unsupported business operation. Financial admission, execution, historical evidence disposition and reverse resource authorization remain downstream work.

The deployment directory is provisioned through a separate database deployment role, never through ADMIN_KEY or workload RPC. Four identity tables contain only public certificates, keys, nonces, revisions and safe registration receipts. Core API uses only bounded SECURITY DEFINER functions, owned by a NOLOGIN role, with a fixed search path. Registration checks instance/certificate state under SHARE NOWAIT, obtains sorted transaction advisory locks before row locks, and commits session plus receipt together. Current-session status takes instance/certificate/session SHARE NOWAIT and rechecks every observed binding/revision inside the same transaction. Historical public material remains readable after natural expiry, retirement or security revocation; no historical financial writer is delivered by this unit.

Internal endpoints are POST /_internal/core/v1/identity/challenges, /registrations and /current-session. All use real h2-only mutually authenticated TLS. The first two require exact provisioned peer DER/SAN and public proof of startup key possession; current-session additionally requires a strict signed command and an application-private WeakMap context. Core API startup registers its own fresh in-memory key using its own real loopback TLS client connection; gateway/core-worker use the same core-client startup contract. This unit does not assemble their business applications.

The signed current-session command kind is identity_current_v1. Its data is exactly an empty strict object; its semantic digest covers kind, contract_version, verified owner, original deadline and data. It is read-only and creates no execution command. Unsupported routes cannot acquire business permission. Command category C is exactly the seven accepted plugin catalog kinds; only these retain nullable owner. Existing noncatalog rows are legacy read recovery and cannot be newly inserted. No workload E command is delivered until b.2 defines the actual supported kinds.

Transport has finite connection, stream, header, body, processing and drain budgets. No transparent retry or redirect exists. All errors are fixed safe strings. Strict DispatchProjectionV1 rejects every unknown field at every level, including raw headers/path/query/metadata. Full actual upstream bytes remain a Gateway host concern. Private startup keys are generated at startup and never serialized.

Verification and actual limits are recorded in the local delivery report. Default budgets do not establish capacity, high availability or future financial correctness.

`INTERNAL_IDENTITY_CONFIG_FILE` names a 0600 deployment JSON file containing `database_url`, fixed `audience` (`cluster/core-api`), bind `hostname`/`port`, TLS `servername`, server `key_file`/`cert_file`, `ca_file` and separate client `client_key_file`/`client_cert_file`. TLS certificates are provisioned before service startup. The optional bounded TTL/limits fields are validated by `identity-main.ts`; production limits may only reduce the profile. `bun run core:identity` starts this actual identity listener, not the pending financial API. `scripts/identity-provision.ts` and `scripts/identity-revoke.ts` use only `INTERNAL_IDENTITY_DEPLOY_DATABASE_URL`, with the separately granted deployment role. Their committed changes audit the actual database session actor. Neither accepts project keys or ADMIN_KEY.

The PostgreSQL pool has four connections per Core identity listener. A complete bounded body is read before reserving a connection. Reservation observes stream cancellation; every running query has a cancellation listener, and the reservation is released in finally. The final current-session function retains SHARE NOWAIT locks until its outer transaction commits. The scoped runtime role script explicitly revokes the four tables after its historical broad SELECT grant.

Observed transport boundary: a newly established h2 session has a first complete HEADERS watchdog (default 1000ms). Later incomplete HEADERS/CONTINUATION blocks are bounded by native parser/header limits plus session idle/lifetime and finite drain; the application has no public Bun hook for a separate timer starting at every partial header fragment. With test headers=300ms, idle=400ms, lifetime=1200ms and drain=100ms, the first-header timeout closed at approximately 307ms and post-success incomplete header vectors closed at approximately 802–804ms, including continuous 25ms CONTINUATION input. These measured values are examples, not exact timing promises.

`maxSessionMemory:4` is a native admission credit/new-stream rejection threshold, not total RSS or an absolute memory ceiling: a flow-controlled existing 5MiB response remains queued, while the next legal stream is refused with RST_STREAM 11 before handler entry. The production profile separately limits response/body/header bytes, streams, all TCP connections including pre-TLS sockets, peer connections and reserved receive buffers. An oversized HPACK value was rejected before END_HEADERS by the native decoder; its compression error is not attributed to the 4MiB credit threshold. Receive-budget tests record actual reserved-byte peaks, and stop waits for both native sessions and TCP sockets to close before resolving. This closes the observed early-stop bookkeeping race rather than relying on later database shutdown to let close events run.

The append preserves historical null-owner command bytes. Existing seven catalog kinds remain category C with nullable owner; unknown new command kinds are rejected. No workload E kind is invented here. New permits require a genuine session and immutable key/certificate/service/instance/incarnation binding; existing historical rows are not relabeled. A consumed registration and its receipt are immutable tombstones. Natural expiry, disable and certificate retirement preserve public material and do not set security revocation; all three security revocations are one-way.

The actual delivery does not implement admission/begin, financial evidence classification, credential handle consumption, reverse resource actions or three-application business assembly. Their endpoints remain refused and their financial/host acceptance remains pending b.2/c/T11. Cross-fault-domain HA, clock-drift policy, deployment rotation drills and capacity are outside these tests.

Core RPC requires a deployment-provisioned leaf DER SHA256 pin and complete exact SAN string in addition to CA and hostname verification. Reconnect takes an explicit trusted target containing the replacement origin/pin/SAN; it never weakens verification to a shared CA alone. The generic runtime transport retains generic optional pin configuration, while the Core contract requires it at both type and runtime boundaries.

The final PostgreSQL authority boundary validates each projection as an exact object of required, nonempty JSON strings before extracting values. Peer endpoints accept only their six common peer fields plus the matching endpoint; current-session accepts those common fields plus its ten command/session fields and no endpoint. Service, instance, lowercase UUID/digest, positive decimal revision, trace, operation, method, path and canonical millisecond UTC deadline follow the wire formats. JSON numbers do not alias revision strings. Current directory/session bindings and revisions are compared without SQL NULL equality ambiguity, under the existing SHARE NOWAIT locks through outer commit. Core still verifies actual mTLS and Ed25519 signatures and alone constructs its private verified projection; these database checks do not introduce a signature verification or context-minting API.

Challenge and registration validate every required UUID, byte length, audience, digest and bounded TTL before locks, lookup or replay. Provision validates required service/instance/hash/SAN strings and finite ordered certificate times before any insert or audit; existing certificate replays require exact public material. Change validates its required service/instance/action and any supplied hash/session selector before lookup. Legal selectors remain session with optional certificate hash for DISABLE/SECURITY_REVOKE, certificate without session for RETIRE/SECURITY_REVOKE, and instance with both selectors NULL for DISABLE/SECURITY_REVOKE. Invalid authority fails with a fixed error and no directory, registration, receipt, session or audit edits. Lookup-only NULL or unknown keys retain their absent-result behavior. This corrects the unaccepted v5 SQL and its checksum; accepted migrations through v4 remain unchanged.
