# enterprise-v2 T16 legacy 删除

本记录承接[审查记录](enterprise-v2-review.md) §4 的 legacy 残留清单，规划并记录 T16 删除 legacy 单体网关的过程。删除前逐例核对 legacy 测试承载的行为在 v2 中的去向，避免随文件删除丢失有效断言。

## 1. 当前状态（代码核对，2026-11-15）

本节为删除前状态；l4（2026-11-16）删除结果见 §6。

- 生产分流：Caddy 已把 Chat（仅 POST）、资源、账户与请求元数据路由到 v2 Gateway 与 Core 公开监听；`@legacy path /v1/* /v1beta/*` 兜底仍转发其余方法与未列出的路径（R6）。OpenAPI 双向用例显示 legacy 专有路由只剩管理面 `POST /admin/recover`。
- legacy 代码：`apps/legacy-gateway`（21 个模块、5 个单测文件 22 例）；`packages/storage` 的 `Store`（R3 后只服务 legacy 运行时）；`packages/runtime` 的 `usageChannel`；`packages/adapters/src/protocol` 中只被 legacy 调用的导出（如 `prepareOperation`、`bedrockEventStream`、`extractUsage`、`imageCount`、`encodeSSE`；v2 只使用 `parseClientJson`、`requestCharacters`、`validateRequestPolicy`、`SSEParser`、`StreamTranslator`、`copyExact`、编解码与 `stringifyExact` 等）。
- 脚本与部署：`package.json` 的 `dev`/`start`/`worker` 与 `test` 扫描范围；`scripts/build.ts`、`seed.ts`、`verify-artifact.ts`（legacy 9 项）、`bench.ts`（R5）、`verify-backup.ts` 的 `usageChannel`；`infra/legacy-gateway@.service`、`legacy-gateway-worker.service`、`runtime-role.sql`；架构与 OpenAPI 单测中的 legacy 条目。
- 测试：`routing.test.ts` 42 例与 `gateway.test.ts` 77 例经 legacy 进程内应用验证；`billing.test.ts` 58 例的准入经 `admit_gateway_batch`（v2 中为 `allocate_customer_batch_v1` 的包装），证据经 `Store.persistUsage`（legacy `persist_usage_batch` → `record_usage_evidence`）后调用 `settle_requests`。v2 证据路径为 `core_evidence_group_v1` → `core_evidence_snapshot_v1`（要求供应商 `upstream_holds`）→ `settle_requests`，legacy 证据模型没有供应商持有，因此 billing 用例不能只换入口函数，必须改走真实 Core 准入与签名证据。
- SQL：`admit_gateway_batch` 包装、`persist_usage_batch`、`ingest_initial_usage` 只有 legacy 调用；`settle_requests`、`exact_billing_price`、`expire_wallet` 与 v2 SQL 共用。
- `packages/runtime` 的 `Limits`（Core 用于健康许可与半开探测）没有自己的测试，其探测隔离边界只由 legacy `routing.test.ts` 经 legacy 应用验证。

## 2. 决策

- **L1 逐例审计**：legacy 用例逐例归为四类：v2 已覆盖（列出 v2 用例）、有意差异（引用已记录决策）、legacy 专有机制（列出 v2 对应机制及其用例）、缺口。缺口中 v2 行为与 legacy 或规格不符的登记为 T16 发现并先红后绿修复；行为正确只缺用例的补 v2 用例。审计结果见 §4。
- **L2 billing 改走 v2**：`billing.test.ts` 的账本规则（来源、过期、债务、信用、退款、争议、批次、并发、回放）以 Core 执行 RPC 准入与签名证据结算重写，断言与人工算例保留；只验证 legacy 机制本身的用例（legacy 证据队列积压、legacy 旧库拒绝等）按审计归入 v2 对应机制或删除。
- **L3 删除范围**：删除 legacy 应用、`Store`、`usageChannel`、legacy 专用的 `adapters/protocol` 导出及只测它们的用例、legacy 脚本分支与 systemd 单元、`package.json` 入口、legacy 测试文件；Caddy 删除 `@legacy` 兜底，未列出的路径由 Caddy 直接 404（R6）；架构与 OpenAPI 单测改为只断言三进程。`POST /admin/recover` 随 legacy 删除（[E10](enterprise-v2-events.md)）。
- **L4 SQL 层**：应用删除后逐个核对只被 legacy 调用的 SQL 入口与 `runtime-role.sql` 角色：无 v2 SQL 内部调用、无角色依赖的，以追加迁移删除并经升级用例验证；仍被 v2 SQL 调用的保留并记录原因。

### 6.5 发现

- R16：v2 管理面创建渠道或替换 Key 时不校验云凭证结构（legacy 在管理面校验）。已在本里程碑修复，见[审查记录](enterprise-v2-review.md)。
- R17：v2 图片 JSON 应答按 `data` 项数计张。修改插件需要升版并重建包，单独提交修复。
- l3 测试夹具缺陷：`billing.test.ts` 的 `admit` 在 Core 回 `SAME_COMMAND` 时从头重新准备并新建请求。若 admit 已提交而 begin 回忙，旧请求的预扣留在钱包上，新请求得到 `insufficient_funds`，“concurrent holds…”等并发用例约三分之二的轮次失败（l4 首轮门禁暴露，单独连跑 6 轮中 4 轮失败）。公共夹具 `granted` 改为：准备阶段（不落账）可整体重试，admit 与 begin 各以原命令 id 重试，与契约中 `SAME_COMMAND` 的含义一致；`admit` 不再自行重试。修复后连跑 8 轮全部通过。产品代码不变。
