# Chat SSE 容量实测 · 2026-11-20

> 历史流式基准。本文记录 Enterprise v2 在 2026-11-20 的结果。现行流式结算见[路由与执行](../../routing-and-execution.md)。

目标是在 1000 个钱包均匀发起请求时，正式 Gateway 每秒完整结束 3000 路 SSE，并对每个请求核实终态、资金和外部 ACK。以下测试均使用本机 HTTP 上游替身，含预热的账务数字单独列出。

**正式 Gateway 的短 Chat SSE 连续两轮通过 150 RPS，3000 RPS 档未通过。** 以下三轮均使用相同的 1.9.1 已批准插件、同步终态、逐请求上游校验、实际双边资金和外部 ACK。核账按钱包与日记唯一键查询，消除了早先的历史流水扫描。每轮固定到达 60 秒，发生器漏发为零。

## 实现与核账查询的对照

**使用早期核账查询时，同步终态的 3000 档取得 46.58 完整 RPS。** 每秒固定到达 3001 个请求，持续 60 秒，180,060 个全部发出。2868 个请求收到有效正文、`[DONE]` 及正常结束，并最终核对资金和外部 ACK；其中 2795 个在窗口内全部完成。177,192 个请求失败，包括 152,741 个过载响应、740 个限流响应、108 个 Core 不可用及 23,603 个客户端超时。收到首段内容的 2868 笔 TTFT P99 为 4987.90 ms，这些请求发起至三方全部完成的精确 P99 为 4972 ms。TTFT 使用直方图桶上界，联合 P99 是毫秒时间戳的实际排序值。

含 11 笔预热，上游共收到 3532 笔，全部精确结算，客户支出 353,200，供应商成本 208,388；另有 754 次已发权但未实际发送，双方最终预扣为零。主库有 7818 条正式用量事件，外部实际 ACK 7064 条。普通证据队列和两个终态恢复队列全部清空。未确认完整成功的请求和缺少外部确认的事件均未计入达标值。[集成后目标轮的原始记录与重算](evidence-stream-2026-11-20/public-replicated-stream-target.tar.gz) · [正式代码差异与修复前后回归](evidence-stream-2026-11-20/public-replicated-stream-source.tar.gz)

**同一负载下，普通证据队列模式为 17.82 完整 RPS。** 该轮包含流式计量修正。180,060 个请求全部发出，1295 个收到首段内容，1080 个有效完整结束，1069 个在窗口内同时完成有效 HTTP、精确双边账务与外部 ACK。215 个请求收到内容后未完整结束。已收到首内容的请求 TTFT P99 为 2918.03 ms，1080 个最终匹配请求的精确联合 P99 为 7105 ms。

每个请求带唯一校验值，由上游写进最后一段文本，客户端核对本请求的完整内容、正常终止和 EOF。153,479 个请求收到过载响应，108 个 Core 不可用，859 个被限流，24,534 个客户端超时。含 7 个预热请求共观测到 1302 次上游接收和 1302 笔精确结算，客户支出 130,200，供应方支出 76,818，期末双方预扣为零。最终有 222 个已核实资金和 ACK 的请求没有对应测量期的有效完整 HTTP，其中含 7 次预热。默认上游每流只有一个文本增量，分段间隔另在低档测量。[修正后目标轮完整原始数据及独立重算](evidence-stream-2026-11-20/public-host-target.tar.gz) · [实测宿主及驱动源码](evidence-stream-2026-11-20/public-host-source.tar.gz)

计量宿主修改前，在同一到达率和流量窗口下，有 1288 个请求收到首内容，878 个完整结束，858 个在窗口内通过逐身份审计（14.30 RPS），精确联合 P99 为 6037 ms。两轮的在线 ACK 去重实现也有变化，不能据此单独估计宿主修改的性能收益。[修正前目标轮](evidence-stream-2026-11-20/public-target.tar.gz) · [当时的驱动源码](evidence-stream-2026-11-20/challenge-driver.tar.gz)

在已构建产物、配置本机原生 PG/Redis 工具的仓库中，用以下命令复现同步终态目标轮。去掉 `--replicated-stream-terminal` 可测普通证据队列模式。负载器与上游均由测试夹具在回环地址启动。

## 正式 Gateway 基线

最终审计工具另跑了一轮分帧校准。上游替身重复输出 8 段文本，每个网络块最多 192 字节，块间等待 20 毫秒。以每秒 11 个到达验证 10 RPS，660 个测量请求均完整结束并精确对账，其中 654 个在窗口内完成（10.90 RPS）。首帧 P99 为 167.24 ms，首内容 P99 为 188.40 ms，4620 个相邻文本增量间隔的 P99 为 22.80 ms，逐身份联合 P99 为 643 ms。含 3 个预热请求的发送总数、逐请求唯一校验值及双方资金均通过。在线 ACK 去重使用磁盘索引，测试夹具已清理。[分帧原始数据与重算结果](evidence-stream-2026-11-20/public-paced.tar.gz)

公开入口为 `POST /v1/chat/completions`，请求体含 `stream: true`。两档使用同一套构建物，4 个 Gateway、2 个 Core、1 个在线 worker（并发 8）、1000 个钱包、1 个供应账户、PostgreSQL 物理主备以及 Redis AOF 确认副本。每档固定到达 60 秒，发生器并发预算 10,000、请求限时 5 秒。客户和供应方每个成功请求分别计 100 和 59 个最小金额单位。

| 目标 / 每秒计划到达 | 测量请求 | 收到首内容 | 有效 HTTP 完整结束（含收尾） |   原审计窗口内交集 |  首内容 P99 | HTTP P99（含失败） |
| ------------------- | -------: | ---------: | ---------------------------: | -----------------: | ----------: | -----------------: |
| 10 / 11             |      660 |        660 |                          660 |   658（10.97 RPS） |   146.07 ms |          224.05 ms |
| 3000 / 3001         |  180,060 |      1,344 |                        1,132 | 1,114（18.57 RPS） | 2,902.27 ms |        5,014.98 ms |

高档按计划发出了全部请求。153,796 次过载、86 次 Core 不可用、682 次限流、24,364 次客户端到期。收到首段内容的请求中有 212 个未完整结束。18.57 RPS 是系统处于这次过载时的窗口结果，稳定容量需要在中间档单独测量。旧审计按已出现的交付检查 ACK，缺少成功终态约束，且仅验证流包含文本。因此上述窗口交集只作为旧版基线。

含 7 个预热请求，1,351 笔实际发送取得了精确客户和供应账，支出分别为 135,100 和 79,709。另有 524 个 attempt 终态为未发送。客户和供应预扣以及期末队列均归零。PG、Gateway、Core API 的 CPU 采样分别为 73.39、69.61、45.73 核秒。主库顶层 SQL 累计时间中，执行批约 39.5 秒、结算约 21.3 秒、资金组锁约 14.1 秒，包含等待时间。相同的过载错误可从多条代码路径返回。[原始 HTTP、审计及逐请求时间戳](evidence-stream-2026-11-20/public-baseline.tar.gz) · [核账摘要与产物哈希](evidence-stream-2026-11-20/public-baseline.json)

正式 60 分钟夹具在每秒计划到达 3001 路时需要 872,877,934,592 字节磁盘，预检可用 244,531,200,000 字节，未创建夹具。这个数字是仓库对完整物理主备拓扑的空间预算。每分钟的稳定吞吐仍待实际长测。

## 公开入口的结算积压

每秒发起 151 个短流，以 150 个完整请求/秒为目标。两轮使用相同构建物和相同的逐身份终态审计。比较默认 Core 与按已认证项目分配 Core 的候选，后者同时改变两条目标连接的分配。严格审计允许合法进度事件独立 ACK，只有选定 attempt 的成功终态已验签、客户和供应方金额及分录正确且外部 ACK 已齐备才记入窗口。

| 路由                    |   有效 HTTP | 首内容 P99 |   HTTP P99 |   60 秒内完整请求 | 发起至 HTTP、资金与 ACK 全部完成的 P99 | 结算队列峰值 |
| ----------------------- | ----------: | ---------: | ---------: | ----------------: | -------------------------------------: | -----------: |
| 默认                    | 9060 / 9060 |  821.81 ms |  930.81 ms | 2567（42.78 RPS） |                              43,170 ms |         5324 |
| 按项目固定 Core（候选） | 9060 / 9060 | 1155.94 ms | 1267.40 ms | 2425（40.42 RPS） |                              44,178 ms |         5506 |

联合 P99 按三个时间日志独立排序重算，样本包括窗口结束之后才收到 ACK 的请求。两轮各有 9067 笔含预热的精确客户和供应账。候选轮有一个消费租约超过审计等待期限，最终已 ACK。默认轮到第 60 秒已记录 11,028 次结算锁冲突，停止到达后约 28 秒才排空。逐笔双边资金审计查询也耗用累计约 31 秒数据库执行时间。固定项目使资金组锁的累计时间从约 186 秒降到 0.3 秒，窗口完整吞吐和首内容延迟均未改善，该候选留在实验记录中。这两轮每笔仅有一个非空文本增量，增量间隔没有样本。按此次驱动，固定文本及消费终态逐笔核对，上游真实发送次数按总数核对。[原始审计、逐请求重算脚本及候选补丁](evidence-stream-2026-11-20/public-routing-ab.tar.gz)

修正流式宿主、加入逐请求上游校验和联合 P99 门禁后，正式入口又在相同的 151 到达/秒配置下测量。9,060 笔测量请求均取得有效 HTTP，只有 2447 笔在窗口内完成三方核对（40.78 RPS）。首内容 P99 为 741.46 ms，发起至三方全齐的精确 P99 为 44,046 ms。两个消费租约过期，最终 17,704 个事件全部获得外部 ACK，期末双方预扣为零。[当前正式产物的中间档原始记录](evidence-stream-2026-11-20/public-host-151.tar.gz)

### 正式入口的同步流终态

Gateway 和 Core 都启用同步流终态的早期候选只识别 HTTP 分块响应。标准上游在 Bun 1.4.4 上会把这一短流发送为带 Content-Length 的 SSE，实际捕获的单笔为 791 字节。151 到达/秒时，全部 18,134 份证据仍由普通 worker 处理，窗口交集只有 2361 笔（39.35 RPS）。[分块限定候选的原始对照](evidence-stream-2026-11-20/public-terminal-v3-151.tar.gz)

固定长度候选读取到 HTTP 消息体 EOF，核对长度后才提交正常终态并放行同批的计量正文和终止帧。相同的 151 到达/秒下，9,060 笔均发出并完整结束，窗口内三方核对从默认配置的 2447 增至 **6907（115.12 RPS）**，完整 P99 从 44,046 ms 降至 26,741 ms。首内容与 HTTP P99 均为 410.91 ms。含 11 笔预热的 9071 笔客户和供应结算、18,142 份正式事件及外部 ACK 全部对齐，期末双方预扣为零。普通 worker 处理的成功证据为零。该轮数据有效，吞吐与联合 P99 均未通过 150 档。[固定长度候选的原始对照](evidence-stream-2026-11-20/public-terminal-v4-151.tar.gz)

同步终态的 151 到达/秒测试还暴露出外部消费者自身的瓶颈。执行 2434 次完整账务检查累计占用 52.01 秒数据库查询时间。在同一钱包有 8000 条历史日记的真实 PostgreSQL 夹具中，旧计划对 8 个请求重复扫描客户日记，访问 193,680 个缓冲页。改为用钱包和结算引用的唯一键逐请求定位后，访问量降至 520，通用计划的批查询从 37.70 ms 降至 0.57 ms。核对的资金、签名、所有正式事件及 ACK 条件相同，完成时间仍以实际观察为准。此处是审计查询耗时，公开容量另测。[执行计划、负例与复现命令](evidence-stream-2026-11-20/audit-plans.tar.gz)

### Worker 与资金写入的对照

在默认路由和相同的 151 到达/秒下，先让 worker 与短流发权事务按资金组协调。该实验将 worker 记录的锁冲突从 15,373 次降至 7 次，窗口内完整完成从 2567 增至 2995（49.92 RPS），联合 P99 从 43,170 ms 降至 40,162 ms。队列峰值仍有 5556。一个批包含多个独立资金组时，繁忙组会阻塞整批，历史两阶段许可和纯估算也可能等待。按组隔离回归复现了这些问题，这一版本仅保留作对照。[首次协调实验及原始逐笔数据](evidence-stream-2026-11-20/worker-blocking.tar.gz)

随后限定为经持久化回执确认的合并短流许可，跳过纯估算，跨组非阻塞取锁，单组等待同时受锁、语句和事务期限约束。新版的原生资金回归通过 116 个断言，历史升级及迁移中断回退通过 11 项。相同驱动与参数下，完整交集为 2509（41.82 RPS），比默认路由的 2567 少 58 笔。精确联合 P99 为 43,436 ms，锁冲突 15,334 次，队列峰值 5365，另有一次消费租约过期。最终 9060 个测量请求有效结束，含预热 9067 笔双边账正确，所有 17,721 个正式事件最终均获 ACK。该迁移未采用。[修正后的 SQL、回归及原始逐笔对照](evidence-stream-2026-11-20/worker-bounded.tar.gz)

## 渐进式流原型

原型的源包、测量结果与逐请求原始文件按[证据目录及校验说明](evidence-stream-2026-11-20/README.md)组织。

这个原型采用独立的回环 HTTP 入口、实际发行的流式插件、紧凑型双边资金账和指定 PostgreSQL 同步备库。外部消费者逐份验签并实际 ACK。延迟上游样本中，12 个客户端均在上游结束前收到首内容。单宿主和三宿主两轮最少分别提前了 393 和 394 毫秒。首个内容增量所带的 `PARTIAL` 证据在放行前已获备库确认，每轮共核对 36 份证据和 ACK。另有 4 个每流 40 段文本的样本，共触发 24 次插件 `stream_drain`。

| 每秒计划到达 3010 个，60 秒 | 实际到达入口 | HTTP、主备账及外部 ACK 全齐（含收尾） | 窗口内完整吞吐 | 首内容 P99 |   完整 P99 |
| --------------------------- | -----------: | ------------------------------------: | -------------: | ---------: | ---------: |
| 单个插件宿主                |       77,625 |                                77,625 |    1259.62 RPS | 1678.47 ms | 1724.13 ms |
| 三个插件宿主                |      139,023 |                               139,006 |    2282.42 RPS |  981.00 ms | 1038.03 ms |

三宿主将不同请求分给独立的插件宿主，各请求仍按下游拉取推进，证据和资金使用原有写入与备库确认路径。180,600 次计划到达中，41,577 次遇到客户端在途上限未发出，另有 17 次上游连接复位。该原型保留了这些请求的测试预扣，未取得可完成核账的终态。完整 P99 只覆盖三方记录全齐的请求。两轮均未通过 3000 RPS。原型使用固定路由、单币种和预设资金上限，正式身份与权限、动态报价、分布式配额和未决资金恢复仍需在正式入口验收。[原型实测与复算说明](evidence-stream-2026-11-20/prototype/RESULTS.zh.md) · [两版源码与七组原始证据校验清单](evidence-stream-2026-11-20/prototype/SHA256SUMS)

## 架构约束

公开流式宿主按每次读取驱动插件，一次读取可能包含多份累计计量。对于同一批先后观察到的不同用量，在处理会覆盖该用量的后续帧之前，先将已观察到的进度交给原有签名与耐久发布路径。进度为累计快照，结算按对应 revision 取值。终态仍在成功发布后才允许输出。回归使用已发行的 OpenAI Chat 与 Anthropic Messages 插件，覆盖共包与拆包、后续错误、发布失败和中途取消。

OpenAI Chat 1.9.1 的独立回放中，同一读批里的累计用量 1 → 3 → 5 原先可能只交付最后的 5。修正后的宿主保留 1、3 的阶段证据和最后的 5。另行构建并用本地测试密钥签发的 1.9.2 候选合并了普通文本帧的字段读取。相同宿主、相同输入的 64 个串行短流中，每笔 prepare 消息均为 2 次，流式插件进程间消息由 23 减为 14 次，本进程 CPU 由每笔 2.462 ms 降至 1.828 ms。正式 Gateway 继续使用获准的 1.9.1 工件。新版本需要独立的发布签名和运行时审批，旧包的身份与摘要仍绑定原实现。[两版回放、发布身份、源码补丁和回归证据](evidence-stream-2026-11-20/frame-evidence.tar.gz)

在公开入口默认 151 到达/秒的对照中，PostgreSQL 为 9067 个含预热请求累计耗用 172.18 核秒，平均约 19.0 ms CPU/请求。12 核机器要持续完成 3000 RPS，即使完全用于网关系统，所有服务加起来也只有约 4.0 ms CPU/请求。这个对照包含验签、完整审计和排空，给出的是该配置的单位成本。减少 RPC 等待和降低准入锁等待本身解决不了这个差距。

同一轮的顶层 SQL 统计显示，证据结算写入 217,927,568 字节 WAL，执行批写入 175,357,075 字节，合计占顶层 WAL 的 87.9%。9,067 笔准入产生 18,134 条签名事实，其中 17,671 条获接受、463 条为迟到的旧修订。结算当前已经按表批量写入，下一步可单独验证减少每条签名事实的重复载荷写入。这项变更须保留原始与规范快照各自的 ID、修订、差异以及账务和投递的外键，并在备库和历史归档按原 ID 核对。WAL 字节是写入量，该轮未采到单表 CPU。[对应原始 SQL 与进程统计](evidence-stream-2026-11-20/public-routing-ab.tar.gz)

要把原型的收益移到公开入口，一条完整的 Chat 流必须从已认证项目、已批准的插件和双边正额预扣取得唯一发送许可。发行插件按需拉取上游，各自拥有执行状态，含新计量事实的内容输出需经过对应的证据耐久确认。正常终态与资金分录以及待投递事件必须一致，外部 ACK 继续独立观测。对于断流、回执未知和迟到用量，沿用原 attempt 幂等恢复，保留未决资金责任。这些边界决定哪些工作可以合批，也决定为什么原型吞吐需要在正式入口重新验证。
