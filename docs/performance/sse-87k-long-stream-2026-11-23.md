## 瓶颈归因

1. **New API 每路内存高 5× 且 CPU 高 3.5–8×**：
   - `relay/channel/openai/relay-openai.go` 与 `helper.go` 为每路流维护 `responseTextBuilder strings.Builder` 整段缓存 348 KB 输出正文（含切片扩容与 64 KB `bufio.Scanner` 实占 `~890 KB/路`），并对每帧 SSE 执行两次完整 JSON 反序列化、跨 goroutine/channel 传递与每帧独立 `Flush()`。
   - 独立 `7,500` 并发下，New API 进程 RSS 达 `5.72 GB`、CPU 达 `670%`，每帧独立 `Flush()` 叠加 GC 抖动触发内核 `write: no buffer space available` 导致 3,436 路中途断流；场景 2 高并发下还出现 `redis: connection pool timeout` 回退 DB 导致 10–30 s TTFT 尖刺。
2. **Gateway 单进程精确硬上限 `8,192` 与线性多实例扩展**：
   - Gateway 在 `chat -> chat` 透传路径不缓存完整响应正文，每路约 `158–167 KB` RSS，单核峰值帧处理约 `~830k 帧/s`。
   - 单进程在 Bun 1.4.5 `Bun.serve` 下存在精确 `8,192` 并发连接硬上限；生产建议单实例设 `MAX_IN_FLIGHT ≤ 6,000–7,500`，通过多实例无状态扩展线性叠加。
3. **本机单环路宿主机上限（`~12,000` 双跳并发）**：
   - 4x Gateway 在 `15,000` 并发时约 `~11,580–12,000` 双跳并发（`~48,000` 同机回环 socket 端点）打满 macOS `kern.ipc.nmbclusters=131072`（`netstat -m` 记录 `125,953,662` 次内核 mbuf 分配拒绝）。

## 4x 满载排查结论与针对性加固

针对上述 4x 极端满载暴露的两类现象，已完成独立复现、根因定位与代码加固：

### 1. `HPE_STRICT` / `HPE_CR_EXPECTED` / `invalid_upstream` 根因定性（宿主机 macOS 27.0.1 回环 `ENOBUFS`）

- 抓包确认：客户端报 `HPE_STRICT: Expected LF after chunk data`，网关侧 `bun-http1.ts` 报 `invalid_upstream: Malformed chunk terminator` 与 `invalid_upstream_json`。
- **独立 2×2 原始 TCP 字节序隔离验证**（不经过任何 Gateway 或 HTTP 代码，发送 `16,384 × 113 = 1,851,392` 字节递增字节流，2,048 并发）：
  - `Node -> Node`、`Node -> Bun`、`Bun -> Node`、`Bun -> Bun` **四组原始 TCP 全部复现字节错位且接收总字节数多于发送字节数**（收到 `1,866,632–2,072,108` 字节，多出 `+15 KB` 至 `+196 KB`，对应 `lo0` 16 KB MTU 分段），`netstat -m` 记录 `125,953,662 requests for memory denied`。
  - 结论：**非 Gateway 或 `bun-http1.ts` 的分块/复用缺陷**，而是本测试机 macOS 27.0.1（`Darwin 27.0.0 / xnu-13432.1.9`）在高并发非阻塞 `lo0` 触及 `kern.ipc.nmbclusters=131072`（`ENOBUFS`）时向 TCP 流注入重复分段；Gateway 严格校验器正确识别了受损报文并 fail-closed。

### 2. `open_holds` 残留、瞬态 `http_500` 与 Worker 回收加固

复现与源码核对确认了 4 处真实可复现缺陷并已完成最小充分加固与回归验证：

1. **Worker 过期预扣清扫遗漏租约解绑（`packages/ledger/src/hold-transitions.ts`、`leases.ts`）**：原 `sweepTimedOutHolds` 直接 `UPDATE billing_holds SET state = 'UNKNOWN'`，未调用 `detachHoldFromLeaseTx`，导致租约态超时预扣在转 `UNKNOWN` 后仍挂着 `wallet_lease_id` / `supplier_lease_id`、`lot_allocations` 为空，且在 `reconciliation.ts` 触发 `supplier_attempt_conflict`；同时 `IN (SELECT ... LIMIT)` 未用 `MATERIALIZED` CTE 严格限制单批锁行数。现已改为无租约快路径使用 `WITH expired AS MATERIALIZED (... LIMIT $1 FOR NO KEY UPDATE SKIP LOCKED)`，租约态过期预扣按游标分页并以 `NOWAIT` 解绑租约、容忍并发争用避免头阻塞，同时 `markUnknown`/`releaseHold` 在预扣已被 Worker 扫走时仍清理本地租约在途计数防止租约被无限续期。
2. **Worker 过期清扫单 tick 吞吐受限与指标缺口（`apps/worker/src/runner.ts`）**：原每 `2 s` tick 仅扫单批 200 条预扣。现改为与 `outbox` 一致的时间预算排空循环（每批 `500` 条预扣 / `100` 条租约，循环间复核主节点租约并在排空或到预算时退出），并暴露 `stg_worker_swept_holds_total` 与 `stg_worker_swept_leases_total` 指标。
3. **账本瞬态锁争用重试与直接结算微批二分隔离（`packages/ledger/src/funds.ts`、`hold-transitions.ts`、`settlement-direct.ts`、`settlement-dispatch.ts`）**：为 `releaseHold`、`markUnknown` 与提交后 `markAccountsReconcileRequired` 补充对 PostgreSQL 瞬态并发错误（`40P01`、`40001`、`55P03`）的有界退避重试；直接结算仅在事务提交后写回结果数组，并在多笔微批遇锁超时时受时间预算保护地立即二分隔离，避免单笔热点锁超时导致同批其余无争用请求集体 `ledger_commit_failed`。
4. **网关预扣收口重试与错误码保护（`apps/gateway/src/proxy.ts`）**：将非流式与流式失败/中断路径收敛到 `finalizeHold`，仅在账本确认后才置位 `holdFinalized`（不再在进入流式前提前置位，也不再在失败抛出后二次重试或将 `"release"` 降级为 `"unknown"`），瞬态失败重试 2 次且保留上游真实 `4xx/502/503/504` 错误码而非覆盖为 `500 internal_error`。
