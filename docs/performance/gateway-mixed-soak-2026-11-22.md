# 混合插件稳态与网关并发复测

## 验收口径

单网关和双网关依次运行独立构建，使用不同的隔离数据库和相同的 Redis、Worker、Mock 与数据库耐久配置。每轮 1,800 秒，发生器计划每秒 2,000 笔，最多 256 笔同时在途。按请求数轮转普通 JSON 50%、普通 SSE 25%、真实内置 WASM 脱敏 JSON 12.5%、真实 HTTP Webhook 脱敏 SSE 12.5%。逐请求检查正文和脱敏结果，SSE 还必须收到终态。每分钟记录吞吐、错误、延迟和进程资源。

计量夹具回传 7 个未命中输入 token、3 个缓存命中输入 token、5 个输出 token。客户价为 10、5、20 atoms，供应商价为 2、1、4 atoms，故每笔应结算 185 和 37 atoms。逐笔核对用量、金额和相应插件审计，按模型对账并检查重复结算、挂起预扣、租约和资金守恒。

短 JSON 饱和复测保留 8 秒测量窗口、请求报文、拓扑与持久化规则。冷连接诊断与已建立连接的稳态分开测量。性能提升相对同一环境下的前一份独立构建计算。以历史最高已确认档为规划参考，提升 50% 对应单网关 21,616.8 RPS、双网关 26,843.3 RPS。

## 优化范围

- 压测端按最多 64 路新增连接的节奏预热，保留高并发档所需的空闲连接，预热在计时前完成。冷连接模式保留原驱动，作为网络诊断对照。
- 整数计价仍使用精确整数累加，分数与小数保留有理数累加并统一向上取整。快速结算将稳定的序列化、用量摘要及金额字符串移到持锁前准备。同一笔预扣仍先持久化才能派发，结算事务、供应商租约栅栏及 Outbox 顺序沿用现有协议。
- 集群准入使用 Redis Lua 脚本摘要。仅在 Redis 明确返回脚本不存在时回退原脚本，通信超时和其他错误沿用失败处理及主备切换路径。使用自定义 Redis ACL 的部署需要同时授权 `EVALSHA` 和 `EVAL`。 [Redis EVALSHA](https://redis.io/docs/latest/commands/evalsha/)

## 2,560 并发连接重置

复现使用同一份改动前 Gateway 构建与相同请求。旧发生器每个网关最多保留 1,024 个空闲连接，2,560 并发需要每端 1,280 条连接，至少 256 条新连接同时打向每个监听器。本机 macOS 的 `kern.ipc.somaxconn` 为 128。独立环回 Bun 监听器暂停接受连接 75 ms 的对照中，128 个冷连接全部成功，256 个冷连接仅 128 个返回 200，另有 79 个 `ECONNRESET` 和 49 个 `EPIPE`。在同一监听器分批预热后，256 个请求全复用连接并成功。macOS 全局 `listen queue overflow` 计数在受控复现中也保持为零，归因依据是容量阈值、客户端在建连阶段失败以及预热对照。 [Darwin 监听队列上限](https://github.com/apple-oss-distributions/xnu/blob/xnu-12377.121.6/bsd/kern/uipc_socket.c#L841-L858)

| 双网关并发 | 旧建连方式错误 | 分批预热错误 | 预热后 RPS | 预热后 P99 ms |
| ---------: | -------------: | -----------: | ---------: | ------------: |
|      2,048 |              0 |            0 |   18,722.8 |        181.53 |
|      2,304 |              0 |            0 |   18,563.3 |        232.03 |
|      2,560 |            201 |            0 |   16,125.6 |        286.25 |
|      3,456 |            367 |            0 |   16,966.3 |        358.22 |

两轮成功响应均逐笔唯一结算，共 625,756 和 569,698 笔。账户守恒通过。预热修复了发生器造成的瞬时新建连接突发，吞吐仍需与相同预热口径的构建比较。生产负载均衡器与冷连接风暴是单独的容量边界。

## 复跑命令

```sh
bun run build
BENCH_GATEWAY_NODES=1 BENCH_SOAK_SECONDS=1800 BENCH_SOAK_RPS=2000 bun run bench:prod --mixed-soak
BENCH_GATEWAY_NODES=2 BENCH_SOAK_SECONDS=1800 BENCH_SOAK_RPS=2000 bun run bench:prod --mixed-soak
BENCH_LIMIT_COLD_CONNECT=1 BENCH_JSON_CONCURRENCY=2048,2304,2560,3456 bun run bench:prod --limit
BENCH_JSON_CONCURRENCY=2048,2304,2560,3456 bun run bench:prod --limit
```

以 `BENCH_DIST_DIR` 指定已归档的构建目录可复跑旧版本。驱动每分钟把进度写入 stderr，结束把完整 JSON 及资金检查写入 stdout。基准程序只创建和删除本次独立数据库，退出时停止本次进程。

## 30 分钟混合稳态

单网关完整测量 1,800.032 秒，计划 3,600,000 笔，实际发出 3,566,316 笔，全部获得有效响应。实际成功吞吐 1,981.25 RPS，P99 121 ms。发生器的在途和追赶上限合计拦下 33,684 个计划请求，占 0.9357%。这些请求没有派发，HTTP、传输、协议与脱敏验收错误均为 0。脚本保留全计划零错误门禁，因此这批漏发使进程退出码为 1。起量和吞吐分开审阅。

## 同口径容量与 50% 目标

比较在本机独立 macOS arm64、Bun 1.4.5 和 PostgreSQL 17.11 上做，全部开启三项数据库耐久设置。双网关统一使用分批预热。此前性能记录的数据库环境不同，以下吞吐提升只相对此表基线。

- 基线构建 Gateway SHA256 为 `25c32f1fa65d0093c853de6e2b9dfd4552f491a4d3fa4b352bbacbe58da8f804`。
- 含整数计价、结算预序列化和 Redis 摘要优化的候选构建 Gateway SHA256 为 `00f61a6503c4b7cd4e0e51c02c9bec161917aec3bed572621537e574c78199c5`。

四轮短负载错误率为 0，完成响应均唯一结算，资金守恒。单网关 1,536 并发时网关 RSS 为基线 459.3 MiB、候选 474.9 MiB。双网关 2,560 并发排空后联合 RSS 为 880.0、878.4 MiB。双网关 3,840 并发两份构建均零错误，比此前的 2,304 并发档增加 66.7%，主要来自避免冷建连突发。在该档，候选 P99 达 325.57 ms。

本机同口径基线实际峰值为单网关 16,259.9 RPS 和双网关 19,542.7 RPS，乘以 1.5 对应 24,389.9 与 29,314.1 RPS。候选第一轮峰值为 16,021.3 和 18,582.3 RPS，未达到该目标。

本机单网关饱和诊断中，结算锁等待仍出现 430 个事务锁采样。长测的默认隔离 PostgreSQL 频繁触发 WAL 检查点，日志记录到 7–10 秒间距。压测分别关注结算热租约与存储写入。

全量门禁通过 93 项单测、33 项集成、构建产物和强杀恢复检查。Redis 清空脚本缓存后，续租继续有效，跨节点并发拒绝与 RPM、TPM 计数准确。独立 PostgreSQL 同步主备切换未丢失确认事务，推理约 5.57 秒恢复。Redis Sentinel 配额约 2.80 秒恢复，PITR 演练通过。故障演练与 30 分钟稳态分开执行。

### 交错复测

双网关 2,560 并发按基线、候选、候选、基线顺序复测，依次为 19,548.2、20,074.7、19,652.5、19,837.6 RPS。候选两次均零错误，P99 为 247.77 与 235.93 ms。基线首轮零错误，末轮有 2 个请求错误。两组两次平均值相差约 0.9%，加上首轮矩阵的反向波动，无法把差距视为可重复的显著吞吐提升。

这组短测没有取得可重复的 50% 成功吞吐提升。较大的 WAL 空间和微批只用于本机对照，仓库生产默认值保持原配置。3,840 是本机已验证的短时连接并发档。两轮长测成功请求均精确结算，同时都有发生器漏发。下一轮若以持续吞吐为目标，应优先验证如何缩短共享供应商租约的结算串行区间，并在同一持久化拓扑同步验证尾延迟和故障切换。
