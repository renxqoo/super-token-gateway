# 插件修订改造本机验证

基线为 `5b63227`，新版本为本次工作区独立构建，schema 为 `2026112202`。环境为 macOS arm64、Bun 1.4.5、本机 PostgreSQL 17 和 Redis 7.4。数据库保持 `fsync=on`、`synchronous_commit=on` 和 `full_page_writes=on`。基线和改造后按相同脚本、并发档与持续时间分别串行执行。

## 执行方式

```sh
bun run verify
BENCH_SECONDS=8 bun run bench:single
bun run bench:prod --stress
bun run bench:prod --limit
bun run test:production
```

## 第二轮：发布确认、紧急撤销与租约锁优化

第二轮基线为上表完成后的旧构建 `2026112202`，候选为包含节点级应用确认、紧急撤销与租约锁调整的 `2026112203`。两轮基线的并发拓扑与结果各自对照。第二轮每个短 JSON 档持续 8 秒并包含尾部排空。同一拓扑使用相同的请求、持久化 PostgreSQL、HTTP keep-alive、Mock 数量、连接池、微批配置和准入上限。单网关使用两个轮询 Mock，双网关使用一个 Mock、独立 Worker 和 Redis 共享配额。两种拓扑分别使用不同的负载和配置，扩展结果按各自基线对比。

```sh
BENCH_SECONDS=8 BENCH_JSON_CONCURRENCY=512,1024,1536,2048,3072 bun run bench:single
BENCH_JSON_CONCURRENCY=512,1024,1536,2048,3072 bun run bench:prod --limit
BENCH_JSON_CONCURRENCY=2048,2304,2560 bun run bench:prod --limit
BENCH_SECONDS=8 BENCH_JSON_CONCURRENCY=1024,2048 BENCH_PG_WAITS=1 bun run bench:single
mkdir -p /tmp/stg-gateway-profile
BENCH_SECONDS=8 BENCH_JSON_CONCURRENCY=1024 BENCH_CPU_PROFILE_DIR=/tmp/stg-gateway-profile bun run bench:single
```

### 瓶颈定位

基线单网关在 2,048 并发达到 11,281.9 RPS，增加至 3,072 并发只多 50.6 RPS，P99 从 230.80 ms 升至 327.66 ms。1,024 并发的 Bun CPU profile 包含 3,027 个采样，热点包括 JSON 序列化、SQL 数组编码和网络写入。进程统计中 Gateway 约 68% CPU，单个负载客户端约 20%。这轮优先验证数据库等待。

对 1,024 和 2,048 并发合计进行 `pg_stat_activity` 抽样。旧构建预扣租约语句出现 531 个事务锁等待样本、79 个元组锁等待样本。优化后同样抽样窗口为 0 个预扣租约锁等待，结算锁仍有等待。用 `FOR KEY SHARE` 允许预扣与持 `FOR NO KEY UPDATE` 的结算并行，以 `FOR UPDATE` 保持实际关租互斥。隔离测试分别验证钱包和供应商租约关闭等待，以及普通结算锁下能够完成预扣。1,024 并发的带采样对照从 10,789.7 提升到 14,365.8 RPS，P99 从 130.17 ms 降到 85.04 ms。两个带采样的运行均保持零错误、零重复结算和账务守恒。 [PostgreSQL 17 行锁兼容性](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)

单网关最终完成 563,792 笔请求且全数唯一结算，1,024 并发超过 12,000 RPS 门槛。1,536 至 3,072 并发进入约 14,200 至 14,400 RPS 的平台，3,072 并发仍零错误，P99 比 1,536 并发增加 100.83 ms。

双网关又在最终构建上连续细测两次。2,304 并发两次均零错误，达到 17,360.8 和 17,895.5 RPS，P99 分别为 193.28 和 175.22 ms。2,560 并发出现 233 和 199 个连接重置，成功吞吐也降至 17,055.8 和 17,525.2 RPS。两次运行都通过唯一结算和账务守恒核对。此机器、负载和配额拓扑的零错误上限位于 2,304 至 2,560 并发之间。

### 发布与撤销验证

- `bun run verify` 共通过 92 项单测、32 项集成测试、构建产物与耐久验证。历史 schema 升级夹具、15 个内置渠道的 30 笔 JSON 和 SSE 请求均通过。强杀恢复 16 笔预扣并重放逻辑备份。
- 两个实际 Gateway 共用 PostgreSQL。回归覆盖已派发流撤销后没有成功终态且账务保留 `UNKNOWN`、未派发请求不写预扣、正常备选路由继续服务、已提交结算保留且一元响应停止发送。人为阻塞节点确认写入时，另一节点仍可应用紧急撤销。旧启用入口、旧预扣锁和两处撤销竞态均取得失败与修复通过证据。
- `bun run test:production` 验证控制与数据角色分别可撤销和写入应用确认。隔离 PostgreSQL 同步切换未丢失确认事务，推理恢复耗时 5,525.74 ms。Redis Sentinel 共享配额恢复耗时 2,877.80 ms。PITR 恢复点前已确认事务完整。
- 以上性能数据是本机短时合成负载，未覆盖生产承载量及 30 分钟混合 WASM/Webhook 稳态。
