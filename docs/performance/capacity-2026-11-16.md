# T17 本机最大稳定负载报告

> 历史基准。本文记录 Enterprise v2 在 2026-11-16 的结果。现行验证要求见[容量及对标契约](capacity-contract.md)。

2026-11-16，提交 07e811b（T17 k3）之后的工作树：k4 的 R22 修复（`apps/gateway/src/chat.ts`、`packages/plugin-host/src/sse-stream.ts`）在 SSE 轮次前构建；短 JSON 轮次使用 k3 构建，R22 只改流路径，不影响短 JSON。按 [capacity-contract.md](capacity-contract.md) 验收。本报告测得的 35 RPS 低于用户随后确定的 3000 RPS 门槛，T17 未完成；下文同时给出达到门槛所需改造的实测依据。

## 环境与固定配置

- 硬件/OS：Apple M6，12 核，24 GiB；Darwin 27.0.0 arm64。Bun 1.4.4（仓库本地工具链）、PostgreSQL 17.11、Redis 7.4.12，全部原生进程（`scripts/native-services.ts`）。
- PG：fsync、synchronous_commit、full_page_writes 开启；shared_buffers 256 MiB，max_wal_size 1 GiB，max_connections 200。
- 证据 Redis：AOF always、noeviction，`QUEUE_REQUIRED_REPLICAS=1`，本机 AOF 副本（56394）确认后才算发布；准入 Redis AOF everysec。macOS 上 AOF always 走 F_FULLFSYNC，每次落盘约毫秒级，这是本机耐久成本，未改。
- 拓扑：2 个 Gateway 实例、1 个 Core API、1 个结算 worker（并发 8，另测 2/16）、外部消费者在线 ACK；上游为零延迟 TLS 替身（短 JSON 约 1 KiB 响应）。正费率：客户每请求 100 atoms，供应成本 59 atoms。
- 发生器：`bench-system --online-capacity`，固定到达率，60 秒窗口，排空上限 120 秒；`--target-rps` 给出时由工具判定 HTTP 吞吐、逐 request ID 交集（HTTP 成功 ∩ PG 证据与账单已提交 ∩ 外部真实 ACK）、每分钟 P99 ≤ 1500 ms 与排空。每轮 `audit.json` 记录产物 SHA-256、PG/Redis 设置与进程 CPU/RSS；原始证据在 `.local/capacity/bench-*`（本机，不入库）。
- 新增发生器参数 `--request-timeout-ms`（默认 30000，范围 1000–600000）：同时设置发生器请求期限与 Gateway `total_timeout_ms`，供 30/120 秒 SSE 使用；默认值保持原行为。

结算并发对比（同到达率）：80 RPS 时 worker 并发 2 / 8 / 16 的交集为 17.28 / 14.23 / 12.75 RPS，P99 300 / 446 / 977 ms；50 RPS 时并发 2 / 8 为 21.15 / 33.52。提高并发让结算事务更多地在同一供应账户行上互相等待，不提高吞吐。

## 瓶颈

40 RPS、60 秒逐进程 CPU（核）：PostgreSQL 1.03、插件 helper 0.46、Gateway 0.33、Core API 0.16、worker 0.07、Redis 0.07，合计约 2.1 核，即每请求约 53 ms CPU；按 3000 RPS 需约 160 核，本机 12 核。`pg_stat_statements` 同轮：证据持久化 `persist_core_evidence_groups_v1` 13345 次调用（约每证据组 3 次，锁冲突重试）共 28.0 s，执行批 `core_execution_batch_v1` 26.2 s，SQL 内规范 JSON 与其 sha256 约 33.5 万次调用共 16.6 s（每请求约 140 次），调用方身份校验每请求约 14 次共 7.0 s。

- 供应账户余额热行：准入、begin 与结算都要锁 `upstream_account_balances` 同一行（`FOR NO KEY UPDATE NOWAIT`）。T17 k3 后 Core 在锁冲突时最多 1 秒内重新入批（R19），准入侧尾延迟可控；结算侧锁冲突退避（10–200 ms 抖动、2 秒预算）在持续准入下抢不到行，40 RPS 以上积压线性增长。单钱包与 10 钱包结果接近均匀分布，说明主瓶颈是供应侧单行而不是客户钱包。
- 架构方向（不在 T17 范围）：对供应账户采用“先划拨额度、分片并行消费”的额度单元，消除单行串行。未实现，作为后续决策项报告。
- 证据副本确认：R20 后 `WAITAOF` 分片等待，每窗口发布 P99 约 50–150 ms，不再是瓶颈。

## SSE

上游替身每个响应约 54 个事件、8.5 KiB，按 160 字节分块，块间隔 90 / 550 / 2200 ms 对应约 5 / 30 / 120 秒流。

| 流长  | 到达 RPS | 计划/完成 | 同时在途峰值 | TTFT P50 / P99 ms | 完成时长 P99 | Gateway CPU 秒/请求 |
| ----- | -------- | --------- | ------------ | ----------------- | ------------ | ------------------- |
| 5 s   | 4        | 240 / 240 | 21           | 234 / 274         | 5.24 s       | 0.86                |
| 30 s  | 2        | 120 / 120 | 62           | 1143 / 1234       | 31.1 s       | 0.91                |
| 120 s | 1        | 60 / 60   | 60           | 4476 / 4525       | 127.8 s      | 1.70                |

全部有效完成、精确结算、外部 ACK 一致，上游无取消。TTFT 约为两个上游块间隔，反映替身首个完整事件跨两个 160 字节块，不是网关排队。token 间隔由替身固定，未单独测量。

失败尝试与边界：

- 首轮 SSE 5 秒 20 RPS：Gateway 两实例约 475 CPU 秒/77 秒，约 6 核饱和，随后超时与 `no_route`；30 秒 10 RPS、120 秒 5 RPS 的计划在途分别约 300、600，超过两实例合计 256 个插件 attempt，余量以 503 overloaded 拒绝（R18 预算，按设计）。
- 每帧成本（R23）：宿主每个 SSE 帧至少一次 helper 调用、每次新建 Wasm 实例，实测约 13–18 ms Gateway CPU/帧；纯 JSON 请求约 0.07 CPU 秒。本机 12 核据此约每秒 700–900 帧，54 帧响应约 13–16 RPS 的理论上限，实际需留余量。多帧批 ABI 是改进方向，属架构变更，未在 T17 实施。
- 每 Gateway 实例最多 128 个并发流（插件 attempt 预算），长流的并发上限由实例数决定。

## k5 追加测量（R25 修复后）

为区分供应余额单行与其他成本，发生器新增 `--supplier-accounts N`（1–64，默认 1）：额外创建 N−1 个各自充值的供应账户及其渠道、路由、价格与插件绑定，审计按全部账户合计核对供应账本。

- 修复前，16 个供应账户在 20 RPS 即大面积 30 秒超时；PG 等待事件以 `BuffileWrite`（临时文件写入）为主，来源为 R25：路由候选查询把插件包整行（约数 MB WASM）带入排序。修复后同配置不再溢写。
- 修复后 80 RPS、worker 并发 8：1 个账户 HTTP 79.2 RPS、窗口交集 18.1 RPS，16 个账户 HTTP 76.1 RPS、交集 3.8 RPS；结算队列积压 4300–5000，worker CPU 仅 0.05 核，结算受单任务延迟限制而非 CPU。
- worker 并发 64：1 个账户交集 18.9 RPS（队列 3320，供应余额单行串行）；16 个账户结算跟上（队列 2，交集 47.3 RPS），但准入侧出现 1125 个 503 overloaded，PG 约 3.0 核。
- 50 RPS、16 账户、worker 64 一轮有效（2000/2000，P99 754 ms）。`pg_stat_statements`：顶层语句合计约 115 s / 40 s 窗口，即每请求约 57 ms PG 时间；规范 JSON 摘要每请求约 80 次（16 个候选在 context 与准入中各算多次），含递归约 24 s；`core_execution_batch_v1` 44.4 s、`persist_core_evidence_groups_v1` 32.7 s、`core_context_v1` 14.2 s、`core_preflight_v1` 7.7 s；每次 RPC 的调用方身份重核共 28806 次。

结论：R25 消除了多渠道下的临时文件溢写，供应账户分散后结算可跟上，但当前 Core 每请求 6–7 次带完整权威重核的 PG 函数调用使 PG 每请求耗时约 40–57 ms，本机上限约 50–80 RPS。达到 3000 RPS（每请求全链路 CPU ≤ 4 ms）需要改变 Core 的数据路径：跨请求批量执行、合并 context 与准入、候选摘要按目录修订缓存、供应余额额度分片、内置适配器进程内执行。这些是架构改造，不是参数调优。分阶段建议与待裁决项见 [capacity-improvement-plan.md](capacity-improvement-plan.md)。

## 发现与修复

- R19/R20/R21（k3，已提交）：Core 锁冲突重新入批、副本 `WAITAOF` 分片、后续 attempt 发送前停止时请求可终结。
- R22（k4）：一次上游读取超过 256 个 SSE 事件时 Gateway 忽略 `consumed` 丢事件，Bedrock eventstream 解码路径在宿主内同样丢弃；已修复并各有回归用例。
- R23：SSE 每帧 helper 实例成本，未修复，交架构决策。
- R25（k5，P1）：路由候选查询把插件包整行（约数 MB WASM）带入结果与排序，8 个以上渠道时每次请求溢写临时文件；迁移 2026111226 修复，有回归用例。
- R24（k4，P0）：Core 内部连接到达 5 分钟寿命被 GOAWAY 关闭后，Gateway 的 Core 客户端继续使用已关闭连接，此后全部请求 503 core_unavailable，直到重启；已修复并有回归用例。所有 60 秒轮次都短于连接寿命，因此只有长测能暴露。

## 失败实验（已撤回）

- 结算锁冲突退避上限由 200 ms 改为 16 ms：60 RPS 窗口末积压 2747→1833、排空 23.5→14.4 s，但 P99 530→1150 ms 且积压仍线性增长，不改变稳定边界，撤回。
- Gateway 侧按 25 ms 合并上游读取再送 `stream_feed`：helper 调用数不变（宿主仍逐帧调用），400 小事件 4.9 s 无改善，撤回。

## 测量工具说明

- 80 RPS 以上的 `receipt_confirmed_acks` 失败来自发生器外部消费者：结算滞后时其 25 秒租约过期、消息被重新投递，属于负载器侧现象；资金与证据账目本身一致（`accounting` 差异 0）。
- 同名档位的运行日志 `.local/t17-ramp-*.log` 会被后一轮覆盖，结果以 `.local/capacity/bench-*/audit.json` 为准。

## 故障与可用性

本轮未在负载下注入故障。本地故障窗口由门禁覆盖：`test:durability` 7 项（含 k3 新增副本暂停后的确认检查）、`test:backup -- --quiesced` 及 `gateway-lifecycle` 进程强杀/排空用例，均在 k3 门禁通过。PG 同步副本、主节点隔离、队列晋升集合与跨故障域 SLO 仍未验证，99.99% 只是部署目标。

## 长测

第一次 60 分钟、32 RPS、目标 31（R24 修复前，构建同短 JSON 轮次）：前 5 分钟窗口交集 31.8 / 32.0 / 27.0 / 33.9 / 34.4 RPS，第 6 分钟起 Gateway 对全部请求回 503 core_unavailable（共 105642 个），判定失败；原因为 R24。

第二次（R24 首版修复）：60 分钟内无连接寿命导致的全量失败，但第 10 分钟起每次连接轮换都有 503 core_unavailable 与 30 秒超时并逐步恶化（共 13252 个 503、7750 个超时），判定失败；原因是首版修复以 `close()` 立即销毁旧连接、打断排空中的请求，且未重试服务端拒绝的流，已在 R24 处置中修正。

第三次（R24 完整修复，15 分钟、32 RPS、目标 31）：28800 个请求全部 200，无 503；第 5、9、10、12 分钟 P99 分别为 1653、17052、12389、8253 ms，交集 25.4、14.8、24.4、30.9 RPS，判定失败；与 PG 5 分钟检查点周期吻合，待在吞吐改造中定位。60 分钟长测在门槛档位重新执行。
