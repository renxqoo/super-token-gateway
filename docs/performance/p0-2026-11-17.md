## 1. 实现与测量口径

- SR-01：[bench-reference.ts](../../scripts/bench-reference.ts)、[bench-reference-lib.ts](../../scripts/bench-reference-lib.ts)、package.json `bench:reference`。输入二进制、钱包数、到达率、时长、trust quota，并支持追加授权的 `--pre-consume-multiplier`。独立 `newapi_p0_<uuid>` 库、独立缓存 Redis、1000 个客户与非无限令牌、1 个 OpenAI 渠道及 ability；上游使用同一构建的 mock。自动建表后停止、播种、重启，避免同步窗口未生效。HOST 限 loopback。结束清理进程、库与 runtime；审计和 HTTP 证据保留。
- SR-02：[benchmark-metrics.ts](../../scripts/benchmark-metrics.ts)、[bench-system.ts](../../scripts/bench-system.ts)。每 500 ms 按 PID+进程开始时间采样 CPU 高水位，保留退出进程的已见增量，回退不减 CPU、PID 复用单列；插件 helper 从 Gateway 分离，PG 客户后端与实例共享后台分开；Redis 含全部副本。旧首尾树求差可得到 −3 秒，复现及独立手算回归见证据目录。PG 按 dbid 从 postgres 扩展视图采集；开测前仅重置本轮自建库，区分顶层与嵌套调用，保留前25条语句；reset/淘汰/回退导致统计无效，不能算通过。
- 新增脚本相关单测 14 个。覆盖丢弃与尾批、quota差异、正额预扣的反例、CLI边界、日志末行、PID退出/复用/负值、多副本、PG差分/嵌套/淘汰/重置/top25；期望来自人工算例和容量契约。只读独立审查发现的副本覆盖、中断后继续启动问题已修复并复查。
- 全部正式轮固定到达、60 秒，P99≤1500 ms，计划全部发出，最多120秒排空。本项目逐 request ID 交集（HTTP ∩ PG证据/账单 ∩ 外部ACK）；new-api **没有外部ACK**，使用HTTP完成窗口及最终消费日志、逐钱包/令牌/渠道quota一致性替代，不能当作等同资金/ACK保证。原生quota每请求=2（默认费率，用户已确认），同时报告原始累计=2×请求数与折算累计/2。
- `rate` 与 `target` 明确分开；本项目 offered=target+1，参考 offered=target+10。原因是 bench.ts 在边界才发最后批并等待返回：rate=target=3000 的健康轮仍以2999.86吞吐、179992窗口完成而严格失败。没有四舍五入或吞吐容差，也没有改变现有验收函数。
- CPU 与PG窗口包含预热、正式请求及排空；分母是全部对应请求，非仅正式180000等。CPU总计包含应用、PG客户后端、插件和Redis；上游、发生器、审计/消费者装置及PG共享后台单列或排除。CPU采样是下界：两次采样之间出生并退出的进程，以及退出前最后未采到的尾段无法恢复；不能将按PID保留已采工作说成精确进程会计。PG共享后台含实例级工作，Redis也是整进程口径。

## 2. 环境与构建身份

Apple M6、12核、24GiB，Darwin uname 27.0.0（sample显示macOS27.0.1），Bun1.4.4；原生PG17.11 `127.0.0.1:55452`，Redis7.4.12。每次叠加 `.env.local` 与 `.local/native-gate.env`，显式 `QUEUE_REQUIRED_REPLICAS=1`。PG fsync/synchronous_commit/full_page_writes 全为on；max_wal_size=1GiB，checkpoint_timeout=300s，wal_compression=off，未实施A8。证据Redis AOF always/noeviction/aof-load-truncated=no，副本确认数1；准入Redis everysec。new-api Redis仅缓存，无持久化，不能与本项目证据队列耐久性等同。

本项目1 Gateway、1测量Core API、1在线worker、1供应账户、1000均匀钱包、worker并发8、发生器并发256/预热16。fixture另有空闲Core B；上游无附加延迟。new-api每连接池上限64，发生器2048/预热64。v2上游TLS，new-api上游HTTP；请求均为同一bench.ts的短Chat（`benchmark input`，max_completion_tokens32），mock默认输出`Hello, 世界 🌍`、输入10/缓存3/输出5 tokens，短JSON；同一createMockApp公开入口核得上游`synthetic`/`gpt-4o-mini`正文368/370字节（UTF-8，不含HTTP头/TLS），见[尺寸证据](evidence-p0-2026-11-17/mock-response-sizes.json)。v2客户端协议转写的正文不等于这个上游尺寸。故协议转写、模型名和TLS差异仍存在。

## 7. P1 前核对（只调查，未改产品实现或方案）

### begin 的钱包与余额锁

`core-execution.sql:372–376` 是早期定义。当前 migration manifest 的 2026111221 随后用 `core-batches.sql:309–480` 替换 `core_execution_v1`；最新候选函数来自 2026111226 的 `core-candidates-projection.sql`。两代 begin 都保留同样的资金前置条件，不能只检查早期文件就判定锁为冗余。

- `core-batches.sql:431` 的钱包 NO KEY UPDATE 与客户预扣/结算、退款、冻结、授信修改串行，之后 `:440` 拒绝 `freeze_reason` 非空，或 evidence_disputed/manual_frozen/debt/credit_reserved/credit_limit 推导出的冻结状态。客户冻结入口为 `packages/storage/src/customer-funds/index.ts:97`，授信写入见 `sql/functions.sql:294`。begin 本身不改钱包金额，但锁保护其最后一次可发送判断。
- `:433` 锁供应余额；`:440` 拒绝 `balance_atoms < reserved_atoms` 和 hold 不处于 HELD。`:442–443` 还重建估算用量、比对其 digest、manifest 与 exact_billing_price。余额锁和钱包锁先于 request、billing_hold、attempt、permit，既保持资金域锁序，也与结算/abort/recovery 的修改串行。
- begin/abort 共享这段取锁代码；abort 在 `:449` 起释放 hold、减少供应 reserved、写流水，并可能关闭请求、释放客户预扣，因此其写锁有直接写入理由。不能整体删掉共享分支的锁。
- 最新 `core_candidates_v1` 对账户、渠道等取 FOR SHARE，拒绝非 ACTIVE 账户。账户停用、风险结算、对账等写 state/revision 的入口分别在 `upstream-funds/accounts.ts:96`、`core-settlement-authentication.sql:49`、`upstream-funds/reconciliation.ts:96`。

**对方案的影响：** SR-19 / 03 §4.2 的“只对状态行取 KEY SHARE”不能直接维持现有状态栅栏。PG 17.11 源码 `src/backend/access/heap/README.tuplock:49–69` 明确：KEY SHARE 允许不改主键的 UPDATE（NO KEY UPDATE），包括以上冻结/停用操作；FOR SHARE 才与这些更新冲突。后续设计必须保留 begin 时的冻结、授信、供应敞口及 hold 校验，明确它们与状态更新/结算的线性化方式，并在去掉热点余额写锁前证明替代栅栏。可以评估独立状态栅栏或共享锁等方案，但本次不选择、不实施，也不改写 D1–D6。
