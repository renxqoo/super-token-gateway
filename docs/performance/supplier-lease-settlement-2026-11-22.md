# 供应商租约结算与混合发压复测

## 口径

短 JSON 对照沿用前一轮的报文、拓扑、8 秒采样窗口以及 PostgreSQL 持久化三项设置。单网关容量测试运行独立网关和 Mock。双网关容量测试及两轮混合长测额外运行 Redis 和 Worker。压测在同一台 macOS arm64 本机顺序执行，使用 Bun 1.4.5、PostgreSQL 17.11 和 Redis 7.4。对照构建为本轮开始前的网关产物。通过隔离库的 PostgreSQL 锁等待日志定位竞争表，并用独立诊断构建分段记录结算 SQL、应用处理与提交回执。诊断构建的吞吐不参与容量对照。

长测每个拓扑的计划固定为 1,800 秒、每秒 2,000 笔，共 360 万笔。维持 JSON、SSE、WASM、Webhook 的比例 50% / 25% / 12.5% / 12.5%。正常调度的首个时隙位于窗口起点。最后时隙允许最多 50 ms 的计时器调度容差，超出即记为计划失败。排空另计。发生器保留迟到时隙，用有界追赶和在途预算消化积压。验收要求全部时隙发出，无 HTTP、传输、协议、插件或账务错误。

## 结算变更

同一项目稳定映射到四个结算队列之一。每个队列同一时间只提交一批快速结算。各队列使用现有 16 个供应商资金格中的独立四格范围。供应商租约按账户、币种和队列建立，并持久化实际资金格与租约 ID。缺少可用资金格时沿用事务预扣的跨格搜索。跨格转入的预扣不能为当前队列建立跨格租约。租约分配仍按现有余额限制从具体资金格预留，默认预留量分摊到各队列。冷预扣由单一队列按顺序锁定当批涉及的资金格，避免同节点同时争抢最后一个有余额的格。如果跳锁可能掩盖余额，只重查未生成预扣的请求，在另一事务内按全格顺序取锁。

受理仍持久化预扣再派发。快速结算仍遵守原钱包、租约与资金格行锁约束。Outbox 写入放在同一结算事务的最后一条写语句，保留全局顺序和最终一次提交。全局发布锁因此在财务批量写入完成后才请求。

快速结算收到 PostgreSQL `55P03` 并退出事务时，对原有请求和供应商尝试重试结算一次。已建立的预扣仍受原锁和幂等约束。连接断开等提交结果可能未知的错误继续使用原故障处理路径。重试只涉及账务事务，各插件和上游调用仍执行原有一次结算流程。

## 基线锁诊断

隔离 PostgreSQL 打开 `log_lock_waits`，阈值设为 2 ms。结合单网关 `BENCH_PG_WAITS=1` 和单、双网关诊断构建，在同一请求链路分段取样。指标是应用端观测时间，包含查询处理、网络返回和提交回执。它们可比较阶段占用，不能精确反推出每一行锁在 PostgreSQL 内释放的时刻。

| 基线观测阶段                   | 单网关 P50 / P95 ms | 双网关 P50 / P95 ms |
| ------------------------------ | ------------------: | ------------------: |
| 事务开始到发出供应商租约锁查询 |       30.07 / 39.18 |       43.46 / 57.36 |
| 供应商租约锁查询往返           |         0.51 / 3.16 |         1.19 / 6.21 |
| 后续钱包、批次及资金格锁       |         0.55 / 4.63 |         2.75 / 8.14 |
| 完成剩余应用准备               |         0.37 / 0.77 |         0.59 / 1.02 |
| 批量财务与事件写入             |       19.51 / 24.95 |       25.54 / 35.67 |
| 批量写入返回后等待提交确认     |         0.48 / 1.33 |         0.92 / 3.33 |
| 供应商锁查询返回至提交确认     |       22.39 / 27.85 |       31.65 / 41.41 |

单、双网关样本分别为 195 和 193 批，中位批大小 512 和 385。PostgreSQL 单网关日志先观察到钱包租约行竞争。原批次横跨所有钱包，另一个批次往往先卡在钱包租约，供应商的共享占用则延续到写入完成。双网关还直接观察到 Outbox 全局 advisory lock 等待。只增加供应商租约数量会把这层竞争留在钱包或事件发布路径。

## 改造后锁诊断

使用同样的诊断负载档位，关闭 PostgreSQL 锁等待日志采样。单、双网关分别取到 619 和 493 批，中位批大小 28 和 120。采样每批等权，批大小变化会影响结果。

| 候选观测阶段                   | 单网关 P50 / P95 ms | 双网关 P50 / P95 ms |
| ------------------------------ | ------------------: | ------------------: |
| 事务开始到发出供应商租约锁查询 |        2.35 / 23.91 |       14.95 / 25.48 |
| 供应商租约锁查询往返           |         0.46 / 8.46 |         3.38 / 9.09 |
| 后续钱包、批次及资金格锁       |        0.91 / 15.17 |        7.94 / 26.30 |
| 批量财务写入                   |        2.52 / 22.92 |       11.08 / 20.17 |
| Outbox 写入往返                |        2.29 / 11.94 |       12.89 / 27.26 |
| 等待提交确认                   |         0.78 / 6.56 |         2.63 / 8.12 |
| 供应商锁查询返回至提交确认     |        5.95 / 45.65 |       38.16 / 64.74 |

分队列减少了每个事务接触的钱包和供应商租约，锁住一格时另一格能够完成结算。单网关的锁后中位时长下降，尾部时长上升。双网关的 Outbox 写入往返中位数与 P95 达 12.89 和 27.26 ms，包含全局发布锁等待、写入与网络往返。双网关锁查询返回至提交回执的中位数仍从 31.65 升到 38.16 ms。继续增加队列需要评估 Outbox 提交串行与小批量写入成本。

## 回归与高可用

- 锁住一个供应商租约的回归在原实现中阻塞另一个钱包，改造后另一资金格成功结算 100 客户 atoms 与 50 供应商 atoms。两笔结算落到不同资金格并符合余额总额。
- 稀疏资金回归在修复前将暂时被锁的唯一资金格误报成余额不足。修复后原请求重查成功，可完整释放预扣。
- 钱包锁超时回归通过 PostgreSQL 确认结算被钱包行锁阻塞，并在超过 5 秒锁超时后释放。修复前返回锁超时。修复后只生成一笔结算，客户和供应商分别为 100 和 50 atoms，资金守恒通过。
- 调度回归注入时钟跳跃和在途满载，核对每个时隙按顺序恰好派发一次。过了容差仍未发送的时隙继续记为失败。
- 空闲租约探测回归在两次 10 秒、2,000 RPS 双网关试验排空后锁住一个钱包行 1,600 ms。使用原判定时，600 ms 的样本仍有 55 个活跃租约，验收返回失败。启用轮询时，首次采到 42 个活跃租约，1,822.69 ms 后为零，两次均完成 20,000 笔计时请求及 200 笔预热、逐笔核对无差异。
- `bun run verify` 通过 95 项单测、35 项集成测试、构建产物、强杀预扣恢复和逻辑备份。真实隔离主备演练中，PostgreSQL 同步切换保留全部 8 笔已确认事务，推理恢复 5.51 秒，Worker 恢复 5.61 秒。Redis Sentinel 共享配额约 2.49 秒恢复，丢失 1 次已确认的配额更新，观测 RPO 101.29 ms。PITR 保留目标时间前全部已确认事务。故障演练与稳态样本分开。
- `bench:prod --stress` 注入主上游 HTTP 503，64 并发下 1,000 笔全部成功，两个网关各记录 32 次尝试切换，其他请求随熔断改走备用，切换阶段 P99 为 71.21 ms。同轮 1,000 个长 SSE 全部正常结束。全轮 431,651 个成功响应逐笔唯一结算，资金守恒且排空后不存在活跃租约。

## 复跑

```sh
bun run verify
bun run test:production
bun run bench:prod --stress
BENCH_SECONDS=8 BENCH_JSON_CONCURRENCY=1024,1536,2048,3072 bun run bench:single
BENCH_JSON_CONCURRENCY=2048,2304,2560,3456,3840 bun run bench:prod --limit
BENCH_GATEWAY_NODES=1 BENCH_SOAK_SECONDS=1800 BENCH_SOAK_RPS=2000 bun run bench:prod --mixed-soak
BENCH_GATEWAY_NODES=2 BENCH_SOAK_SECONDS=1800 BENCH_SOAK_RPS=2000 bun run bench:prod --mixed-soak
```

通过 `BENCH_DIST_DIR` 指定已归档的基线产物。基线与候选的 `gateway/main.js` SHA-256 分别为 `00f61a6503c4b7cd4e0e51c02c9bec161917aec3bed572621537e574c78199c5` 和 `2919eca59f0cae3d1c630951feeb0905e4fce1414403f9c282d674f8b41186d3`。混合发生器每分钟输出分类型错误和资源采样，结束记录应发、实发、窗口后提交、排空和计划至响应延迟。数据库逐笔核对用量、客户应收、实收、供应商支出、债务、退款、货币及插件审计。再按实际选中供应商尝试回溯资金格，逐钱包、逐资金格对实支，核对重复请求、未知预扣和资金守恒。

`bench:prod` 在排空约 600 ms 后开始检查活跃租约，报告首次读数并等待余额释放，5 秒内无法确认活跃租约已归零即判失败。5 秒窗口小于 15 秒的租约 TTL。该检查发生在计时段之后。

## 30 分钟混合稳态

单网关完整发出 3,600,000 笔并全部成功，实际吞吐 1,999.97 RPS，排空 24.80 ms。JSON、SSE、WASM、Webhook 分别完成 1,800,000、900,000、450,000、450,000 笔。最后一笔在理想窗口结束后 0.586 ms 发出，落在预设 50 ms 容差内；逾期漏发为 0。计划时点至响应 P99 为 1,107 ms，发出至响应 P99 为 456 ms，派发延迟 P99 为 694 ms。最大等待派发的计划时隙 6,762，未造成丢失。最差一分钟的计划至响应 P99 达 3,524 ms。该时段附近的 PG 日志显示密集 WAL 检查点与超过一秒的单次文件同步，无法仅凭时间相关性把全部尾延迟归因于检查点。

网关 RSS 每分钟样本范围 192.45–327.02 MiB，CPU 样本 29.1%–55.6%。客户端、Mock、Worker、Redis 的 RSS 峰值分别为 152.06、57.59、49.78、5.34 MiB。数据库核账时 10.68 GiB，计时段生成 75.67 GiB WAL。另有预热 200 笔。全部响应逐笔唯一结算，计时段客户实支 666,000,000 atoms，供应商实支 133,200,000 atoms。逐钱包、逐资金格与供应商选中尝试对账均无差异，账务守恒，排空后无在途、活跃租约与未知预扣。

第一次双网关长测发出并成功完成 3,600,000 笔，实际吞吐 1,999.97 RPS。最后一笔在理想窗口结束后 0.283 ms 发出，排空 24.75 ms，计划至响应、发出至响应和派发延迟的 P99 分别为 3,039、1,074 和 2,638 ms。最大派发积压 10,050，最差一分钟 P99 为 5,283 ms。逐笔金额、钱包、供应商资金格和守恒检查通过，金额与单网关一致。600 ms 固定探测仍读到 64 个活跃租约，原脚本以此返回失败。

此轮两个网关每分钟 RSS 样本范围分别为 182.80–346.91、183.88–302.80 MiB，CPU 范围分别为 5.9%–52.8%、2.2%–50.9%。客户端、Mock、Worker、Redis 的 RSS 峰值分别为 146.72、57.08、43.95、5.72 MiB。数据库核账时 10.57 GiB，计时段生成 75.60 GiB WAL。

启用空闲轮询后再次跑满双网关 30 分钟。应发与实发仍为 3,600,000 笔，漏发 0。第 27 分钟出现 250 次 HTTP 503 和 135 次 HTTP 200 响应协议或内容检查失败。失败率 0.01069%，成功吞吐 1,997.30 RPS，计划至响应 P99 2,510 ms，发出至响应 P99 750 ms。PostgreSQL 记录 4 次结算查询等待 `wallets` 行锁超过 5 秒，紧邻检查点同步阶段用时 9.566 秒，最长单次文件同步 3.706 秒。环境 I/O 停顿与锁超时同时出现。3,599,615 笔成功请求均有唯一正确结算，385 笔失败留作 `UNKNOWN` 预扣且未收费，清理门禁在 3,271.44 ms 内从 72 个租约归零。这一轮因错误和未知预扣未通过验收。

## 暂停时的验收状态

加入钱包锁超时重试的最终构建 `gateway/main.js` SHA-256 为 `dfe85bdc63df3456843609975601eaa7ee03c0bf73b03c2d3b183e7d2e458ee6`。`bun run verify` 通过 95 项单测、36 项集成测试、构建产物及强杀和恢复验收。`bun run test:production` 再次通过，PostgreSQL 无已确认事务丢失，推理恢复 5.49 秒，Redis Sentinel 配额恢复 2.46 秒，丢失 1 次已确认的配额更新。

最终构建的单网关长测只得到一分钟样本，随后按用户要求停跑。最终构建的两轮 30 分钟长测及同口径容量对照仍待验收。测试产物和日志已保留。
