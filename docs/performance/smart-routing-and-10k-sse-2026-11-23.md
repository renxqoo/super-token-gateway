# 智能路由故障切换与 10000 并发 SSE 压测（2026-11-23）

## 结论

**智能路由在多种上游异常下切换正确、计费精确、不产生重复请求。** **10000 并发 SSE 下网关进程本身不是瓶颈**：0 错误、0 个 429、0 个 5xx、资金 100% 守恒、排空 1 秒内归零。真正的两个上限都在网关之外，且都是部署配置项：

1. **`kern.ipc.somaxconn=128`**（macOS 默认）：冷连接突发时 accept 队列溢出，10000c 丢 3.6% 连接。Linux 提到 4096 后归零（ADR 0011 已记录，`infra/sysctl.d/` 已有配置）。
2. **PostgreSQL `max_connections=100`**：稳态吞吐封顶约 7k RPS，连接数顶到 99–101 时 PG 拒绝任何新连接（含监控查询）。

## 一、智能路由异常切换（`tests/integration/smart-routing-failover.test.ts`，8/8 pass）

| 场景                                       | 网关行为                                                                   | 计费                                                         |
| ------------------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| A 503 → B 429 → C 健康，一请求穿透两层异常 | 200，切到 C，耗时 <1.5s，每渠道各命中 1 次                                 | 1 笔 charge = 15 atoms（精确），A 连续失败 +1，B 冷却中      |
| 慢失败 A（503 延迟 2.5s，接近 3s 超时）    | 切到 B，客户端只等一个超时周期                                             | 正常结算                                                     |
| A/B 都超时（4s > 3s attempt_timeout）      | 返回 **504 `upstream_timeout`**，总耗时 2.8–7s（两个超时上限），不无限重试 | hold → **UNKNOWN**（已发出请求，上游可能已计费，不擅自退款） |
| 全部渠道 503/429/500                       | 502 `upstream_error`，每渠道**各命中 1 次**（无重试风暴）                  | 0 charge，hold RELEASED，守恒 ok                             |
| 全部渠道 429                               | **429 `upstream_rate_limited`** 准确透传                                   | 0 charge                                                     |
| 主渠道 ECONNREFUSED（端口已关）            | 切到备用 <1.5s，死渠道供应商预扣 **RELEASED**（未发出请求不计成本）        | 1 笔 charge = 15                                             |
| SSE 首帧后上游断流                         | **不切换**（防重复计费），hold → UNKNOWN，备用渠道 0 次调用                | 0 charge                                                     |
| LEAST_LATENCY：慢渠道 400ms vs 快渠道      | 前 1–2 次采样可能落到慢渠道，之后 100% 流量到快渠道（EWMA 学习）           | 12 笔全部正确                                                |
| 429 冷却                                   | 冷却窗口内该渠道 **0 次调用**，全部 11 次打到健康渠道                      | 11 笔正确                                                    |

### 切换延迟的边界

- 上游**明确返回错误**（503/429/401）：立即切换，**无额外等待**（`retry_after` 只用于路由冷却，不让当前请求 sleep）。
- 上游**超时**：最多等一个 `attempt_timeout_ms`（默认 3s，可按路由 `retry_policy` 配置），之后切换或返回 504。
- **已发出字节后**失败：不切换，hold UNKNOWN 等运维裁决。这是刻意的——避免同一次生成被两个上游各计费一次。

### 一个设计特征（非缺陷）

`LEAST_LATENCY` 是惰性学习：新渠道初始 EWMA 相同（100ms），排序由候选列表顺序决定。如果一个慢渠道一开始就排在快渠道后面且从不被采样，它永远不会被降权——但也不会收到流量。仓库没有主动探测机制。

## 二、10000 并发 SSE 压测

装置：`.local/load-10000-sse/load.ts`，`dist/` 产物（`68b0cbd`），单网关节点 + 3 个 mock + 共享 PG 17（`fsync/synchronous_commit/full_page_writes=on`），2000 个钱包轮询，10000 个预建 keep-alive 连接。

### 冷连接突发（`somaxconn=128`，模拟客户端瞬间涌入）

| 并发  | RPS   | 错误         | 错误类型            | P50 / P99        | 网关 CPU | RSS    | FD     |
| ----- | ----- | ------------ | ------------------- | ---------------- | -------- | ------ | ------ |
| 1000  | 6,939 | 0            | —                   | 128 / 212 ms     | 13%      | 566 MB | 1,596  |
| 2500  | 6,684 | 130 (0.2%)   | `Failed to connect` | 350 / 497 ms     | 18%      | 571 MB | 3,096  |
| 5000  | 6,733 | 1,078 (1.8%) | `Failed to connect` | 730 / 896 ms     | 62%      | 591 MB | 5,596  |
| 10000 | 7,689 | 2,611 (3.6%) | `Failed to connect` | 1,268 / 1,502 ms | 82%      | 740 MB | 10,595 |

无 429、无 5xx、无客户端超时。所有失败都是 TCP 建连阶段的 accept 队列溢出。

### 预热连接后稳态（排除 somaxconn 干扰）

| 并发      | RPS       | 错误  | P50 / P95 / P99          | 网关 CPU | RSS    |
| --------- | --------- | ----- | ------------------------ | -------- | ------ |
| 1000      | 6,244     | **0** | 142 / 210 / 256 ms       | 14%      | 382 MB |
| 2500      | 6,160     | **0** | 379 / 488 / 576 ms       | 34%      | 483 MB |
| 5000      | 6,494     | **0** | 759 / 979 / 997 ms       | 45%      | 578 MB |
| **10000** | **6,788** | **0** | 1,453 / 1,543 / 1,562 ms | 61%      | 660 MB |

### DB 连接池 64 → 99（`DB_MAX_CONNECTIONS`）

| 并发  | 池 64 RPS / P50  | 池 99 RPS / P50  | 变化       |
| ----- | ---------------- | ---------------- | ---------- |
| 5000  | 6,494 / 759 ms   | 7,239 / 691 ms   | +11% / −9% |
| 10000 | 6,788 / 1,453 ms | 7,330 / 1,316 ms | +8% / −9%  |

PG 后端连接数 99（顶到 `max_connections=100`）。

### 10000c 持续 30 秒（池 99）

- **215,791 请求全部成功**，0 错误，RPS 6,902，P99 1,672 ms，P999 1,688 ms，max 1,688 ms
- 网关 CPU 54%、RSS 697 MB、FD 10,827
- **资金**：231,997 charges = settled = unique，**零重复**，全部 SETTLED，守恒审计 `ok=true`
- **排空**：停发后 1,002 ms 内 `in_flight = 0`、活动租约 = 0
- **PG**：`max_connections=100` 被打满，压测中 `psql` 采样被拒：`FATAL: sorry, too many clients already`

### 瓶颈分析

RPS 从 1000c 起就停在 6–7k，而 P50 与并发数**线性成正比**（1000c 142ms → 10000c 1453ms），是 Little's Law 下吞吐封顶的典型曲线。网关 CPU 始终 < 85%，mock < 5%，说明瓶颈不在计算：

1. **PG 连接数**是硬上限。每请求 ≥2 次 PG 事务（预扣 + 结算），单次约 9–14 ms，64 连接 ≈ 6.5k tps，99 连接 ≈ 7.3k tps——与实测吻合。提到 99 后 RPS 只涨 8%，因为 PG 侧 `max_connections=100` 已顶到。
2. **WAL 写入** 7.4 KB/req × 7k ≈ 52 MB/s，强耐久（`synchronous_commit=on`）下每事务一次 fsync。这是资金正确性的代价，不应为吞吐放宽。
3. **网关单进程**在 10000 并发 SSE 下稳定：RSS 700 MB、FD 10.8k、无内存泄漏迹象、排空干净。

### 运维含义

- **生产必须**：`somaxconn ≥ 4096`（`infra/sysctl.d/` 已提供）、PG 前置 PgBouncer/连接池或 `max_connections ≥ 300`、发生器/网关/DB 分机部署（容量契约已注明 6000+ 并发须多机）。
- 单机 12 核同时跑发生器 + 网关 + mock + PG + Redis，上述数字是**下界**；分机后 PG 连接上限解除，网关 CPU 余量（< 85%）可支撑更高吞吐。
- 10000 并发 SSE 在当前本机配置下的**安全运行点**是 ~7k RPS：超出后请求不会失败，而是排队（P50 线性增长），直到客户端超时。
