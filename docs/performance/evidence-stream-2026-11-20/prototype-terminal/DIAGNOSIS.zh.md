丢弃集中在 10.815 至 30.953 秒。发生丢弃的毫秒末，发生器平均有 2046.07 笔等待 HTTP，其中 1791.42 笔已调用 fetch 且尚未进入入口。入口内平均 254.65 笔，其中 127.41 笔等终态签名后的资金和备库见证，58.58 笔等第一份最终计量签名的持久见证，42.01 笔正从流 feed 进入首份签证，其余分布在资金额度、握手和 HTTP 回复阶段。另有 79.90 笔已结算待消费者外部 ACK。客户端在收到有效 HTTP 与 DONE 后释放在途名额，外部 ACK 队列主要影响联合完成时钟。外部消费者仍与入口共享 PG 和 CPU。

按入口收到请求时刻分组，20–30 秒的首份签名到主备见证平均为 15.08ms，终态签名到资金见证为 29.54ms，已结算到外部 ACK 为 49.78ms。40–60 秒分别为 9.41、13.83、11.43ms。相同两时段中，feed 开始到首签的平均耗时为 21.44 和 25.61ms。20–30 秒三个宿主的该项分别为 21.26、21.73、21.32ms，联合完成 9115、9119、9110 笔。

全窗内 Gateway 进程树消耗 403.39 CPU 秒，含三个同进程 JS 宿主线程。其余为主库 67.19、备库 17.02、消费者 15.79、负载器 21.05、上游 11.67 CPU 秒。采样器保留每个 PID 首末累计值，未保存逐时间片 CPU 和线程级 CPU。30.029 秒附近出现一个新的主库后端，1.5 秒后退出。记录没有该连接 SQL、历史执行计划或 PostgreSQL 等待事件，无法指认统计信息更新或某次扫描。扩展发生器的十秒配对实验已验证连接确实从 256 增至 512，各自零丢弃，联合吞吐 2869.1 与 2863.2/s，P99 为 520.824 与 585.900ms。

候选只减少终态资金写入客户端与主库之间的通信。此前 6377 个终态批平均各 27.73 笔，各批先 BEGIN，依次调用资金过程、插入末签名、插入所有 outbox，最后 COMMIT。候选从客户端发出一次 SQL，服务端函数按原顺序检查相同数据行，保持原有主库事务和 remote_apply，随后照常到指定备库见证、查账。每批省去四次客户端往返；从终态签发到见证的实际收益和容量须另测。逐请求的第一次签名在正常流式输出前持久化并见证，未与终态合并。该变更仅适用于隔离原型，正式 Core 的身份与资金协议仍走正式门禁。
