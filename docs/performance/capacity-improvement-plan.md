# 3000 RPS 容量改进建议

2026-11-16，基于提交 9a8db8d（T17 k5）的实测。门槛来自 [capacity-contract.md](capacity-contract.md)：本机均匀 1000 钱包短 JSON 完整链路稳定负载不低于 3000 RPS，强耐久、精确结算与逐请求交集不变。实测细节见 [capacity-2026-11-16.md](capacity-2026-11-16.md)。

本文是建议，未实施。第 2、4 阶段会改变已确定的安全设计，需用户裁决后才能开工；第 1、3、5、6 阶段不改变安全模型，可直接排期。

## 现状与差距

| 指标                         | 实测                                                                                         |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| T17 首测最大稳定负载         | 35 RPS                                                                                       |
| R22–R25 修复后               | 约 50–80 RPS；16 供应账户、worker 并发 64 时 50 RPS 一轮有效（P99 754 ms）                   |
| 每请求 CPU（80 RPS，1 账户） | PG 19.6 ms、插件 helper 10.4 ms、Gateway 7.1 ms、Core API 3.0 ms、Redis 1.1 ms，合计约 41 ms |
| 3000 RPS 预算（12 核）       | 每请求全链路不超过约 4 ms                                                                    |

差距约 10 倍以上，而且分布在每个进程上；仅优化 PG，即使降为 0，其余进程也把上限压在约 400 RPS。历史单体在同机约 2000–3300 RPS，因为它每个阶段只做一次批量 PG 调用，没有内部签名 RPC、逐调用身份重核与插件沙箱。

### 主要成本来源

1. Core 每请求 6–7 次 PG 函数调用（context、准入批、quota、preflight、quota close、证据持久化、结算），每次都完整重核调用方身份（每请求约 14 次身份函数调用）。
2. 路由候选在 context 与准入中各重算一次，每个候选在 SQL 里递归计算规范 JSON 摘要；16 个渠道时每请求约 80 次摘要，16 账户 50 RPS 下含递归约 24 s / 40 s 窗口。
3. 供应账户余额单行：准入预扣、begin 与结算都锁同一行；1 个账户时结算交集只有约 19 RPS，worker 并发提高到 64 也无改善。
4. 插件 helper 每次调用新建 Wasm 实例；JSON 请求每个钩子最多 5 轮，SSE 每帧至少一次调用（R23）。
5. 长测中第 5、9–12 分钟 P99 尖峰（最高约 17 s），与 PG 5 分钟检查点周期吻合，尚未定位。

## 每请求预算

| 进程         | 现状 ms | 目标 ms |
| ------------ | ------- | ------- |
| PostgreSQL   | 19.6    | ≤ 1.5   |
| 插件 helper  | 10.4    | ≤ 1.0   |
| Gateway      | 7.1     | ≤ 1.0   |
| Core API     | 3.0     | ≤ 0.5   |
| Redis 与其他 | 1.1     | ≤ 0.3   |

## 分阶段建议

每个阶段先更新设计文档，再改代码；完成后按同一发生器配置复测逐进程 CPU、`pg_stat_statements` 与交集吞吐，未达阶段目标时先定位再进入下一阶段。

### 阶段 1：合并 Core 数据路径（不改安全模型）

- 合并 context 与首次准入：同一次 RPC、同一事务内计算候选并准入，候选只算一次；`execution_contexts` 只保存后续 attempt 需要的快照。
- quota、preflight 并入准入批，quota close 并入完成或结算批，每请求 PG 调用从 6–7 次降到 2–3 次。
- 证据持久化在批内按账户排序取锁，消除约 3 倍的锁冲突重试调用。
- 目标：PG 每请求 ≤ 8 ms，本机 ≥ 300 RPS。

### 阶段 2：摘要与身份校验去重（需裁决）

- 规范 JSON：先换成等价的更快 SQL 实现（ASCII 键走按字节排序，含增补平面字符的键回退原实现），微基准约快 1.8 倍，结果逐字节一致，不需裁决。
- 候选摘要按目录修订号缓存：目录行修订号不变时复用摘要，修订时失效。**需裁决**：当前设计要求每次准入从目录行重算。
- 调用方身份按会话缓存：会话证书与吊销修订号不变时不重核，吊销时同步失效。**需裁决**：当前设计要求每次 RPC 在资金事务内重核。
- 目标：PG 每请求 ≤ 3 ms。

### 阶段 3：供应余额额度分片（不改安全模型）

- 每个供应账户的可用余额预先划拨到 N 个额度单元；准入按请求哈希选单元预扣，单元不足时从账户主行补额或换单元，结算只锁所在单元。
- 账本不变量改为“账户余额 = 主行 + 各单元之和”，对账、充值、退款与升级迁移同步调整，需要新的资金集成测试。
- 目标：1 个供应账户下结算不再积压，交集吞吐等于 HTTP 吞吐。

### 阶段 4：插件执行成本（需裁决）

- 内置可信适配器在进程内执行，沿用同一 `runGuest` 契约，第三方插件仍走 Wasm 沙箱。**需裁决**：当前设计要求全部适配器在隔离 helper 中执行。
- 不改信任边界的替代：helper 复用实例并在调用间重置，需证明无跨请求状态泄漏。
- SSE 多帧批 ABI（R23）：一次调用处理多帧，需改插件 ABI 与全部适配包。
- 目标：helper 每请求 ≤ 1 ms，SSE 每帧成本下降一个数量级。

### 阶段 5：Gateway 与 Core 进程 CPU

- 阶段 1–4 完成后用采样分析器定位：内部 RPC 签名与验签、请求与响应的 schema 校验、JSON 序列化。
- 目标：Gateway ≤ 1 ms、Core ≤ 0.5 ms。

### 阶段 6：耐久与长测

- 定位检查点尖峰：调整 `checkpoint_timeout`、`max_wal_size`、`checkpoint_completion_target` 并复测；不关闭 fsync、synchronous_commit 或 full_page_writes。
- 达到门槛档位后执行同配置连续两轮通过与 60 分钟长测。

## 风险与退出条件

- 即使六个阶段全部实施，在 12 核上保持全部耐久与校验仍可能达不到 3000 RPS；每个阶段的复测结果决定是否继续。
- 阶段 1 与阶段 3 改动资金事务结构，必须保持现有资金、授信、权限与升级集成用例全部通过，并补充并发与故障用例。
- 若用户不接受阶段 2、4 的裁决项，预计上限显著低于 3000 RPS，届时应重新确定本机门槛。

## 待用户裁决

1. 调用方身份是否允许按会话缓存，吊销同步失效。
2. 候选摘要是否允许按目录修订号缓存。
3. 内置适配器是否允许进程内执行（第三方仍沙箱）。
4. 若以上不接受，是否为 v2 在本机设定低于 3000 RPS 的门槛，先完成 T19 与 T18。
