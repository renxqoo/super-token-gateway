# 单机 3000 RPS 的短 Chat 执行预算

> 历史容量分析。本文中的 Gateway 和 Core 指 2026-11-19 的实现。现行部署与请求链路见[系统架构](../../architecture.md)。

**联合原型在同一配置下连续两轮完成 3007.60 和 3007.50 笔/秒。** 两轮每笔均实际经过插件、上游 HTTP、签名事件、精确双侧账务、物理备库确认和独立消费者 ACK。现有发布物连续两轮达标的档位为 175 RPS。联合原型验证了正常短 Chat 的架构可行性，产品接入与一小时验收仍待完成。

本机为 12 核 Apple M6。要持续完成每秒 3000 笔请求，每笔请求平均最多使用 4 毫秒全机 CPU 时间。PG 主备、Gateway、Core、插件、上游替身、消费者和同机发生器都在这个预算内。端到端 P99 另有 1500 毫秒的墙钟延迟预算。公开验收逐请求核对响应正文、两侧精确账务和两份外部事件 ACK，要求同配置连续两个 60 秒窗口通过，随后连续一小时逐分钟通过。[容量契约](capacity-contract.md)

## 现有公开链路

每轮均为 1000 个均匀钱包、4 个 Gateway、2 个 Core、按认证项目固定 Core 和指定物理备库。175 档是此前连续通过的两个窗口。300 档是本次相邻独立夹具的对照，每秒固定发出 301 笔，持续 60 秒。候选只把发权和成功终态的批收集时间从 2 毫秒改为 32 毫秒。

| -------------------- | -----------: | ------------: | -------------------: | ------------------------------: | -------------------: |
| 175 档第一轮，2 毫秒 |       175.67 |        584.26 |                20.36 |                            7.34 |               45,007 |
| 175 档第二轮，2 毫秒 |       175.52 |        694.81 |                19.61 |                            7.18 |               45,150 |
| 300 档，2 毫秒       |       300.17 |       1725.70 |                18.45 |                            6.27 |               43,877 |
| 300 档，32 毫秒      |       299.83 |       1679.61 |                15.41 |                            6.02 |               43,631 |

CPU 是进程采样下界，分母为包括预热的已准入请求。主库列仅计测试库后端。按 175 档的单位成本线性外推，3000 RPS 单是主库后端就需要约 59～61 个满载核。Gateway 与 Core API 两项也已超过全机 4 毫秒/笔的预算。原路径顶层 SQL 按相同单位成本一小时约生成 486～488 GB WAL，磁盘驻留量还取决于回收、归档、表和索引增长及备库。[175 档原始审计](evidence-core-admission-2026-11-19/rounds.json)

两轮 300 档各有 18,060 个有效 HTTP 响应，窗口内完整交集分别为 18,010 和 17,990 笔。两个窗口结束后分别用 157 和 207 毫秒排空，双方预扣归零。发权每批从 1.81 增至 2.16 笔，终态每批从 2.00 增至 2.69 笔。扩大窗口使主库 CPU 降低 16.5%，单位 WAL 降低 0.56%。HTTP P99 两轮均超标，运行时保留原来的 2 毫秒。

## 执行组件的成本

取对应 175 档产物的内置 OpenAI Chat 插件和发行版 worker，先校验插件包签名、worker 摘要和能力准入，再在 4 个 worker、8 路并发下执行短请求。每笔从原始请求得到上游请求体，将上游样本转换为公开响应，校验正文和用量，签发并逐一验证两份 Ed25519 用量证据。每次 prepare 实际调用 worker 两次，每次 response 调用三次。热身后 5.004 秒完成 25,225 笔，进程和 worker 线程合计使用约 0.367 CPU 毫秒/笔。此测量使用预先取得的上游响应，范围限于插件、证据密码学和驱动内断言。四个跨进程 RPC、上游网络、资金及 ACK 的成本仍须在完整入口测量。

## 紧凑资金原型

隔离 PG 17.11 主库及指定物理备库均开启 fsync 和全页写入。每笔先将有身份的命令、许可及客户和供应两笔正额预扣同步提交，指定备库见证后才进入第二个事务。第二个事务结清双方、写四条平衡分录和两个可领取事件。独立进程经 HTTP 领取事件，检查用量与金额，实际发送 ACK，再记录收到成功回复的时间。计时终点取备库精确终态与两份外部 ACK 的较晚者。该装置使用 1000 个钱包、16 个供应资金单元和两个写者，不包含面向客户的推理请求。

第一轮固定到达 3000 RPS，在 60 秒内完成 2243.75 RPS。18 万个到达中 45,279 个因有界队列已满而被拒，P99 为 10,242.41 毫秒。对原查询加逐批计时和实际执行计划后，在历史约 2.66 万笔且首次自动统计尚未完成时，一批 128 个身份的终态见证计算分录聚合约 340 万次，耗时 3.75 秒。改为由本批身份驱动的相关主键查找，保留同一组备库事实检查。相同输入 18 万笔全数完成，峰值在途从 8192 降到 402，P99 为 100.34 毫秒。最后 26 笔越过窗口，窗口实绩为 2999.57 RPS。此对照的两个版本使用同一组合成费率。

之后将费率改为当前短 Chat 夹具的客户每请求 100、供应按非缓存输入/缓存输入/输出分别计 3/1/7。正常用量 7/3/5 产生客户 100、供应 59，另用 1/9/2 核对客户 100、供应 26。首次按 3010 RPS 投喂 60 秒，窗口内完成 180,572 笔，即 3009.53 RPS，P99 为 103.45 毫秒。排空后 180,600 笔、722,400 条分录和 361,200 个 ACK 全数吻合。主库进程树约 0.353 CPU 毫秒/笔，备库约 0.039。该轮按集群 WAL 位置差计量约 4222 字节/笔，上表公开入口按顶层 SQL 统计，两种计量边界不同。重放、冲突身份和并发争抢最后一笔余额另有校验。

公开版本的备库核对读取签名回执、许可和资金终态，查询结构与原型不同。公开 A/B 采集了主库执行统计，缺少备库执行计划。2 毫秒公开轮中，主库发权和终态入口共生成约 742 MB WAL，占已计量顶层 SQL 的 93.5%。原型的执行计划只解释原型中查实的退化，公开版本的 P99 仍以公开测量为准。

## 带 HTTP 和真实签名的联合原型

独立发生器向回环 HTTP 入口发送标准短 Chat 正文。入口取得物理备库见证的发权后，通过发行版插件准备请求，向仓库的 HTTP 上游替身发送一次，再用真实响应生成公开正文和两份 Ed25519 用量事件。两份签名原文、公钥、终态、分录及可交付事件同时提交。备库核对原文和终态后才返回 HTTP 成功。独立消费者按固定公钥重验每份签名和用量，提交 ACK 并记录收到回复的时间。另按四份独立身份记录核对窗口内完成数和先后顺序。

| 投放速率与窗口                  |    投喂 | 有效 HTTP | 窗口内完整 | 完整 RPS | HTTP P99 毫秒 | 直至双 ACK 等条件齐备的 P99 毫秒 |
| ------------------------------- | ------: | --------: | ---------: | -------: | ------------: | -------------------------------: |
| 1001/s，60 秒                   |  60,060 |    60,060 |     60,039 |  1000.65 |         39.79 |                            48.29 |
| 3001/s，60 秒，首轮             | 180,060 |   179,747 |    179,572 |  2992.87 |           717 |                          6254.56 |
| 3001/s，60 秒，按键领取         | 180,060 |   180,060 |    179,913 |  2998.55 |        218.78 |                           273.22 |
| 3010/s，60 秒，按键领取，第一轮 | 180,600 |   180,600 |    180,456 |  3007.60 |        318.85 |                           372.82 |
| 3010/s，60 秒，按键领取，第二轮 | 180,600 |   180,600 |    180,450 |  3007.50 |        463.83 |                           519.70 |

首个 3001 档有 313 笔在发生器达到在途上限时拒绝。其余请求各有一次上游发送，全部成功结算并取得两份外部 ACK。HTTP 延迟和完整交集延迟分别计量，拒绝仍计入全部投喂。

21 秒的定位轮显示，领取 512 个事件时，数据库分别扫描了 35,950 行终态或 54,194 行许可。在第 15～20 秒的小窗内，领取操作的 P95 为 129 毫秒，独立验签为 15 毫秒。候选将领取后的证据、终态和许可改为按本页身份逐项读取。相同投喂下所有 180,060 笔都成功，完整 P99 降至 273.22 毫秒。最后 147 笔越过窗口，严格的每秒 3000 笔门槛仍未通过。

随后提高固定到达率到每秒 3010 笔，完整目标仍为 3000 RPS，时间窗仍为 60 秒。同一代码、配置与独立初始主备连续两轮通过。每轮 180,600 笔都返回有效 HTTP，各产生一次上游发送、四条分录和两次外部事件 ACK，主备核对与钱包、供应资金核对均通过。两轮最长完整延迟分别为 426.87 和 571.76 毫秒。排空分别用时 74 和 72 毫秒，子进程正常退出，临时进程、目录、端口和定时器清空。按完整进程树采样约 1.05 CPU 毫秒/笔，按集群 WAL 位置差分别为 6304 和 6324 字节/笔。

该入口使用固定模型和单一客户费率，按测试序号分配已预存资金的钱包，以每侧 100 个原子单位做固定预扣。真实产品的租户鉴权、mTLS 与命令签名、动态路由、按请求上限计算预扣、Redis 配额、故障接管、未明发送状态与存量账迁移没有接入。所有结果只适用于该非流式短 Chat 正路径。[可运行的联合原型](evidence-execution-budget-2026-11-19/joint-source-b.tar.gz) · [两轮审计与文件摘要](evidence-execution-budget-2026-11-19/rounds.json)

## 接入现有产品的边界

优先把现有已认证的短 Chat 准入和成功终态接入紧凑批写，再测每笔 CPU。保留已通过实测的插件宿主与签名事实格式。资金见证和事件领取两处都要验证初始化、统计更新前与已有大表三种执行计划，使每批触及的历史数据量受本批身份数约束。

1. **先替换资金写入的表示。** 首次切入对象是无资源依赖、首个尝试、定价和路由均已确定的非流式 Chat。Core 把已校验的命令身份、请求体摘要、报价版本、两侧金额、配额证明和所有者版本交给有界批写者。发权事务在同一权威余额上冻结客户及供应额度并持久化一次性发送许可。取得主库提交和指定备库见证后，原执行者才能向上游发送。相同命令重放只能查回执。
2. **将两份事件、双侧分录和交付身份一次落账。** 终态按 attempt 校验原执行身份和两份签名事件，使用许可冻结的价格版本计算实际金额，再原子释放预扣、写入精确分录、关单并生成待领事件。指定备库见证成功才返回公开成功。提交结果未知时将同一签名组交现有 AOF 恢复路径处理。无法判定物理发送状态时保留两侧资金责任。领取和 ACK 继续由独立消费者完成。
3. **减少每笔跨进程往返。** 当前成功路径依次完成上下文、合并准入、同步终态和渠道健康观测四个签名 RPC，Gateway 另签两份用量证据。保留 Gateway 的签名私钥及 mTLS 会话绑定，在同步终态消息中携带同一 attempt 的幂等健康观测可减少一次往返。新协议必须核对 channel、attempt 归属和延迟，重放不得重复更新健康指标，发送失败、取消与旧版本继续走已有观测路径。路由票需要维持主体、请求摘要、失效和撤销检查。
4. **按可恢复的所有权交接迁移。** 存量钱包、充值、退款、未决预扣、外部交付游标和后台纠正需要读写同一笔权威资金。先对真实准入/结算输入离线比对两种表示，再在所有者交接事务中核对余额、幂等命令、事件身份和版本，使旧版本的写入失效后允许新写者接管。验证跨 Core 接管、混合批次中单项拒绝、已提交丢回复、备库暂停或晋升、迟到证据和未 ACK 重领。新账产生后的回退需要反向交接。SSE、重试、异步资源和管理查询分别按现有契约验收。

上线门槛仍由真实 Gateway 入口执行。先核对 300 档的吞吐和 P99，再在同一发布物上验证 3000 档两轮及一小时。长测空间应基于实际迁移后的主备数据、索引、WAL 留存和审计增长重新测量。此前按现有模型预检需要 872.88 GB、可用 240.44 GB。

## 复核和重跑

从仓库根目录运行。使用与清单匹配的 Bun 1.4.4、已构建插件产物和仓库的 PG 17 工具。从归档中解开独立实验源码即可创建新的本机临时数据库，新的输出前缀保留原始结果。

```sh
evidence=docs/performance/evidence-execution-budget-2026-11-19
probe_dir=$(mktemp -d)
tar -xzf "$evidence/funding-strict-a.tar.gz" -C "$probe_dir"
.local/toolchain/bun-1.4.4/bun --no-env-file "$probe_dir/funding-strict-a/probe.mjs" 3010 60 "$probe_dir/funding-strict-a/replay.json"
python3 "$probe_dir/funding-strict-a/verify.py" "$probe_dir/funding-strict-a/replay.json"
```

联合原型使用同一个仓库 checkout。前两条命令解开最终候选并重跑，后两条命令从已经归档的四份身份记录独立复算第一轮 3010 档。

```sh
tar -xzf "$evidence/joint-source-b.tar.gz" -C "$probe_dir"
.local/toolchain/bun-1.4.4/bun --no-env-file "$probe_dir/joint-source-b/public.mjs" 3010 60 "$probe_dir/joint-replay"
tar -xzf "$evidence/joint-strict-3010-b1.tar.gz" -C "$probe_dir"
python3 "$probe_dir/joint-strict-3010-b1/recompute.py" "$probe_dir/joint-strict-3010-b1/strict-3010-b1"
```

原始公开版对照的两个目录各保存 HTTP 和 ACK 身份日志。资金原型的归档另含逐身份时间、独立验证脚本及查询计划。联合原型按运行版本归档源码和已签测试插件，按轮次归档 HTTP、上游、ACK、资金见证时钟与独立重算。交付前校验了 15 个归档的 146 个成员，使用解压后的源码重跑 34 笔，逐笔取得有效 HTTP、唯一上游发送、资金匹配和 68 次事件 ACK。计量边界、文件名及 SHA-256 见[实验清单](evidence-execution-budget-2026-11-19/rounds.json)。
