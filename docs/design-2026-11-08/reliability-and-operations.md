# 可靠性、运维与容量

本文件描述目标保证和运行责任，未运行真实集群/供应商故障测试。参考图见 [diagrams.md](diagrams.md)。

## 1. 故障收口矩阵

| 窗口 | 已有权威事实 | 处理 | 禁止行为 |
| --- | --- | --- | --- |
| 授权前失败 | 无金融提交 | 同业务键重试 | 直接发送上游 |
| Admit 事务明确回滚 | 无预扣/许可 | 可重新提交原意图 | 只凭 Redis 许可发送 |
| Admit COMMIT 响应丢失 | 可能已预留并授予一次许可 | 查旧 command/order，返回 OBSERVE_ONLY | 复制可发送回执/换新键盲重发 |
| 新许可确认后，发送前进程死亡 | 用户预留+供应商额度+可能执行事实 | 进入恢复/未知政策 | 按 TTL 当未执行退款并释放供应商额度 |
| 已执行而最终 usage 未到 | 单次调用与 Kmax 在 | 查询/发票关联，客户按 SLA 保留或永久免收 | 编造 usage、自动透明重试 |
| 已收到最终 usage，PG 不可用 | 预留/调用仍在，原件可能只在内存 | 有界保存重试；失败异常结束，保留未知费用 | 正常 DONE 或内存任务假装耐久 |
| SealEvidence 成功后执行节点死亡 | evidence+READY+工作项 | Worker 完成本地结算 | 再调用供应商 |
| Capture 成功后 Worker 死亡 | 唯一 capture/journal/终态 | 重投读取原回执 | 再次累计收费 |
| NO_CHARGE 后晚到结果 | 原始收费终态免收 | 成本证据照存，用户不再原始收费 | 复活订单或归还仍未知 Kmax |
| 原始证据身份冲突 | 两个来源引用/摘要 | REVIEW/对账 | 覆盖原 raw_usage |
| Redis 丢失 | PG 全部金融事实仍在 | 路由/限流保守重建 | 从旧缓存重建可花本金 |
| grant 已发未确认 | 发行者 issued 已占本金 | 按同 grantId 查询/重投 | 同额另发到第二组 |
| return 响应丢失 | 源已扣 free，发行者可能已返还 | 按 returnId 查询 | 第二次加回本金 |
| PG 组不可用 | 该组既有提交等待恢复 | 停该组新许可，已有流尽力收尾 | 将账户映射到空新库继续消费 |
| provider cost 超上界 | 真实外部成本仍可记录 | overrun/差异，停相关新调用 | 丢掉真实费用或透支用户 |
| 外部退款响应未知 | 用户现金预留与 payout order 在 | 同退款身份查询 | 重复支付或提前解冻 |

## 2. 耐久任务与重放

每资金组有本地 financial_work，收据与 CAPTURE 工作同事务写入。Worker 用有界批次、SKIP LOCKED、owner/token/until 和 revision 领取，网络操作都在领取事务之外。没有外部消息系统可用时仍能结算。

任务租约到期只允许重复本地幂等命令或重复查询，不授予再次推理/支付的权利。可重试基础设施错误退避；金额冲突、非法证据和不可恢复配置进 PARKED/REVIEW，保留资金与诊断，不无限重试。

批量 Capture 可以按组减少 commit/重复锁成本，但必须预先按全序拿齐本批账户/订单锁，不能在一个事务里无序循环多个单笔命令。整批毒项回滚后隔离单项，不能丢掉其余已领取任务；认领可续期或安全归还。

NOTIFY 仅为合并唤醒，断线不丢任务。轮询频率/批大小由 backlog 与资源预算调优，不能每个空 Worker 毫秒级全表扫描。任务 DONE 不是唯一财务结果，重复任务始终回看订单/命令回执。

## 3. 未知费用的自动处理

分别统计：用户预扣金额、供应商 HELD、应计成本、最坏准备、未收标价。unknown 出现后在固定 policy 下执行有界查询；有合格最终证据则按截止规则结算，查不到则到期进入 NO_CHARGE 或审批，绝不无期限只写“人工处理”。

默认计费证据政策建议 FINAL_ONLY。没有最终证据不向用户伪称精确扣款；若某产品允许估算收费，它必须有独立价格/政策版本、适用归属和清晰展示，不能在断流后临时开启。

免收用户后，原始请求不再重试；晚到费用由平台承担。供应商 allowance 保留，必要时按审计规则转最坏成本准备而不返 free。这可以在无法证明原进程绝对不会再发送时保护用户：原调用仍由预留的供应商预算承担，不能再把费用转回已免收客户。

取消率、未知率和免收率异常的凭证/账户/供应商需要准入限制与调查。否则客户可以利用反复中断制造大量平台承担费用，即使单笔资金规则正确也会耗尽风险预算。

算例：10k/s、未知率 0.1%=10 条/秒，平均 300 秒收口则约 3,000 条并发未知；完全不能恢复则每天 86.4 万条。未知队列、恢复 API 配额、平台预算和人工例外必须共同定容。

## 4. PostgreSQL 耐久性与安全切主

资金组要求 fsync/WAL 刷盘、正确的 synchronous_standby_names 与 synchronous_commit 策略。仅设置 synchronous_commit=on 且无同步候选，不能保证副本耐久确认。[O1]

HA 控制器必须维护安全候选集合、仲裁与旧主隔离。不能配置“任一副本确认”后任意晋升另一落后副本。同步要求不可满足时停止新许可，不默默降为异步资金提交。

业务 RPO 分层：约定单节点/故障域故障下已确认资金不丢；跨区域毁损依赖独立复制/备份目标，单独声明 RPO/RTO。供应商执行不属于 PG 事务，即使库未丢数据也可能仍有 UNKNOWN。

备份包含基础快照、连续 WAL、配置/加密密钥恢复资料和可取回的证据；副本不是备份。恢复/PITR 后先冻结新许可，核对恢复点之后的支付、上游、已完成响应与独立审计，再开放。不能因数据库能启动就视作资金已恢复。

恢复还必须核对 grant/return 与目的 group epoch；不能只见到历史 grant 就重建一份可花本金。未来移动付款聚合时，先冻结该聚合新许可，封存/移交在途义务与一致水位，隔离旧写入者后才启新 placementEpoch；无法确认隔离就保持暂停。版本号本身不能阻止旧库继续写。

## 5. 容量模型

```text
在途订单 N = 到达率 λ × 平均持续 W
10,000/s × 30s = 300,000 个在途订单
backlog 斜率 = 最终证据产生率 - 有效收费完成率
追平时间 = backlog / (恢复处理率 - 持续新到达率)
```

执行节点需要客户端和上游资源；HTTP/2 可以复用连接，但每条流仍有内存、上下文与协议状态。每流额外 64 KiB、30 万流约 19.7 GB 十进制内存，尚未包含 TLS/socket/运行时。20 KiB 平均客户输出、10k/s 约 205 MB/s，仅是输出数据，不含上游接收/协议开销。以上均为算例。

资金正常路径有同步授权、证据、异步收费及任务认领等提交；再加 journal/effects/slices、身份/限额、预算和出箱。批量可以摊薄 commit，不能抹去行、索引、触发器和 WAL。10k/s 全天 8.64 亿订单需要真实日均负载、单行大小、复制量与冷热留存设计，不是“PG 几千 TPS 舒适区”。

每物理资金组先用完整命令和真实索引/约束测合格吞吐，再按总峰值/单组能力和故障余量决定组数。必须另测单个大付款账户、单个热门产品、共享 provider account 和碎片化资金，不仅是随机用户均匀压测。

## 6. 资源许可与降载

分别设置入口短队列、账户公平额度、上游并发、短 DB 操作、证据保存、后台收费/恢复、日志与对象存储预算。上游等待不占 DB 许可或连接，后台统计不能抢光收据连接。

入口队列上限从可接受排队时长×测得服务率推导，超出明确拒绝，不用分钟级排队掩盖持续过载。每请求拥有剩余 deadline，所有层重试共用同一预算。

降载触发包含：许可队列、PG 锁/池等待、同步复制不可用、最老 READY、backlog 增长、最老 UNKNOWN/未知金额、allowance 低水位、证据保存失败。优先保护已产生费用的 SealEvidence、Capture 和恢复，限制新调用。

Redis 故障时使用保守的预先分配实例配额或拒绝，不能每个副本独享全局限额。金融授权仍使用 PG 真实资金，不因限流缓存故障开信用后门。

### 6.1 Bun 进程的隔离与观测

执行、资金 API、金融后台与控制 API 使用独立进程/容器。执行进程按 CPU、事件循环延迟、在途流、RSS/堆/外部缓冲、socket 与网络流量共同扩展；不只看 RPS 或 CPU。监测 timer 调度延迟与 eventLoopUtilization 等接口时，先验证锁定 Bun 版本的实现，记录指标可用性，不能假设 Node.js 的探针全部等价。

重型 tokenizer、大对象 JSON、压缩和日志编码有输入上限与 CPU 预算。若测得阻塞，放到有界独立计算进程；Bun Worker API 的终止等能力仍须按锁定版本验证，首版不依赖它保证金融生命周期。计算子任务不授予发送权或写资金表。

每进程的许可、排队、连接池、fetch 上游在途、终态窗口及日志队列均有界。计算所有副本的池上限总和，滚动发布临时副本也纳入 PG/供应商连接预算。未处理 Promise 拒绝、不可恢复异常或进程内存逼近限制时，停止新许可并有界收尾/退出，金融恢复仍以 PG 记录为准。部署和兼容矩阵详见 [Bun 运行规范](bun-runtime.md)。

## 7. 日常对账

| 层次 | 内容 |
| --- | --- |
| 提交期 | journal 平衡、effect 连续、账户非负、slices 开闭与本命令影响匹配 |
| 增量 | 以 command/账户水位检查 posted、reserved、来源、capture 和 allowance 转移 |
| 周期完整 | 按一致快照重建余额与 active slices，覆盖所有分区/账户，不只头一页 |
| 外部 | 支付/退款、供应商原始报告、账单、商户/银行已结算资产与内部义务核对 |

差异形成 reconciliation case，经证据/审批执行新 adjustment，不直接 SET balance。只读副本有延迟时必须固定可解释水位，不能将不同时间的数据比较成假差异。

用户现金可用不等于商户银行已到账。外部退款/提现执行前还要满足原支付可退额、已到账/可支付流动性、退款报价及双币累计上限。支付应收、已结算现金、客户负债与供应商责任分别核对，不能凭一个成功回调宣称全系统备付金充足。

## 8. 安全与数据

凭证在受控连接器按版本解密，出站仅允许控制面审核的域名、TLS 和网络范围，拦截 SSRF/重定向越界。客户 Authorization 不原样转给供应商。配置导入、模型名和工具参数按 schema 验证，价格发布检查上界/计量/恢复能力。

日志脱敏、采样和有界批量；金融命令回执与审计独立耐久。普通用户、客服、配置管理员、资金审批人、执行服务、资金 Worker、迁移 owner 分权。不要把拥有任意数据库 DML 的管理员界面称为“资金写权限已封闭”。

原始提示词、产物与最小计费证据分开保留；加密、访问审计、保留和删除遵循适用政策。技术方案不凭空规定全球统一法定保存年限。

## 9. 停机、发布与值班

执行节点先停止新许可、拒绝新长流并给在途调用有界排水；证据收尾有独立 AbortController、服务 deadline 和宽限；维护在途 Promise 注册表，Bun.serve 停服排水与该注册表一起等待，不能将返回 Response 视作收尾已完成。最终超时的调用保留 PG 事实，不能在 shutdown finally 一律免费释放。Financial Worker 停领取新任务，完成或安全放弃本地认领。Bun Worker 线程与此处的耐久金融任务处理器是两种不同概念。

新系统正常版本演进需要 schema/RPC 能力探测与发布屏障；变更 Money 精度、价格语义、发送权或未知处置属于高风险契约，不能只滚动替换一半实例。这里没有其他项目旧状态/旧表的兼容义务。

值班手册至少覆盖：停账户/供应商/资金组新调用、费用未知查询、免收与成本保留、grant/return 卡住、PG 安全切主、从备份恢复、证据冲突、错误价格冻结、支付未知和退款复核。
