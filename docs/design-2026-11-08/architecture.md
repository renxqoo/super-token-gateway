# 总体架构

版本：1.1 · 2026-11-08。本文是新系统的目标设计。所有模块、接口和表名均为新定义，尚未实施。

## 1. 目标与验收边界

建设一个面向个人和组织的模型接入与计费平台。对外提供 OpenAI 兼容流式/非流式调用、能力允许的其他协议和异步媒体任务；对内统一用户资金、供应商成本、路由和故障恢复。

| 目标 | 定义 |
| --- | --- |
| 持续吞吐 | 10,000+ 成功受理并实际执行的业务请求/秒，不含快速拒绝或健康检查 |
| 请求类型 | 长流、短 JSON、二进制和异步任务分别测试，不用小响应代替真实流量 |
| 用户资金 | 预付费默认无透支；同一业务意图原始收费最多一次 |
| 正常交付 | 终态收据已耐久保存后，才发送正常完成标记/最终成功响应 |
| 未知结果 | 可查询、有金额上限、有处置时限，不能按租约推断“供应商未执行” |
| 故障域 | 在约定 PG 同步复制与安全切主范围内，已确认资金提交不丢；跨地域灾难另定 RPO |
| 可审计 | 用户实收、未收、估算、供应商应计/开票成本分别可解释 |

初始建议目标：健康依赖下平台 pre-upstream p99 ≤30ms、最终收据保存 p99 ≤50ms、正常异步结算 p99 ≤5s；可控假上游下合格成功率 ≥99.9%。这些是待验证目标，不是硬件容量承诺。

## 2. 核心决策

1. **执行与资金分开扩展。** 流的连接、背压、协议转换不占用资金事务或资金连接。
2. **先授权一次物理调用，再发送。** 客户资金预扣、供应商成本预留和首次调用许可在同一资金分片事务内提交。
3. **资金权威在 PG。** Redis 不持有唯一余额、预扣或未落账事实；开启 AOF 也不改变这条边界。
4. **消费额度预先分配。** 一个付款账户有多个已融资的消费单元，减少逐请求争用同一账户总行；父资金不能与子单元重复消费。
5. **用户收费与供应商责任分离。** 收据/收费可能已结束，供应商未知成本仍保留；按政策免收用户后，晚到费用不重新扣用户。
6. **每次物理发送有独立身份。** 同渠道重试也登记 invocation，不只保存最终选中的供应商。
7. **本地原子性与外部执行分别承诺。** 不把数据库锁、队列或租约说成供应商 exactly-once。
8. **按证据控制复杂度。** 初期不部署全局事件总线；资金库按稳定聚合可从一个物理组起步，扩组不改变业务身份。

## 3. 推荐技术选型与取舍

| 部分 | 推荐 | 原因与限制 |
| --- | --- | --- |
| 执行节点 | Bun + TypeScript，Bun.serve / fetch / Web Streams | 以有界流管线、AbortSignal 和独立进程承载连接；容量由真实负载验证 [R1] |
| 资金服务/后台处理器 | Bun + TypeScript，同一领域命令库，不与执行节点共享数据库写权限 | 金额与状态规则只有一处；后台复用命令，独立连接预算 |
| 权威资金存储 | PostgreSQL，单写主组、同步耐久提交、稳定分片 | 本地事务/约束/锁；不能跨物理组假设本地原子性 |
| Redis | 健康、软限流、配置分发、短期只读投影 | 丢失后保守重建；异步复制不提供无条件零丢提交 [R2] |
| 耐久后台任务 | 每资金分片 PG 工作表、批量认领、合并唤醒 | 请求事实与任务同事务；任务量/锁开销必须压测 [R3] |
| 原始证据/大对象 | 加密对象存储 + 数据库摘要和元数据 | 只在要求保留内容时存原文；金融最小证据优先保存在 PG |
| 控制面 | Bun + TypeScript API，管理界面独立部署 | 不参与每个 token/请求的同步配置读取 |
| 观测 | OpenTelemetry/指标/结构化日志 | 遥测可采样；账务证据不可依赖 best-effort 日志 |

Bun + TypeScript 是用户已确定的后端技术栈，执行、资金、后台和控制面统一使用。首版 PG 适配器选择 Bun.SQL，通过真实 PG 事务、金额编解码、连接断开与提交未知验收后锁定版本；适配器不得泄漏到领域模块。工程和资源规则详见 [Bun 运行与工程规范](bun-runtime.md)。

TypeScript 开启严格类型检查，同时对外部输入执行运行时 schema 校验。Bun 运行 TypeScript 不代替 `tsc --noEmit`；金额使用封装的 `bigint` 和有理数，数据库/JSON 边界使用十进制字符串。空响应基准不能证明万级长流。

首版不选 Redis 余额权威：需要额外解决复制提交、切主、重建和资金入账串行化。首版不选 Kafka 资金主日志：会引入新的提交权威、余额投影与追平协议。首版不强制独立供应商网络代理：执行节点内的连接器已经是受控出站边界；以后有独立安全/伸缩需求再拆。

## 4. 三个运行面

### 4.1 执行面：Execution Node

同一进程内包含入口协议、鉴权预筛、业务编排、路由、供应商连接器和流处理。客户/供应商数据不必穿过一串微服务；资金 RPC 只传控制与计费事实，不传整条输出流。

职责：生成每次 HTTP 的 ingressId；将客户端业务键解析为稳定 order；规范化请求；选择允许供应商；准备最终出站载荷；申请资金/调用许可；仅发送新授予的一次调用；增量解析与背压；完成前提交最终证据。

执行节点不直接写资金表，不接受用户指定付款主体或内部渠道 ID，不在内存里维护唯一的待扣款记录。

### 4.2 资金面：Finance Service + Financial Worker

Finance Service 负责金融命令、身份/政策最终守卫、价格重算、账户归属、预留与收费。Worker 使用同一命令库执行结算、退款、恢复和对账，资源池独立。

多个服务实例可以处理同一个资金组，正确性由 PG 的唯一键、行锁和事务保证，不依赖“只有一个 Bun 进程活着”。一个命令只能作用于其授权的付款账户/供应商额度。

### 4.3 控制与运营面

发布不可变产品/价格、供应商能力、凭证/配额域和路由策略；发起充值、风险额度分配、账户冻结、审批和证据核对。管理页的投影视图不是金融授权依据。

即时撤销/冻结通过对应资金组的权威政策命令生效，然后发布缓存事件；不能先改控制台异步投影就声称资金授权已吊销。

## 5. 数据与聚合归属

付款聚合 `billing_account` 是可共同消费资金的边界：个人可以独占一个，组织可以由多个成员/凭证共用。所有资金来源、消费单元、订单、调用、证据、收费和硬消费限额都归同一个资金分片。组织共享订阅不被任意 user hash 拆散。

| 数据 | 权威所有者 |
| --- | --- |
| 身份登录 | 身份系统；资金组另持有本账户可消费凭证/成员政策的权威许可 |
| 产品/用户价格/上游能力 | 版本化配置库，发布内容在金融命令中校验并封存 |
| 客户余额/预留/收费 | 对应付款账户的 PG 资金组 |
| 单次供应商调用和费用责任 | 同一订单的资金组 |
| 全局供应商成本上限 | 预算发行者；预先分配给资金组的 allowance 由本组独占消费 |
| 供应商健康、软并发/速率 | Redis 运行状态；最终真实限额仍由供应商与财务预算约束 |
| 分片定位 | 固定虚拟分区映射，带 placementEpoch |
| 观测/报表 | 权威事实的派生视图，不能反写纠正余额 |

## 6. 金融路径

1. 执行节点完成可信鉴权上下文、静态输入验证与已有意图查询；新意图才准备报价和路由。
2. 在调用之外准备最终载荷和计费上界，取得有界运行许可。
3. `AdmitAndPermit` 在本地资金事务同时完成：业务键绑定、用户来源预留、硬限额预留、供应商 allowance 预留、订单/首次调用/许可与回执。
4. 只有这次收到 `CREATED_PERMIT` 的 owner 能发送一次。重放命令只能得到 `OBSERVE_ONLY`，不能再次获得可发送回执。
5. 数据流结束前 `SealEvidence` 保存最小原始用量证据、选择计费事实、创建耐久金融工作项。正常完成标记等待其提交。
6. Worker 执行 `Capture`：实际扣款、释放剩余预留、双分录、收费唯一记录和工作终态同事务提交。
7. 供应商成本独立应计/核对；未知执行进入恢复与风险处置，不自动启动另一个调用。

网络等待从不发生在持有资金行锁或 PG 连接的事务中。授权提交响应未知不等于失败；查询旧操作，不换新键重发。

## 7. 处理外部结果未知

供应商可提供的幂等、最终查询、账单关联、取消与最大费用保证分别验证。首字节前失败可能已经产生费用；收到 partial 累计用量也不自动等于最终账单。[R4]

默认请求政策包含未知处理截止时间与平台承担预算。无法恢复的订单可以原子封为 `NO_CHARGE` 并释放用户资金；该状态永久禁止晚到证据再次原始收费。对应供应商 allowance 仍为 HELD，或者按明确的审计流程转入最坏成本准备金，不能直接返还可用预算。

这里并不要求先证明供应商绝对没执行才允许平台决定免收用户。安全前提是：平台明确接管费用责任、原用户账单不可复活、原供应商预留不被重复使用、原意图不再透明重试。取消供应商责任或归还其预算，则仍需要可靠未执行证据或完成的成本核销。

未知敞口达到资金组/供应商上限即停止相应新调用。系统不承诺同时满足“供应商不可查询、立即精确收费、平台零损失”。

## 8. 扩展策略

### 8.1 用户资金消费单元

充值进入 root 资金账户。资金重平衡命令把真实已入账本金调给多个 spend cell：root 减少、cell 增加，双分录同事务。授权只占一个/少数 cell 的预留，不逐请求更新付款账户总余额行。余额总览汇总 root + cells，不能将已分配本金计两次。

cell 低水位时批量补给，不允许“缓存 miss 从旧总余额初始化新 cell”。更大的单笔调用需要有界重平衡/多 cell 分配；资金碎片不足应返回暂不可分配，不能误报真实余额不足。精确规则见资金文档。

### 8.2 供应商额度预分配

预算发行者从 pool 先扣出一段本金，签发唯一 grant，再由目标资金组幂等接收。每请求只动本组 allowance cell。跨组派发采用保守的资金在途协议：没确认收到的 grant 仍占发行者本金；没耐久退回的可用额度不再次分配。

首个物理组可以同库实现上述原子划拨，多个物理组才需要跨组交付；协议身份与幂等键从一开始一致。pool 不逐请求锁，额度耗尽不会在请求里启动跨库事务。

### 8.3 资金分片

先定义固定虚拟分区与映射，不使用随实例数变化的 hash%N。一个资金聚合不跨写库；跨账户转账另走显式转账工作流，不能假设两库本地事务。

物理组数由真实单组容量与故障余量决定，既可从一个开始，也可按基准预置多个。分片增加不能解决同一个 cell 或硬限额根行的热点，必须同时验证单付款账户压力。

## 9. 模块组织与权限

建议新仓库结构：

```text
apps/execution-node/src/main.ts    Bun.serve、执行节点装配
apps/finance-service/src/main.ts   金融 RPC 与权威命令
apps/financial-worker/src/main.ts  PG 金融任务、恢复、核对
apps/control-api/src/main.ts       配置发布、运营与审批
packages/contracts/src            版本化 DTO、运行时 schema、编解码
packages/execution/src            订单编排、路由、流屏障
packages/connectors/src           供应商协议、最终载荷、证据与错误归因
packages/finance/src              Money、预留、收费、预算、退款、不变量
packages/storage-pg/src           Bun.SQL 适配器、事务与权限
packages/storage-objects/src      原始对象与摘要适配器
packages/control/src              发布、能力、凭证与政策
packages/operations/src           任务、对账、风险和审计
packages/runtime/src              许可、取消、计时、观测与生命周期
db/schema                        从空库建设的版本化 DDL
tests                            规则、真实 PG、协议假体与故障验收
package.json / bun.lock           workspace 与锁定依赖
tsconfig.json                    严格类型配置
```

用 workspace exports、静态依赖检查和独立部署凭证落实边界；包名本身不提供隔离。执行组件不能导入资金表写实现；连接器不决定扣费/退款；资金模块不依赖 HTTP 流实现。金融写入只有命令层，后台和 RPC 共享同一规则，不允许各自维护一个简化版本。

客户不能访问金融 RPC。内部服务以 mTLS/工作负载身份认证，命令再校验付款账户、凭证权限、资产、政策与载荷摘要。平台凭证明文只在连接器受控路径使用，不能作为日志、队列或证据的一部分。

## 10. 最小部署与演进

首个可上线版本具有执行节点、资金服务/Worker、控制 API、PG 主/安全同步候选、Redis 和证据对象存储。服务类型分开不意味着首日需要十几个独立微服务；控制与预算发行可以由同一低频管理部署承载。

每个服务使用独立 Bun 进程/容器和资源预算，入口负载均衡分发连接；首版不依赖 Worker 线程持有资金许可。异步 I/O 不意味着同步解析、计量和日志不会阻塞事件循环。CPU 密集工作只有在保持最终载荷与许可绑定的前提下，才可移到有界计算池。

以后按指标扩展执行节点、独立财务池、增加资金组、细分消费单元、隔离观测管道。事件总线仅在 PG 工作表/下游分发已有实际瓶颈时评估，域状态和幂等不随队列技术更换。

不存在旧代码回退/旧字段兼容计划。这里只设计新系统正常的 schema/API 版本演进、灰度发布、备份恢复与业务停机边界。
